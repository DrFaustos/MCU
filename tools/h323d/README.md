# mcu_h323d — H.323-хост единого медиа-слоя

Отдельный C++-процесс на **H323Plus**, который слушает порт **1720** и
управляет H.323-вызовами. Python-клиент (`mcuclient/h323_host.py`)
общается с ним по **unix-сокету** через newline-delimited JSON.

## Зачем отдельный процесс

Python-биндингов H323Plus **не существует**. H323Plus — callback-тяжёлый
C++-стек, владеющий RTP/PCM/кодеками; держать его в Python-процессе нельзя
(GIL, утечки, падения нативного кода). Поэтому H323Plus живёт в своём
процессе, а Python остаётся оркестратором и микшером — см.
`docs/ADR-0002-h323plus-unified-media.md` (Вариант B).

## Запуск вручную (для отладки)

 

При старте хост печатает `[mcu_h323d] H.323 слушает 0.0.0.0:1720`, а событие
`ready` шлёт в момент подключения Python-клиента (а не при старте), чтобы
готовность не терялась, пока клиента ещё нет.

## Протокол IPC

Одна JSON-строка на сообщение, разделитель — `\n`.

### Хост → Python (события)

| Событие | Поля | Смысл |
|---------|------|-------|
| `ready` | `port`, `name` | Эндпоинт поднят; шлётся при подключении клиента |
| `pong` | — | Ответ на `ping` |
| `call.incoming` | `token`, `alias`, `ip` | Входящий H.323-вызов |
| `call.connected` | `token`, `alias`, `ip` | Вызов установлен |
| `call.disconnected` | `token`, `alias`, `ip`, `reason` | Вызов завершён |
| `error` | `message` | Ошибка обработки команды |
| `shutdown` | — | Хост завершается |

### Python → хост (команды)

| Команда | Поля | Смысл |
|---------|------|-------|
| `ping` | — | Проверка связи (ответ `pong`) |
| `call.answer` | `token` | Ответить на вызов |
| `call.hangup` | `token` | Завершить вызов |
| `shutdown` | — | Остановить хост |

## Медиа (следующий шаг)

Сейчас по IPC идёт только **сигнализация/управление вызовами** (Этап 1):
H.323-звонок принимается, участник попадает в общую комнату. Передача PCM
между хостом и Python-микшером (`mcuclient/audio_mixer.py`) — следующий
шаг: отдельный бинарный канал (shmem/pipe), чтобы не смешивать с JSON.

## Видео по IPC (Этап 4)

Декодированный кадр отдаётся **вторым unix-сокетом**, бинарно: по умолчанию
`<--socket>.video`, отдельно `--video-socket PATH`. В общий JSON-сокет кадр
попадает (событие `video.frame`, base64) **только пока к бинарному сокету никто
не подключился** — это запасной путь для отладки, а не режим работы.

### Почему отдельный сокет, а не base64 в общем JSON

Три причины, и все три проверены на коде, а не на вкусе:

1. **Очередь одна, и аудио в ней важнее.** `mcu_ipc::Server` пишет события в
   один `PPassThroughCommand`-подобный поток: кадр 352×288 YUV420P = 152064
   байта, в base64 — 202752 символа. Пять таких строк в секунду вставляют в
   поток между `pcm.in`-кадрами ~1 МБ, и голосовая задержка становится функцией
   картинки. Отдельный сокет = отдельная очередь: затык видео не трогает аудио.
2. **Бинарный формат не требует кодирования в хосте.** В PTLib нет JPEG-кодера,
   так что «сжать кадр в base64-JPEG на C++» означало бы приносить свой кодек.
   RGB/JPEG делает Python (`mcuclient/h323_video_bridge.py`), хост отдаёт ровно
   то, что ему дал plugin-кодек.
3. **Переполнение должно быть дёшевым.** `mcu_video::FrameServer` хранит **один
   последний кадр на вызов** (`latest-wins`), сбрасывает устаревшие и отваливает
   клиента, который не читает (SO_SNDTIMEO 500 мс, жёсткий потолок 2 с). Память
   ограничена ~8 кадрами независимо от того, зависла панель или сеть.

Формат кадра в аудио-очереди при этом **не** «выключается» молча: если
бинарный сокет не поднялся, хост честно пишет в лог, что кадры пойдут base64,
и продолжает отдавать их в `video.frame` — лучше дорого, чем «видео нет».

### Формат записи (то же в `video_frame.hpp` и в `h323_video_bridge.py`)

`struct "<4sBBHHHHIQI"`, little-endian, без выравнивания, 30 байт заголовка:

| Смещение | Поле | Размер |
|---|---|---|
| 0 | магия `MCUV` | 4 |
| 4 | version (`1`) | 1 |
| 5 | format (`1` = YUV420P) | 1 |
| 6 | reserved | 2 |
| 8 | `token_len` | 2 |
| 10 | `width` | 2 |
| 12 | `height` | 2 |
| 14 | `seq` | 4 |
| 18 | `ts_ms` (monotonic) | 8 |
| 26 | `payload_len` | 4 |
| 30 | `token` (UTF-8) | `token_len` |
| … | Y (w·h), U (w/2·h/2), V (w/2·h/2) | `payload_len` |

Магия в начале каждой записи обязательна: у потокового сокета нет границ
сообщений, и после обрыва читатель ищет начало, а не угадывает по длине
(`tests/test_h323_video_bridge.py` сверяет размер заголовка текстом C++).

### Команды и события видео

| Направление | Имя | Поля |
|---|---|---|
| хост → Python | `video.frame` | `token`, `width`, `height`, `seq`, `fmt`, `data` (base64; **только без бинарного клиента**) |
| хост → Python | `call.media` | `kind=video`, `direction` (`encoder`/`decoder`), `codec`, `width`, `height`, `fps` |
| Python → хост | `video.out` | `token`, `data` (base64 YUV420P), `width`, `height` |
| Python → хост | `video.pattern` | `token`, `on` (`1`/`0`) |

`video.out` пишется в ring encoder-канала, и `McuVideoChannel::Read` отдаёт его
кодёру, соблюдая темп (реальное время, как требует `channels.cxx:897`).
`video.pattern` включает **паттерн внутри хоста** (75% полосы BT.601 + бегущий
блок, `draw_pattern`): картинка в вызов уходит без единого внешнего кадра и без
Python — это минимум, которым стенд проверяет «скелет картинки», когда кодера в
сборке нет.

Хост **не** умеет декодировать JPEG и не масштабирует входящий кадр: Python
обязан прислать ровно `width*height*3/2` байт заявленного размера (меньше —
команда отклоняется, а не обрезается).

### Реальность кодеков в H323Plus 1.28.0 (важно для «почему картинки нет»)

В 1.28.0 видеокодеков **внутри библиотеки нет вообще** — только plugin-формат
(`plugins/video/`): `H.261-vic`, `H.263-1998`, `H.263-ffmpeg`, `H.264` (x264 +
libavcodec). Отсутствие плагинов выглядит ровно как «видео не согласовалось»,
поэтому перед стендом проверяем:

```bash
ls "$PREFIX"/lib/ptlib-*/codecs/video/*_video_pwplugin.so
```

Пустой список — значит `OpenVideoChannel` не вызывается никогда, и ни один тест
видео не обязан проходить. Открытие канала (и `call.media kind=video`) — уже
доказательство, что плагин поднялся; дальше кадр идёт по сокету.

### Как проверить без терминала

```bash
./scripts/h323_in_container.sh h323d                    # сборка с video.hpp
scripts/testbed/h323_video_smoke.sh                     # сокет, команды, живучесть
python3 -m pytest tests/test_h323_video_bridge.py -q    # контракт Python ↔ C++
```

`h323_video_smoke.sh` проверяет ровно то, что нельзя проверить юнит-тестом:
сокет кадров поднят и называется `<socket>.video`, обе команды отвечают
ошибкой на несуществующий токен (а не роняют хост), хост переживает
подключение и смерть видеочитателя, сокеты снимаются при останове.
