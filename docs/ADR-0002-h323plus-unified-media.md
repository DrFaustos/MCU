# ADR-0002: Единый медиа-слой на H323Plus (H.323 + SIP + микшер в одном процессе)

**Статус:** Accepted
**Дата:** 2026-09-22
**Контекст:** переделка MCU под функционал вызовов «как OpenMCU.ru» с лучшей совместимостью (Sony/Polycom)

---

## Вопрос

Как добиться того, чтобы наш MCU принимал **и SIP, и H.323**, имел
**микширование аудио/видео** и лучшую совместимость с проблемными
терминалами (в первую очередь Sony), чем у OpenMCU.ru?

Короткий ответ: **встроить H323Plus/PTLib как единый медиа-слой и
постепенно заменить PJSIP-медиа на него**. OpenMCU.ru работает именно так:
он использует `H323Connection` даже для SIP-соединений, поэтому у него
один RTP/PCM-конвейер и один микшер на оба протокола.

---

## 1. Текущее состояние (факты, не предположения)

| Компонент | Сейчас | Проблема |
|-----------|--------|----------|
| SIP-сигнализация | PJSIP / pjsua2 (`mcuclient/sip_engine.py`) | работает |
| H.323 | **нет** (только внешний Asterisk-шлюз, не проверен) | звонок по H.323 **не принимается** |
| Аудиомикшер | **нет** | конференция 3+ участников невозможна |
| Видеомикшер | **нет** (только одиночный поток) | нет видеостены/раскладок |
| Транскодирование | частичное | проблемы с кодеками Sony (G.722.1C/G.719) |

Прямой ответ на вопрос пользователя: **H.323-вызов сейчас не будет принят**,
потому что процесс не слушает порт 1720 и не имеет H.225/Q.931-стека.
Протокол выбирает вызывающая сторона на своём терминале; чтобы принимать
оба, нужно иметь оба стека в одном процессе.

---

## 2. Почему H323Plus, а не два параллельных стека

Главный риск наивного подхода «PJSIP для SIP + H323Plus для H.323» —
**конфликт двух медиастеков в одном процессе**. Оба хотят владеть:

* RTP-сессиями и jitter-буфером;
* декодированием/кодированием кодеков;
* PCM-буферами и точками микширования;
* AEC (эхо-подавлением).

Если оба стека декодируют в PCM независимо, мы получаем **два несогласованных
PCM-домена** и не можем смикшировать участников разных протоколов.

**Решение OpenMCU.ru:** он не смешивает PJSIP и H323Plus. Он использует
`H323Connection` как **универсальную абстракцию соединения** — и для H.323,
и для SIP. Медиа (RTP, кодеки, логические каналы, микшер) целиком лежит
в H323Plus/PTLib. SIP-сигнализация надстраивается над тем же
`H323Connection`.

**Мы принимаем тот же принцип:** H323Plus/PTLib — единственный владелец
медиа. SIP-сигнализация и H.323-сигнализация — два «фронта», ведущие в
один медиа-слой.

---

## 3. Решение

### 3.1. Единый медиа-слой

 

* **H323Plus** владеет RTP, jitter-буфером, кодеками, логическими каналами.
* **AudioMixer** (наш) работает поверх PCM-буферов H323Plus.
* **VideoMixer** (наш) — voice-activated + раскладки, с кэшем исходящего видео.
* **SIP-фронт** создаёт `H323Connection` для SIP-вызовов (как в OpenMCU.ru).

### 3.2. Версии (проверенная комбинация)

Используем форки willamowius — они поддерживают стабильный API:

| Компонент | Версия | Источник |
|-----------|--------|----------|
| PTLib | 2.10.9.6 | github.com/willamowius/ptlib |
| H323Plus | 1.28.0 | github.com/willamowius/h323plus |
| OpenSSL | 3.0.x | системный / из дистрибутива |

Сборка строго в порядке: **PTLib → H323Plus → MCU**.

### 3.3. Что заменяется в текущем коде

| Файл | Судьба |
|------|--------|
| `mcuclient/sip_engine.py` | постепенно заменяется на SIP-фронт поверх H323Plus |
| `mcuclient/pjsip_adapter.py` | выводится из эксплуатации |
| `mcuclient/call_manager.py` | переиспользуется (абстракция вызова) |
| `mcuclient/room.py` (модель комнаты) | переиспользуется |
| `mcuclient/rtcp_metrics.py` | заменяется на RTCP H323Plus |
| `tests/test_sip_engine_ip.py` | переписывается под новый SIP-фронт |

## 4. Поэтапный план

### Этап 0 — Инфраструктура (безопасный, не ломает текущий код)

1. `scripts/install_h323plus.sh` — сборка PTLib+H323Plus из форков
   willamowius с фиксированными версиями.
2. Docker-образ с собранным стеком (не трогаем рабочее окружение).
3. Проверка: `libh323_*.so` собирается, `h323plus`-примеры запускаются.

### Этап 1 — Приём H.323

1. `mcuclient/h323_endpoint.py` — обёртка над `H323EndPoint`.
2. Приём входящих H.323-вызовов (порт 1720).
3. Участники попадают в **тот же** `RoomManager`, что и SIP.

### Этап 2 — SIP через H323Plus (самый рискованный)

1. Изучить `sipendpoint.cxx` в OpenMCU-ru как референс.
2. `mcuclient/h323_sip_adapter.py` — SIP-фронт, создающий `H323Connection`.
3. Переписать `tests/test_sip_engine_ip.py`.

### Этап 3 — Аудиомикшер (ядро MCU)

1. `mcuclient/audio_mixer.py` поверх PCM-буферов H323Plus.
2. Нормализация суммы (деление на число активных каналов) — иначе
   «base noise».
3. AEC — из PTLib или свой.

### Этап 4 — Видеомикшер

1. Voice-activated переключение (минимум).
2. Кэш исходящего видео (как в OpenMCU.ru).
3. Раскладки 2x2 / 3x3.

### Этап 5 — Совместимость Sony/Polycom

1. Расширенная SDP/TCS-негоциация: `fmtp` для G.722.1C (mode 24/32/48), G.719.
2. H.264 High Profile, согласование `profile-level-id`.
3. H.239 (двойной поток: докладчик + презентация).
4. Диагностика: логировать, **почему** кодек не согласовался.

## 5. Последствия

### Положительные

* Один медиа-конвейер → один микшер на оба протокола.
* H.323-приём без внешних шлюзов.
* Гибкая TCS/SDP-негоциация H323Plus → шанс обойти проблемы OpenMCU.ru с Sony.
* Переиспользуем опыт OpenMCU.ru (проверенная архитектура).

### Отрицательные / риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Сборка PTLib/H323Plus на Windows | высокая | сначала Linux; Windows позже |
| Конфликт PJSIP и H323Plus | средняя | не смешивать: полная замена PJSIP-медиа |
| Потеря текущей функциональности (видео MCU↔MCU) | высокая | сохранить `sip_engine.py` как fallback под флагом |
| Проблемы согласования с Sony | средняя | кастомизация TCS-негоциации |
| Трудоёмкость микшера | высокая | поэтапно, с тестами на каждом шаге |

### Что НЕ делаем

* ❌ Не оставляем два параллельных медиастека (PJSIP-медиа + H323Plus-медиа).
* ❌ Не тащим GStreamer/Asterisk как «временное» решение — это компромисс,
  который придётся выкидывать.
* ❌ Не начинаем с микшера, пока нет приёма H.323 и SIP-фронта.
