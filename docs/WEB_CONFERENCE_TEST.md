# Web-конференция: как проверить из браузера (без второй машины)

Документ для разработчика/агента: как **за минуты** поднять MCU с web-панелью
и проверить вход в конференцию из браузера, публикацию своей камеры/микрофона
и раздачу медиа другим участникам (fan-out). Дополняет
[TESTING_TWO_CLIENTS.md](TESTING_TWO_CLIENTS.md) (там — два нативных клиента).

---

## 1. Требования

* `aiortc` — для WebRTC-ingest и fan-out:

 

Без `aiortc` панель работает, но `/api/webrtc/offer` отвечает **503**, а
публикация/приём видео недоступны.

* Для `getUserMedia` (камера/микрофон в браузере) нужен **secure context**:
  `https://` либо `http://localhost` / `http://127.0.0.1`.

## 3. Сценарий проверки в браузере

1. Откройте `http://127.0.0.1:8080/`.
2. Введите **имя** и войдите — появится сетка тайлов.
3. Нажмите **«Опубликовать камеру/микрофон (WebRTC)»** — браузер через
   `getUserMedia` шлёт свои треки в MCU (`POST /api/webrtc/offer`,
   `role=publish`, `participant=<id>`).
4. Откройте **вторую вкладку** (или другой браузер) и войдите под другим именем —
   каждый участник должен **увидеть видео** и **услышать звук** другого
   (fan-out).

### Что смотреть при проблемах

| Запрос | Что показывает |
|--------|----------------|
| `GET /api/conference` | список веб-участников (`kind=web`) |
| `GET /api/webrtc/sessions` | активные сессии и их `role` |
| `GET /api/status` | поля `webrtc_available`, `webrtc_sessions`, `conference_participants` |
| лог сервера (`mcu-client.log`) | строки `mcuclient.webrtc`, `mcuclient.sfu` |

Типичные причины «нет видео/звука»:

* панель открыта по `http://<IP>` (не localhost) без TLS — браузер блокирует
  `getUserMedia`; включите `--web-tls`;
* `aiortc` не установлен — offer отвечает 503;
* соединение за NAT без STUN/TURN — настройте `features.web.ice_servers`
  (см. [WEB_CONTROL.md](WEB_CONTROL.md), §7b);
* участник не публикует — проверьте, что нажата кнопка публикации и в
  `/api/webrtc/sessions` есть сессия с `role=publish`.

## 4. Автотесты (без браузера)

 

* `test_webrtc_sfu.py` — конференц-ядро (участники + шина медиа);
* `test_webrtc_ingest.py` — приём треков, доступность aiortc;
* `test_webrtc_publish_bus.py` — регрессия: принятые кадры публикуются в шину
  (без этого fan-out отдаёт пустые треки);
* `test_webrtc_e2e.py` — реальный offer/answer с aiortc (скипается без него);
* `test_web_server.py` / `test_web_http.py` — REST/HTTP, включая roundtrip
  конференции.

## 5. Границы (что этот сценарий НЕ проверяет)

* Запись веб-потока — нет.
* Микширование аудио — нет: каждый зритель получает отдельный трек на каждого
  публикатора (для небольших комнат это нормально).
* Симулкаст/джиттер-буферы — нет.
* Раздача SIP/H.323-видео в браузер напрямую — нет (нужен транскодинг).
* Полноценный тест «два реальных браузера» требует браузера с рабочим WebRTC
  (Playwright не гарантирует медиа-треки). Серверная логика покрыта тестами,
  а viewer-offer проверен с настоящим `aiortc`.
