**Стадия: pre-alpha — активная разработка.**

Приложение находится в ранней разработке. Стабильных релизов нет,
статус функций меняется от сборки к сборке. Всё ниже — снимок состояния,
а не гарантия.

## Что НЕ реализовано / ограничено

* 🟡 **H.323-приём — через отдельный C++-хост `mcu_h323d`** (Вариант B, ADR-0002): хост на H323Plus собирается (`tools/h323d`, CMake), слушает 1720, Python подключается по unix-сокету (`mcuclient/h323_host.py`, `run.py --h323 --h323-socket PATH`). Проверено: сборка + IPC-дымовой тест `scripts/h323d_smoke.py` (ready + ping/pong). E2E-звонок с реального H.323-терминала пока не прогонялся. `h323_gateway.py` (Asterisk `chan_ooh323`) — устаревший обходной путь. См. `docs/ADR-0002-h323plus-unified-media.md` и `docs/H323_STATUS.md`.
* ❌ Реальное микширование медиа (аудио-суммирование с AEC,
  видеостена). Сейчас это скорее клиент/простой SFU, а не полноценный MCU.
  По ADR-0002 аудиомикшер и видеомикшер — Этапы 3–4.
* 🟡 NAT traversal: для WebRTC (браузер) — STUN/TURN настраиваются
  (`features.web.ice_servers`); для SIP/H.323-вызовов — по прямому IP.
* 🚧 Шифрование SRTP/TLS — опционально и по умолчанию выключено.
  Для закрытого контура это осознанное решение (см. ADR-0002 §3.3):
  H.235/SIP TLS/SRTP не используются.
* 🟡 Адаптивный битрейт по RTCP: авто-опрос метрик включён (`features.rtcp_poll_interval`), требуется проверка на реальном канале с потерями.
* ❌ Передача файлов (файлового обмена в стеке нет; текстовый чат работает —
  см. таблицу выше и `scripts/testbed/run_two_instance_chat_test.sh`).
* ❌ Захват экрана на Wayland через PipeWire/порталы.

## Предупреждения

* Сборки могут **ложно срабатывать в Windows Defender/SmartScreen**
  (нет цифровой подписи).
* Возможны **аварийные завершения** при звонках и работе с медиа.
* Конфигурация и API могут меняться без предупреждения.

## Как помочь

Проект тестируется вручную на реальных ВКС-терминалах. Если нашли
проблему — приложите `mcu-client.log` (создаётся рядом с приложением)
и укажите модель терминала, протокол (SIP/H.323) и шаги воспроизведения.

## Журнал исправлений

### 2026-10-10 — отказ сайдкара на 20 секунд становился «mediasoup выключен» до перезапуска

**Симптом.** `mediasoup` включён (`enabled: true`), сайдкар в момент первого
обращения ещё поднимается (это секунды после старта). Мост не поднялся — и
больше не поднимется НИКОГДА, до перезапуска приложения: сайдкар ожил, а
`mediasoup_rtp_bridge()` по-прежнему `None`. Замерено зондом
`.agent/probe_ms_retry.py`: 1 обращение к control API за всё время. Панель при
этом отдаёт `mediasoup_rtp: None` — ровно то же значение, что при выключенном
режиме, а `POST /api/mediasoup` отвечает 503 «mediasoup не включён».

**Корень.** В ленивой фабрике `False` в кэше значил ДВА разных состояния:
«выключено оператором» и «пробовали — не вышло». Раз кэш выставлен, повторной
попытки нет. Ветка `except` в `mediasoup_signaling()` писала только `log.debug`
и не называла причину; в `mediasoup_rtp_bridge()` была та же молчаливая ветка
(`log.debug` + `_ms_rtp = False`, `_ms_rtp_error` пустой). Прошлый срез
(`6b93fb8`) закрыл схлопывание отказа в `None` только для `bridge.start()`, а
отказ signaling/ensure_room остался молчаливым.

**Почему наивный починка опасен (замерено).** `push_sip_pcm_to_sfu()` дёргает
фабрику мостов на каждый кадр — **3000 обращений за минуту звонка на сессию**.
Ретрай «пробовать при каждом вызове» выливается в 3000 запросов к control API в
минуту. Поэтому повтор есть, но ограничен: `MS_RETRY_INTERVAL = 10.0`, общий
срок (`_ms_rtp_retry_at`) для обеих фабрик. «Выключено оператором» по-прежнему
кэшируется как `False` и НЕ повторяется — иначе выключенный режим стучался бы в
несуществующий сайдкар.

**Второй дефект, который создал бы сам ретрай.** Точечного закрытия транспорта у
сайдкара не было: `room.close()` закрывает комнату целиком, а `stop()` моста
лишь обнулял `_transport_id` — для сайдкара это значило «транспорт живёт
дальше». Пока повторных попыток не было, утечки не было; с ретраем каждый цикл
«отказал — попробовал снова» поднимал новый `PlainTransport`, а он держит
UDP-порт из `rtc_min..rtc_max` (по умолчанию 40000-40100 = 101 порт) — диапазон
исчерпался бы примерно за 17 минут непрерывных отказов, и сайдкар перестал бы
создавать транспорты вовсе. Лечить отказ ценой утечки ресурсов нельзя, поэтому в
срез вошли: `Room.closeTransport()` + маршрут `POST /transports/close` +
`MediasoupClient.close_transport()` + вызов на КАЖДОМ пути отказа моста от уже
созданного транспорта (`_close_remote_transport()`, в т.ч. в `stop()`;
повторный `stop()` тот же id не шлёт).

**Живая проверка (не статическая).** Сайдкар с `rtc_min/max = 40600..40604`
(5 портов), внешний HTTP-клиент (`.agent/probe_sidecar_close.mjs`): close
отвечает `ok`; повторный close того же id — 400 «Транспорт … не найден» (значит
снят с учёта комнаты); цикл «создал/закрыл» прошёл 8 раз подряд, т.е. порты

**Третье лицо того же дефекта.** 503 `POST /api/mediasoup` врал «mediasoup не
включён», когда режим включён, а сайдкар недоступен: `ms-conference.js`

### 2026-10-10 — панель рапортовала о звуке, которого не было, а справочник — о полях, которых не было

**Симптом 1 (счётчики лгут).** Зонд `.agent/probe_sip_port_silent.py`: порт
получает три кадра НЕИЗВЕСТНОЙ формы, `_fill_frame` не записывает ни байта и
молча возвращает `None`, а `tx_frames` = 3. Эти числа агрегирует
`sip_bridge_service._collect_counters()` и показывает `GET /api/status`, т.е.
панель утверждает, что звук в вызов уходит, когда не уходит ничего. Приём
молчал так же: `rx_frames` = 0 и ни строки в журнале. Третья форма того же
вранья: pjsua2, отклонивший `clockRate`, оставлял порт «созданным» с
`fmt.clockRate = 0`, а `stats()` рапортовал запрошенные 16000 Гц.

**Корень.** Три молчаливых развилки в `mcuclient/sip_audio_port.py`:
`_fill_frame` возвращал `None` и при успехе, и при отказе (вызывающий не мог
отличить переданный кадр от незаписанного); `except Exception: pcm = b""` на
приёме сливал «НЕ ПРОЧИТАНО» со штатной тишиной; `except Exception: pass` при
сеттерах поля формата. Класс тот же, что закрыт в `doctor.py`, `log.py`,
`run.py`, `media_devices.py`, `rtp_audio.py`, — но здесь его молчание читает
панель, а не журнал.

**Правка.** `_fill_frame` → `bool` (записал / не записал). Приём разведён на
состояния: `_read_frame` отдаёт `(pcm | None, причина)`, где `None` — отказ и
`b""` — штатная тишина (null-аудио без микрофона); `_as_bytes` — единственная
точка приведения, поэтому не-буфер становится отказом «форма не распознана», а
не тишиной (без неё `callable(...)` сужает тип до `object`, и мусор ушёл бы в
звонок). Отказ называется РОВНО ОДНА WARNING на серию и снимается одной INFO о
восстановлении: кадр приходит 50 раз/с, построчный журнал дал бы ~1500 строк за
минуту звонка, а молчание читалось бы как «веб-участники добровольно молчат».
`tx_frames` растёт только на реально записанных кадрах. `_make_format` отдаёт
`(fmt, причина_отказа)` и `create()` ОТКАЗЫВАЕТСЯ поднимать порт, которому
pjmedia отклонил поле, — раньше такой порт выглядел рабочим и в журнале, и в
статусе. `stats()` порта отдаёт `frame_failures`/`last_error`, мост агрегирует
их в `frame_failures`/`frame_errors` панели.

**Симптом 2 (важнее по классу): документ обогнал код.** Строку
`` `sip_ports` (`rx_frames`, `tx_frames`, `frame_failures`, `frame_errors`) ``

`test_rest_api_tables_list_exactly_the_server_routes` сверяет ПУТИ маршрутов, а
поля ответов не сверял ни один тест. То есть зелёный набор стоял ровно там, где

**Страж.** `tests/test_doc_status_fields.py` (3 кейса): статика — обещанные

### 2026-10-10 — точка входа молчала ровно там, где её читают при «запуск не удался»

было некуда — логгер настраивается позже, в `main()`.

`except KeyboardInterrupt: pass` (431, 542, 569). Это не отказ, а штатная

docstring, а не спрятано: писать в уже закрытый логгер значит получить то

### 2026-10-10 — приложение молчало, когда молчал его собственный журнал

**Симптом.** README обещает: в Windows-сборке `--windowed` причина
«закрылось сразу после запуска» остаётся в `mcu-client.log`. Зонд на
незаписываемом пути (родитель лог-файла — обычный файл) показал обратное:
`_make_file_handler()` вернул `None` без единой строки вывода,
`_pick_log_path()` молча переехал в `~/.mcu-client` (а искать журнал учат
рядом с `.exe`), `_enable_faulthandler()` при отказе всех каналов оставил
`_log_fd = None` — трассировка segfault не шла никуда. `report_fatal()`
при этом печатал «Подробности в лог-файле: ПУТЬ», где файл физически не
мог существовать. В windowed-сборке stderr уходит в devnull, поэтому все
эти отказы — молчание единственного свидетеля.

**Корневая причина.** В `mcuclient/log.py` 7 из 9 `except` глотали молча
(`pass`, `return None`, `shown = False`). При разборе вскрылись ещё два
дефекта: `_log_fd` присваивался ДО `faulthandler.enable()` — при отказе
флаг «уже включено» оказывался выставлен, дескриптор тёк, а ранний return
навсегда запрещал повторную попытку (процесс оставался без свидетеля
segfault); флаг «сообщить один раз» объявлялся на классе, а писался в
экземпляр, то есть не работал вовсе.

**Правка.** Механизм `_startup_notice(message, via_log=True)`: до
`setup_logging()` заметка печатается в stderr и копится в
`_STARTUP_NOTICES`, `setup_logging()` переливает её в лог; после настройки
пишется немедленно — отказ в рантайме не может ждать второго
`setup_logging()`, которого не бывает. Названы все отказы: откат пути
журнала и полный отказ всех папок, незакрытый файловый handler, отказ
дублирования fd, отказ окна ошибки, отсутствие faulthandler (
«НЕ включён» против «включён только в stderr» — на windowed-сборке второе
равно первому). `report_fatal()` больше не обещает несуществующий файл.
Отказ `flush` ловится в `flush()`, а не в `emit()`: `StreamHandler.emit`
зовёт `flush()` сам, и в `emit()` он был бы неперехватим — ушёл бы в
`logging.handleError`, то есть в никуда.

Осознанное ограничение: заметка о битом flush идёт мимо логгера
(`via_log=False`) — логгер пишет в тот же файл, который отказался
сбрасываться, и заметка утонула бы в той же ошибке. На windowed-сборке с
мёртвым stderr этот единственный факт остаётся необнаружимым; это
зафиксировано в docstring, а не спрятано под «готово».

`build_appimage`, — вызывается в начале `main()`, рядом с отказом на
несовместимые флаги. Реализация остаётся одной: `build_appimage` зовёт её
же, а не дублирует. Архитектура сверяется с `APPIMAGE_ARCHES`:
`APPIMAGETOOL_URL` жёстко содержит `x86_64`, так что на `aarch64`
appimagetool не запустился бы; `platform.machine()` на Windows пишет
`AMD64`, поэтому сверяется нижний регистр. Отсутствие `file` теперь
отвечает `SystemExit`, как весь операторский ввод: трейсбек там, где виноват
не код, только мешает.

**Регрессии** — `tests/test_packaging_windows.py` (15 проверок, +3): чужая
ОС, чужая архитектура и отсутствие `file`; каждый кейс требует пустого
списка вызовов — то есть что отказ наступил ДО `ensure_pjsua2`,
`ensure_pyinstaller` и `build_binary`. Плюс хелпер `_stub_host`: подменяются
атрибуты модуля `build` (`platform`, `shutil`), а не stdlib — иначе прогон
на машине без `file` врал бы, а откат monkeypatch задевал бы чужие тесты.

**RED:** заглушить вызов `_ensure_appimage_host()` в `main()` → падают
ровно три новых кейса; `build.py` после прогона восстановлен побитово.

- **`media.transmitFrom()` в pjsua2 не существует** — `_attach_call` звал только

- **Порт жил на 16 кГц при веб-миксе 48 кГц**: pjsua2 обрезает кадр под размер

- **Порты не отвязывались от вызова** перед уничтожением (в медиаграфе pjsua2
  оставался маршрут на мёртвый объект) — добавлен `stopTransmit` при закрытии
  порта, при переезде слота на другой вызов и при остановке.
- `EventBus` не умел отписываться: подписка моста переживала остановку и
  удваивалась при рестарте панели. Добавлен `EventBus.unsubscribe`.
- Веб-микс для терминала собирается без голоса самого SIP
  (`AudioMixSession.mix_excluding` + `WebSession.web_mix_for_sip`), иначе
  терминал слышит собственный голос.
- Порядок вызовов для портов фиксирован по id участника

### 2026-09-22 — прокачка событий PJSIP в headless

`run.py` в headless-режиме (`--headless` / серверный цикл) теперь вызывает
`engine.process_events()` вместо голого `time.sleep()`. Без `libHandleEvents()`
входящие INVITE копились в буфере сокета (Recv-Q рос), авто-ответ не
срабатывал, и дозвониться до клиента было невозможно — процесс при этом был жив.
Новый метод `SipEngine.process_events(timeout)` защищён guard'ом по
`PJSIP_AVAILABLE`/endpoint, зажимает отрицательный таймаут в 0 и проглатывает
ошибки движка, чтобы не ронять цикл. Покрыт тремя регрессионными тестами.

### 2026-09-22 — безопасное перечисление видеоустройств PJSIP

`MediaManager` больше не роняет процесс нативным segfault при выходе за
пределы списка устройств: `getDevCount()` снимается один раз и ограничивается
`MAX_VIDEO_DEVICES = 32`, а каждый `getDevInfo(i)` вызывается в отдельном

### 2026-09-27 — Безопасная обвязка RTP-моста SIP↔mediasoup
