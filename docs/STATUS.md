## Что НЕ реализовано / ограничено

* 🟡 **H.323-приём — через отдельный C++-хост `mcu_h323d`** (Вариант B, ADR-0002): хост на H323Plus собирается (`tools/h323d`, CMake), слушает 1720, Python подключается по unix-сокету (`mcuclient/h323_host.py`, `run.py --h323 --h323-socket PATH`). Проверено живьём стендами на нескольких процессах `mcu_h323d`: сигнализация Q.931/H.225/H.245, медиа G.711 в обе стороны и **микширование двух H.323-участников через MCU** (микс, отсутствие эха, мьют, снятие фантомов). Звонок с реального аппаратного терминала Sony/Polycom пока не прогонялся. `h323_gateway.py` (Asterisk `chan_ooh323`) — устаревший обходной путь. См. `docs/ADR-0002-h323plus-unified-media.md` и `docs/H323_STATUS.md`.
* 🟡 Реальное микширование медиа: аудио-микширование H.323-вызовов работает и
  проверено стендом трёх хостов (Этап 3, `docs/H323_STATUS.md`); для SIP/веба
  то же ядро `AudioMixer` поднимает аудио-мост web-панели. Нет AEC
  (эхокомпенсации) и видеомикшера/видеостены — Этапы 3–4 по ADR-0002; для
  SIP/веба это по-прежнему скорее клиент/простой SFU, а не полноценный MCU.
* 🟡 NAT traversal: для WebRTC (браузер) — STUN/TURN настраиваются
  (`features.web.ice_servers`); для SIP/H.323-вызовов — по прямому IP.
* 🚧 Шифрование SRTP/TLS — опционально и по умолчанию выключено.
  Для закрытого контура это осознанное решение (см. ADR-0002 §3.3):
  H.235/SIP TLS/SRTP не используются.
* 🟡 Адаптивный битрейт по RTCP: авто-опрос метрик включён (`features.rtcp_poll_interval`), требуется проверка на реальном канале с потерями.
* ❌ Текстовый чат и передача файлов.
* ❌ Захват экрана на Wayland через PipeWire/порталы.

  (нет цифровой подписи).

* Конфигурация и API могут меняться без предупреждения.

## Журнал исправлений

### 2026-10-10 (h323) — H.323-вызов замолчал, но его последний голос остался в миксе всех

Девятый срез той же линии («замолчавший канал обязан уйти из микса»), теперь со
стороны H.323. `H323AudioBridge` наполняет микшер push-ом (`set_buffer` на
каждый `pcm.in`) и убирает буфер только по ЯВНОМУ событию: мьют,
`call.disconnected`, `connection.closed`. У замолчавшего, но живого вызова
такого события в природе не бывает — UDP-поток просто молчит, хост
`mcu_h323d` ничего не сообщает, убирать канал некому.

Замерено пробой живьём ДО правки: подсветка `call-1` уже погашена
(`is_speaking=False`, `volume_level=0`), а микс для собеседника по-прежнему
RMS 5656 — последний услышанный голос суммировался в микс ВСЕХ до конца вызова.
Молчаливость ровно та же, что у веб-микшера (`f8d8a59`): уровни гасятся по
штампу кадра, а микс считается по буферам микшера, то есть от РАЗНЫХ
предпосылок.

Правка в двух частях. `_publish_levels()` теперь убирает залипший канал из
МИКШЕРА (`remove` + `forget`), а не только тушит подсветку. И время в мосту —
ОДИН снимок на кадр: `_mix_and_send()` берёт `time.monotonic()` раз и передаёт
его и в `_mark()`, и в `_publish_levels(now=...)` — два независимых вызова
часов на один кадр дают два разных ответа на вопрос «жив ли канал», и
отмеченный живым канал тут же гасился бы как устаревший.
`LevelsIndicator.is_stale()` вынесен публично именно затем, чтобы затухание
можно было применить к микшеру, а не только к панели.

Зачистка трогает ТОЛЬКО свои каналы (значения `_pids`). Мост умеет работать на
внедрённом общем микшере (`mixer=`), где живут участники SIP-слоя и веба:
всеобщая зачистка по штампу оглушила бы их, а своего штампа у них у моста нет —
`is_stale()` для них ответил бы «да».

Тесты: `tests/test_h323_audio_bridge.py` 31 → 35. RED подтверждён откатом кода
(`h323_audio_bridge.py` подменён на HEAD): падают ровно 3 кейса — уход
замолчавшего канала из микса, возврат возобновлённого канала, неприкосновенность
чужих каналов общего микшера. Четвёртый кейс («живой поток с джиттером не гаснет
между тиками») зелёный и до правки: он инвариант, глушить по «тика без нового
кадра» нельзя — публикация и расчёт идут одним шагом (20 мс) и законно
разъезжаются по фазе. Порог в тестах подменяется на 0.0, а не -1.0: иначе
стареет и канал, получивший кадр в ЭТОМ же тике, и проверялось бы отсутствие
отправки, а не залипание.

Проверки: замер на дереве с правками только этого среза (файлы кодекового стража
сняты с HEAD) — **1186 passed, 0 failed, 0 skipped**; итоговый набор после обоих
срезов дня — 1188. `tests/test_doc_values.py` -> 17 passed,
`scripts/check_annotations.py` -> OK (8 модулей), ruff (--select E,F,W) по
затронутым файлам чист; в дефолтном наборе +2 `UP045` (`Optional[...]`) —
предсуществующий класс, CI его не проверяет. Мера кейсов моста обновлена в
`docs/H323_STATUS.md` (31 → 35) и в базе знаний; таблицу Этапа 3 пришлось
править руками: страж чисел знает только ссылки вида `` `tests/файл.py` (N) ``,
а там путь исходника — слепая зона.

### 2026-10-10 (h323) — замолчавший без закрытия канал залипал в аудио-миксе навсегда

Восьмой срез той же линии («публикатор обязан убираться из микса»), но с другой
стороны: прежние закрывали ЯВНОЕ событие — штатный выход по имени (`Conference
.leave`), закрытие вкладки (`_forget_bus_channel`), конец вызова. Здесь события
нет вовсе: обрыв RTP, смерть процесса терминала, вкладка, закрытая без
`close_session`. У мёртвого источника события «поток иссяк» в природе не бывает,
поэтому убирать канал по событию некому — `MediaBus` держит последний кадр до
самого `drop()`.

Замерено пробой живьём ДО правки: канал `dead` на шине, кадры больше не
публикуются — спустя 1.5 с `mixed_for()` отдавал амплитуду 3000, канал по
-прежнему в миксе. Молчаливость объясняется механикой подсветки: `tick()`
вычислял карту `fresh` (выросла ли версия кадра) и честно тушил по ней
`LevelsIndicator`, но `set_buffer()` клал для ВСЕХ публикаторов шины. Панель
показывала «не говорит», слышимый голос оставался — подсветка и микс считались
от РАЗНЫХ предпосылок.

Правка: затухание живёт в микшере, на тех же часах, что и подсветка.
`AudioMixSession.tick(now=None)` берёт `time.monotonic()` ОДИН раз на тик и
передаёт его и `mark()`, и `LevelsIndicator.update(now=...)` — двух
независимых счётчиков времени у микшера нет намеренно. Новый
`LevelsIndicator.is_stale()` публичный именно затем: затухнувший канал убирается
из микшера (`remove` + `forget`), а возобновившийся — возвращается с своей
громкостью (без кейса `test_channel_revives_when_its_stream_resumes` правка «в
одну сторону» тихо ломала вызовы с кратковременной потерей звука). Порог — НЕ
ноль: публикация и тик идут одним шагом (20 мс) и законно разъезжаются по фазе,
глушить по «в этом тике кадра не было» значило бы ронять живой поток через тик
(инвариант `test_living_stream_does_not_blink_between_ticks`). Время —
параметр, а не `sleep`: детерминированное `tick(now=0.5)`.

Тесты: `tests/test_audio_mix_session.py` 16 → 18. RED подтверждён откатом кода:
подмена `webrtc_sfu.py` на HEAD роняет ровно эти два кейса (остальные 16 —
зелёные); подмена одного `audio_mixer.py` не роняет ничего — `AudioMixSession`
живёт в `webrtc_sfu.py`, а `audio_mixer.py` даёт только `is_stale`.

Проверки: мини-раннер `tests/_runner.py` -> **1182 passed, 0 failed, 0
skipped**; pytest-коллекция — 1182 кейса в 102 файле, две меры совпадают;
страж доков `tests/test_doc_values.py` -> 17 passed; `check_annotations.py` ->
OK; ruff (--select E,F,W) новых замечаний не внёс (в дефолтном наборе — +2
`UP045` (`Optional[...]`), предсуществующий класс, CI его не проверяет).
Диагноз «мёртвый канал» теперь различим и вживую: `publishers()` показывает
залипшие id, а затухание по `LEVEL_STALE_MS` убирает их само.

### 2026-10-10 (h323) — RTP из mediasoup возвращал браузерам их собственные голоса

Третий обход той же линии («публикация в шину обязана иметь парный конец»:
`7bd25e9` — SIP-канал, `32f8fb8` — WebRTC-сессия, `4356b4b` — пространство id).
Обход даёт список мест публикации против списка `drop`: `publish_audio` в пакете
их три (`sip_web_bridge`, `webrtc_ingest`, `web_server._on_sfu_audio`), а уборки
— два. Третье место и было дефектом, причём не только в уборке.

**Корень — направление колбэка, а не формат кадра.** Docstring самого моста
(`mediasoup_rtp_bridge.py:8-13`) описывает два хода: «SIP -> браузеры» идёт
нашим `produce_plain` (`push_sip_pcm_to_sfu`), а «Браузеры -> SIP» — приёмом
`on_pcm` с PlainTransport. `_on_sfu_audio` — это ровно приём, т.е. голоса
**браузеров**, и обязан он уходить терминалу. Прежняя редакция выкладывала его в
`MediaBus` под id `"sip"` — обратно в микс веба.

Замерено пробой живьём ДО правки (`WebSession` + `conference.join('Алиса')`,
кадр амплитуды 1000 в `_on_sfu_audio`):

* микс Алисы — амплитуда **1000** при нулевой речи в вебе: браузеры слушали
  собственные голоса, и это замкнутый контур
  `шина -> on_mix -> терминал -> push_sip_pcm_to_sfu -> SFU -> этот же колбэк`;
* `web_mix_for_sip('sip-0')` — **1000 вместо 0**: id `"sip"` есть
  `SipWebAudioBridge.SIP_PUBLISHER_ID`, чужой канал `mix_excluding` вычесть не
  мог, т.е. терминалу возвращался звук из SFU (тем самым эхом, против которого
  написан `7bd25e9`);
* после `close()` панели `publishers() == ['sip']`, `latest_audio('sip')` — ЕСТЬ.
  Убирающих место не было **ни одного** (не только в `close()`): публикация без
  парного `drop` в чистом виде.

Именно этот канал маскировался «работает»: в миксе он слышен, поэтому тесты на
«звук дошёл» его пропускали. Исправление — направление: кадр уходит в
`sip_bridge.push_web_mix(...)` (в `sip_sink`), канал в шине не заводится вовсе,
а некому слушать — кадр выбрасывается. Частоту/каналы вынесены в
`WebSession.SFU_AUDIO_RATE/CHANNELS` и заперты сверкой с `PLAIN_RTP_PARAMETERS`
моста: приёмник, разобравший 8 кГц как 16 кГц, отдаёт целые байты и голос
терминала на полтонны ниже — по «звук дошёл» это невидимо.

Тесты: `tests/test_mediasoup_rtp_wiring.py` 4 -> 11 — кадр доезжает до терминала
(`(320, 8000, 1)`), не попадает в микс браузера, не попадает в микс терминала,
без приёмника не оставляет канала, отказ приёмника не роняет приём RTP,
параметры PCM равны заявленным мостом. Обязательная обратная половина
`test_native_sip_call_is_still_heard_by_browsers` — без неё «фикс» мог выродиться
в заглушку (терминал перестал бы быть слышен браузерам).

Не проверено на живом сайдкаре: `npm ci` в `mediasoup-sidecar` в этом окружении
не проходит (нет `node_modules`), вывод получен на фейковом control-клиенте и
реальном UDP (`tests/test_mediasoup_rtp_bridge.py`).

Проверки: мини-раннер `tests/_runner.py` -> **1180 passed, 0 failed, 0
skipped** (до среза 1173; замер снят изолированным деревом — `faa16e2` + только
`web_server.py` и его тест, потому что в рабочем дереве в этот момент лежал
чужой незакоммиченный срез по `audio_mixer.py`/`webrtc_sfu.py`);
pytest-коллекция — 1180 кейсов в 102 файлах, две меры совпадают; RED подменой
`web_server.py` на HEAD-версию: падают ровно 6 кейсов этого среза;
`ruff (--select E,F,W)` по `web_server.py` — те же 3 замечания, что и в HEAD
(`F401 ssl`, `F401 WEBRTC_AVAILABLE`, `E402`), новых срез не внёс; ruff F821 по
пакету -> 0; mypy ровно CI-командой -> Success; `check_annotations.py` -> OK.

### 2026-10-10 (h323) — закрытый браузер оставался в аудио-миксе навсегда

Седьмой срез той же линии («публикатор обязан убираться из шины»). Найден не по
симптому, а обходом после правки SIP-половины: `grep` по `publish_audio` /
`publish_video` против `\.drop(` показал, что из WebRTC-половины шину не убирает
никто. `Conference.leave()` зовёт `drop` только при штатном выходе по имени, а
`WebRTCManager._close_session` гасил реле́й и `RTCPeerConnection`, канал не трогал.

Замерено пробой боевым путём (менеджер с шиной → offer → трек с кадром →
`close_session` → `AudioMixSession.tick()`) ДО правки:

* после закрытия `publishers()` = `['web-1']` при нуле живых сессий,
  `latest_audio('web-1')` — ЕСТЬ;
* амплитуда микса для другого получателя: 3000 до закрытия и 3000 после — т.е.
  закрывший вкладку суммируется в каждый следующий микс бессрочно.

Молчаливость объясняется механикой микшера, а не удачей: `MediaBus` держит

### 2026-10-10 (h323) — аудио-мост SIP↔веб: канал на каждый вызов

Шестой срез серии, но начат не с находки, а с висячего незакоммиченного WIP:
per-slot каналы аудио-моста (`sip-<слот>`) были написаны в
`sip_bridge_service.py`, `sip_web_bridge.py`, `web_server.py` и не имели **ни
одного** теста — grep по `tests/` не нашёл ни `channel_of`, ни `publisher`, ни
`forget`. Такую правку нельзя было ни закоммитить, ни защитить от регресса.

Что именно чинит этот код (дефект был боевым, не косметическим): все SIP-вызовы
публиковали PCM в шину под одним служебным id `sip`. На двух терминалах их кадры
затирали друг друга (в шине оставался последний принятый), а
`mix_excluding("sip")` вычитал разом оба — вызовы слышали браузеров, но не друг
друга, то есть в вызов уходила тишина. Плюс канал никогда не вычищался: а
`MediaBus` держит последний кадр до `drop`, и микшер берёт состав публикаторов
из шины — браузеры слушали застывший голос завершённого терминала (фантом).

Покрытие заведено на трёх уровнях связки «порт -> мост -> сессия -> шина»:

* `tests/test_sip_bridge_service.py` 48 -> 53: канал доезжает до приёмника
  (`sip-0`/`sip-1`, а не общий `sip`), веб-микс для слота вычитается по СВОЕМУ
  каналу, `stop()` убирает каналы всех слотов, освобождённый при уменьшении
  числа вызовов слот тоже убирается, а сессия, которая канал НЕ принимает,
  обязана получать звук как раньше;
* `tests/test_sip_web_bridge.py` 8 -> 15: `channel_of` отличается от общего id,
  два вызова сосуществуют в шине, названный канал не трогает общий, `forget`
  убирает канал и молча переживает шину без `drop` и упавшую шину;
* `tests/test_bridge_wiring.py` 4 -> 8: боевая точка входа `WebSession` —
  `on_sip_audio` сохраняет канал, `web_mix_for_sip` вычитает только свой канал
  (терминал не слышит себя, но слышит другой вызов), без канала вычитается
  общий `sip`, `forget_sip_channel` убирает канал из шины.

RED подтверждён откатом ТОЛЬКО кода (`git stash push --` трёх модулей, тесты на
месте): падают ровно 14 новых кейсов, на WIP-коде все проходят. То есть
покрытие настоящее, а не зелёный декор.

Два дефекта нашего же стенда вскрылись по ходу, и оба маскировались зелёным:

* порты поднимает не `start()`, а `ensure_ports()` (в бою — поллер или событие);
  стенд ждал порты после `start()` и получал `[]` — 5 падений оказались ошибкой
  теста, а не продукта;
* `mix_excluding()` читает буферы микшера, а они наполняются только `tick()`.
  Без тика микшер отвечает тишиной на ЛЮБОЙ запрос, и проверки «эхо / вычтен не
  свой канал» прошли бы независимо от правильности вычитания. Тик добавлен, и
  кейсы сделаны различающими: одна публикация, разный запрошенный канал.

Тот же урок, что в предыдущем срезе, только с другой стороны: shim
`_with_channel` решает сигнатуру колбэка инспектом (`_accepts_extra_arg`) и
кэширует её, потому что «передать канал наугад» означает `TypeError`, который
проглотит `except` рядом и звук потеряется МОЛЧА. Обратная совместность со
старыми сессиями и моками — не вежливость, а требование: проверена отдельным
кейсом, а не на веру.

Не проверено на живом терминале: вывод подтверждён тестами на фейках, ушами на
реальном SIP-звоннике — нет.

Проверки: мини-раннер `tests/_runner.py` -> **1160 passed, 0 failed, 0
skipped** (до среза 1144); pytest-коллекция — 1160 кейсов в 101 файле, две меры
совпадают; страж доков `tests/test_doc_values.py` -> 17 passed.

### 2026-10-10 (h323) — мёртвый хост `mcu_h323d` оставлял вызовы «живыми»

1. **Обрыв не был событием.** `H323dClient._read_loop` при разрыве снимал

   процесса не приходит никогда. Добавлен `forget_all()`: освоболяет ровно те

  обеих сторон (`_transmit`), а слот считается подключённым только когда
  подняты ОБА направления — иначе остаётся на ретрай.
- **Порт жил на 16 кГц при веб-миксе 48 кГц**: pjsua2 обрезает кадр под размер
  порта, то есть 20 мс из 48 кГц превращались в обрезанный звук. Частота порта
  теперь берётся из микшера сессии.
- **Порты не отвязывались от вызова** перед уничтожением (в медиаграфе pjsua2
  оставался маршрут на мёртвый объект) — добавлен `stopTransmit` при закрытии
  порта, при переезде слота на другой вызов и при остановке.
- `EventBus` не умел отписываться: подписка моста переживала остановку и
  удваивалась при рестарте панели. Добавлен `EventBus.unsubscribe`.
- Веб-микс для терминала собирается без голоса самого SIP
  (`AudioMixSession.mix_excluding` + `WebSession.web_mix_for_sip`), иначе
  терминал слышит собственный голос.
- Порядок вызовов для портов фиксирован по id участника
  (`SipEngine.active_audio_calls`): без этого порты «переезжали» между вызовами.

Тесты: 48 регрессий `tests/test_sip_bridge_service.py` (частота, обе половины
канала, переезд слота, эхо, подписка/отписка, жизненный цикл в `WebServer`).

### 2026-09-22 — прокачка событий PJSIP в headless

`run.py` в headless-режиме (`--headless` / серверный цикл) теперь вызывает
`engine.process_events()` вместо голого `time.sleep()`. Без `libHandleEvents()`
входящие INVITE копились в буфере сокета (Recv-Q рос), авто-ответ не
срабатывал, и дозвониться до клиента было невозможно — процесс при этом был жив.
Новый метод `SipEngine.process_events(timeout)` защищён guard'ом по
`PJSIP_AVAILABLE`/endpoint, зажимает отрицательный таймаут в 0 и проглатывает
ошибки движка, чтобы не ронять цикл. Покрыт тремя регрессионными тестами.

### 2026-09-22 — безопасное перечисление видеоустройств PJSIP

пределы списка устройств: `getDevCount()` снимается один раз и ограничивается
