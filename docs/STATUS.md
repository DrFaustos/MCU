## Что НЕ реализовано / ограничено

* 🟡 **H.323-приём — через отдельный C++-хост `mcu_h323d`** (Вариант B, ADR-0002): хост на H323Plus собирается (`tools/h323d`, CMake), слушает 1720, Python подключается по unix-сокету (`mcuclient/h323_host.py`, `run.py --h323 --h323-socket PATH`). Проверено живьём стендами на нескольких процессах `mcu_h323d`: сигнализация Q.931/H.225/H.245, медиа G.711 в обе стороны и **микширование двух H.323-участников через MCU** (микс, отсутствие эха, мьют, снятие фантомов). Звонок с реального аппаратного терминала Sony/Polycom пока не прогонялся. `h323_gateway.py` (Asterisk `chan_ooh323`) — устаревший обходной путь. См. `docs/ADR-0002-h323plus-unified-media.md` и `docs/H323_STATUS.md`.
* 🟡 Реальное микширование медиа: аудио-микширование H.323-вызовов работает и
  проверено стендом трёх хостов (Этап 3, `docs/H323_STATUS.md`); для SIP/веба
  то же ядро `AudioMixer` поднимает аудио-мост web-панели. Нет AEC
  (эхокомпенсации) и видеомикшера/видеостены — Этапы 3–4 по ADR-0002; для
  SIP/веба это по-прежнему скорее клиент/простой SFU, а не полноценный MCU.
* 🟡 NAT traversal: для WebRTC (браузер) — STUN/TURN настраиваются
  (`features.web.ice_servers`); для SIP/H.323-вызовов — по прямому IP.
* 🚧 Шифрование SRTP/TLS — опционально и по умолчанию выключено.
  Для закрытого контура это осознанное решение (см. ADR-0002 §3.3):
  H.235/SIP TLS/SRTP не используются.
* 🟡 Адаптивный битрейт по RTCP: авто-опрос метрик включён (`features.rtcp_poll_interval`), требуется проверка на реальном канале с потерями.
* ❌ Текстовый чат и передача файлов.
* ❌ Захват экрана на Wayland через PipeWire/порталы.

## Журнал исправлений

### 2026-10-10 (h323) — мёртвый хост `mcu_h323d` оставлял вызовы «живыми»

`mcu_h323d` можно убить (`kill`, OOM, упавшая сборка) посреди разговора. До правки
в комнате навсегда оставался участник в `CONFIRMED`: web-панель показывала
действующее соединение, `hangup` из панели уходил в закрытый сокет, а буфер
микшера продолжал попадать в микс остальных («фантом», который никто не вешал).

Воспроизведение: unix-сокет-заглушка, шлющая `ready` + `call.incoming` +
`call.connected`, ЗАКРЫВАЕТ соединение — это и есть падающий хост. До правки:
`client.connected` становится `False`, а `Room.participants` остаётся 1 —
вердикт зонда «ФАНТОМЫ». После: участников 0, вердикт «чисто».

Корень — один, в трёх местах по цепочке:

1. **Обрыв не был событием.** `H323dClient._read_loop` при разрыве снимал
   `_running` и писал в лог, подписчикам не доставлялся НИКТО. Обрыв для
   подписчика неотличим от простоя, поэтому `H323Endpoint` держал вызовы
   мёртвого хоста как живые. Теперь разрыв без нашего `close()` — событие
   `connection.closed` (с `reason`), а намеренная остановка им не считается:
   `close()` снимает `_running` ДО закрытия сокета, ложной тревоги нет.
2. **`shutdown` хоста тоже ничего не зачищал.** `on_event` лишь писал
   «хост остановлен». Обрыв обрабатывает `H323Endpoint._on_host_lost()`:
   снимает всех участников с `notify_host=False` — `call.hangup` мёртвому
   сокету не отменяет вызов, но пачкает лог «не доставлен».
3. **Аудио-мост чистился только по `call.disconnected`**, который при смерти
   процесса не приходит никогда. Добавлен `forget_all()`: освоболяет ровно те
   id в микшере, которые завёл сам мост, и НЕ отписывает себя от событий —
   владельцем соединения остаётся эндпоинт, иначе мост терял медиа до
   перезапуска хоста без единой ошибки.

Проверки: боевой pytest по всем h323-модулям -> RC=0; мини-раннер
`tests/_runner.py` по тем же файлам -> **117 passed, 0 failed, 0 skipped, RC=0**;
`tests/test_doc_values.py` (сверяет числа тестов в `docs/H323_STATUS.md`,
стало 40/22/21) -> RC=0; блокирующий mypy-набор CI -> «Success: no issues found
in 7 source files»; `scripts/check_annotations.py` -> OK (8 модулей); ruff
(--select E,F,W) по изменённым файлам -> «All checks passed!» (по всему репу
30 предсуществующих замечаний в файлах, которых срез не касается). Новых кейсов 7: `connection.closed`
у клиента и его отсутствие при штатном `close()` (2), зачистка фантомов,
смерть хоста в простое, «не слать hangup мёртвому» (3), освобождение всех
буферов микшера и «мост не отписался сам» (2). Предсуществующие 3 mypy-ошибки
в `audio_mixer.py`/`webrtc_sfu.py` (ndarray) правкой не затронуты.

### 2026-10-09 (h323) — CI покраснел там, где локальный прогон был зелёный

Пуш срезa уронил `lint-and-test` на всех трёх Python. Локально в этот момент
было **1070 passed, 0 failed** — значит, дело в окружении прогона, а не в коде,
и его надо было воспроизвести, а не «перезапустить». Для этого подняли чистый
venv в точности как шаг CI (`pip install pytest`, без pjsua2/numpy/mss).
Воспроизвели и разобрали две независимые поломки; обе предсуществующие — до
этого их прятали другие падения того же прогона (2026-10-08 CI падал с
«1020 vs 1022»).

1. **Мини-раннер путал коллекцию с планом исполнения.** В `--collect-only`
   ветка `skipif` стояла ДО печати `COLLECT`, и активный skipif-кейс выпадал из
   коллекции: в CI (pjsua2 нет) — ровно 2 кейса `test_sip_interop.py`, отсюда
   «мини-раннер 1067, pytest 1069». Краснели сразу три зависимые меры:
   `test_runner_covers_every_case_pytest_collects`,
   `test_the_two_official_checkpoints_count_the_same_cases` и «контроль
   чистоты» self-test'а. Локально дефект невидим: pjsua2 установлен, условие
   `skipif` ложно, расхождения нет. Исправлено: `--collect-only` считает и
   skipif-кейсы (как pytest), а на исполнении они по-прежнему пропускаются —
   регрессия `test_runner_collect_only_counts_skipif_cases` закрепляет обе
   половины.
2. **Два NAT-теста проверяли не маппинг, а наличие биндинга.**
   `_configure_nat` прошивает STUN через `make_string_vector(_pj, …)`, а без
   pjsua2 `_pj is None`, типа `StringVector` нет, и код по контракту ОБЯЗАН STUN
   не применять (иначе `TypeError` отменил бы всю настройку NAT). Тест же требовал
   прошитое значение и был зелёным только на машине с pjsua2. Биндинг теперь
   подписывается явно (`monkeypatch.setattr(se, "_pj", _FakePj)`), как это уже
   делали соседние тесты того же файла.

Тесты, которым действительно нужен нативный модуль, к падению отношения не
имели: они защищены `if pj is None: return`. Краснели те, у кого такой защиты
не было, — за неё работала «зелёная машина разработчика» с установленным
pjsua2.

RC=0**; `/usr/bin/python3 -m pytest tests/ -q` -> RC=0; pytest в чистом venv

### 2026-10-09 (h323) — «строгий» модуль, до которого строгость не доезжала

Три независимых разрыва в типизации, каждый воспроизведён живьём (mypy 2.4.0
в изолированном venv: боевой python mypy поставить не даёт PEP 668):

1. **В репе ДВА конфига mypy, и README слал оператора в мёртвый.** При наличии
   `mypy.ini` mypy секцию `[tool.mypy]` из `pyproject.toml` не читает —
   подтверждено `mypy --verbose` (`Config File: .../mypy.ini`). README отсылал
   читать `[[tool.mypy.overrides]]`: человек изучал настройки, которые никто не
   применяет. Правка пошла в README (указатель на `mypy.ini`), регрессия —
   `test_docs_do_not_send_the_operator_to_a_dead_mypy_config`.
2. **`qt_platform.py` стоял в strict-шаге CI с e6729c6 (2026-09-19), но
   строгость к нему не применялась**: per-module секции в `mypy.ini` не было, а
   без неё `disallow_untyped_defs` не включается — новая нетипизированная
   функция прошла бы «блокирующий» шаг молча. Секция добавлена; модуль
   проходит строгость как есть, заново типизировать не пришлось.
3. **`adaptive_bitrate.py` был объявлен строгим в `mypy.ini` (b4adba8), но
   strict-шаг `ci.yml` его не перечислял** — то есть блокирующей mypy-проверки
   у него не было вообще. Добавлен в шаг.

Наборы строгой типизации (`mypy.ini` — 7 секций, strict-шаг `ci.yml` — 7
модулей, `STRICT_MODULES` — 8) сведены проверкой
`test_strict_typing_sets_do_not_drift_apart`: модуль, который CI перечисляет,
но `mypy.ini` для него строгость не включает, краснеет; обратный случай
(объявлен строгим, но не проверяется) — тоже. Расширить `STRICT_MODULES`
можно только через явный `STRICT_SET_AHEAD`.

Почему `h323_audio_bridge` сидит в `STRICT_SET_AHEAD`: mypy проверяет
транзитивные импорты, а мост тянет `webrtc_sfu`, где `AudioMixer` объявлял id
участника как `int`, тогда как веб-слой (`MediaBus`,
`mix_excluding(publisher: str)`) живёт на строках. Замер на копии HEAD (тот же
venv): 8 ошибок, из них 5 — `str` против `int` в
`set_buffer`/`remove`/`mix_for`/`participant_ids`. Введён
`ParticipantId = Union[int, str]` (микшер id только хранит и сравнивает),
вызывающий код в `webrtc_sfu.py` приведён к тому же типу. Остались 3 ошибки,
не этого среза: присваивание `ndarray` другого dtype в `resample_mono` (2) и
Unused "type: ignore" при `warn_unused_ignores`.

Self-test стража доехал до конфигураций: кроме 7 подсовов в документы — 4
подсова в `mypy.ini`, strict-шаг `ci.yml` и `STRICT_MODULES` (с assert на
уникальность якоря: ненайденный якорь дал бы зелёный прогон и ложное
«ПОЙМАНО») и подсов мёртвой mypy-ссылки в README.

- **`media.transmitFrom()` в pjsua2 не существует** — `_attach_call` звал только
  его, поэтому направление «вызов -> порт» не подключалось никогда: браузеры
  молча не слышали терминал. Теперь канал поднимается через `startTransmit` с
  обеих сторон (`_transmit`), а слот считается подключённым только когда
  подняты ОБА направления — иначе остаётся на ретрай.
- **Порт жил на 16 кГц при веб-миксе 48 кГц**: pjsua2 обрезает кадр под размер
  порта, то есть 20 мс из 48 кГц превращались в обрезанный звук. Частота порта
  теперь берётся из микшера сессии.
- **Порты не отвязывались от вызова** перед уничтожением (в медиаграфе pjsua2
  оставался маршрут на мёртвый объект) — добавлен `stopTransmit` при закрытии
  порта, при переезде слота на другой вызов и при остановке.
- `EventBus` не умел отписываться: подписка моста переживала остановку и
  удваивалась при рестарте панели. Добавлен `EventBus.unsubscribe`.
- Веб-микс для терминала собирается без голоса самого SIP
  (`AudioMixSession.mix_excluding` + `WebSession.web_mix_for_sip`), иначе
  терминал слышит собственный голос.
- Порядок вызовов для портов фиксирован по id участника

### 2026-09-22 — прокачка событий PJSIP в headless

`run.py` в headless-режиме (`--headless` / серверный цикл) теперь вызывает
`engine.process_events()` вместо голого `time.sleep()`. Без `libHandleEvents()`
входящие INVITE копились в буфере сокета (Recv-Q рос), авто-ответ не
срабатывал, и дозвониться до клиента было невозможно — процесс при этом был жив.
Новый метод `SipEngine.process_events(timeout)` защищён guard'ом по
`PJSIP_AVAILABLE`/endpoint, зажимает отрицательный таймаут в 0 и проглатывает
ошибки движка, чтобы не ронять цикл. Покрыт тремя регрессионными тестами.

### 2026-09-22 — безопасное перечисление видеоустройств PJSIP
