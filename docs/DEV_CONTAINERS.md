# Локальный контейнерный стенд MCU (2 клиента)

Быстрый способ проверить реальный SIP-звонок между двумя клиентами MCU
**локально**, не дожидаясь сборки AppImage/`.exe` в GitHub Actions.

Стенд поднимает два контейнера в одной bridge-сети:

| Контейнер | IP         | Роль                        |
|-----------|------------|-----------------------------|
| `mcu-a`   | 10.0.3.10  | клиент A (звонит)           |
| `mcu-b`   | 10.0.3.20  | клиент B (принимает)        |

Внутри сети нет NAT — SIP/RTP идут напрямую, ICE/STUN не нужны.

## 2. Запуск стенда

 

Скрипт сам определяет:

* **GUI**: если задан `DISPLAY` и есть `/tmp/.X11-unix`, окна обоих клиентов
  выводятся на экран разработчика (через XWayland, `QT_QPA_PLATFORM=xcb`).
  Иначе контейнеры стартуют в `--headless`.
* **Звук**: если есть PulseAudio-сокет `/run/user/<uid>/pulse/native`, он
  пробрасывается; иначе клиенты стартуют с `--null-audio` (тестируется
  сигналинг и видео без реального звука).

Переменные для управления:

| Переменная   | Значение | Смысл                                  |
|--------------|----------|----------------------------------------|
| `MCU_X11`    | `auto`/`x11`/`headless` | Режим вывода GUI          |
| `MCU_SUBNET` | CIDR     | Подсеть (по умолчанию `10.0.3.0/24`)   |
| `MCU_A_IP` / `MCU_B_IP` | IP | Адреса контейнеров                |
| `MCU_SIP_PORT` | порт   | SIP-порт (по умолчанию `5060`)         |
| `MCU_IMAGE`  | имя      | Рабочий образ (по умолчанию `mcu-dev`) |

## 6. Ограничения и fallback

* **Вложенные контейнеры недоступны** в некоторых средах (нет capabilities,
  `unshare --net` запрещён). Тогда используйте процессный стенд:
   
* **Screen share** в контейнере без X-сессии не тестируется — нужен
  `v4l2loopback` плюс реальная X-сессия.
* Если окна не появляются: проверьте `echo $DISPLAY` на хосте и наличие
  `/tmp/.X11-unix`. На чистом Wayland без XWayland GUI не вывести — используйте
  headless-режим и `scripts/dev/test_call.sh`.
* Перед первым запуском проверьте окружение: `python3 run.py --doctor`.

## 7. H.323-стенд в контейнере на Bazzite/podman

Хостовые грабли Bazzite/Silverblue: нет `apt`, пакеты в систему не ставятся,
а PTLib/H323Plus (Этап 0 из `docs/ADR-0002-h323plus-unified-media.md`) требует
именно их. Решение — образ `docker/mcu-dev-h323.Dockerfile` (Ubuntu 24.04,
`podman` или `docker`) и единая точка входа `scripts/h323_in_container.sh`:

```bash
./scripts/h323_in_container.sh build     # собрать образ (один раз, ~15 мин)
./scripts/h323_in_container.sh smoke     # собрать mcu_h323d + ready/pong-дымь
./scripts/h323_in_container.sh testbed   # стенд двух хостов (сигнализация,
                                         # медиа, DTMF) — обязан дать RC=0
./scripts/h323_in_container.sh video-live # живой видеостенд Этапа 4 (паттерн →
                                         # H.261 → RTP → PNG); PNG в --dump-dir
                                         # сохраняются только внутри /work
./scripts/h323_in_container.sh video-panel # терминал + операторская панель
                                         # (аргументы — через MCU_H323_EXTRA_ARGS)
./scripts/h323_in_container.sh tests     # python3 tests/_runner.py (в образе
                                         # есть pytest и ruff)
./scripts/h323_in_container.sh bash      # интерактив, репо смонтирован в /work
./scripts/h323_in_container.sh <cmd...>  # любая команда в контейнере
```

Репо монтируется в `/work` читаемо-записываемо: артефакты (`tools/h323d/build`)
переживают прогоны и видны с хоста своими правами (podman rootless пишет
наружу от вашего uid). Переменные: `MCU_H323_IMAGE` (имя образа),
`MCU_H323_ENGINE` (`podman`/`docker`), `PORT_A`/`PORT_B`/`KEEP_LOGS` —
пробрасываются в стенд, `MCU_H323_RUN_ARGS` — дополнительные аргументы
`run` (например `--cap-add NET_ADMIN` для tc/netem-экспериментов),
`MCU_H323_BUILD_ARGS` — аргументы `build`, `MCU_H323_H323D_VOL` — имя тома
сборки хоста.

Надстройка поверх закреплённой пары версий — теми же build-аргументами
основного Dockerfile (дефолты не меняются). Стенд H.264 (royalty-free,
`docs/CODECS.md` §5.1, стек 1.29.1 + OpenH264):

```bash
MCU_H323_IMAGE=mcu-dev-h323:v129 \
MCU_H323_BUILD_ARGS="--build-arg PTLIB_VERSION=2.10.9.8 \
  --build-arg H323PLUS_VERSION=1.29.1 \
  --build-arg MCU_H323_VIDEO_PLUGINS=H.261-vic,H.264-openh264" \
  ./scripts/h323_in_container.sh build
```

Для образа с другим ABI стека заводите СВОЙ `MCU_H323_H323D_VOL` — иначе
инкрементальная сборка хоста смешивает объекты двух стеков.

Стек в образе собирается **тем же** `scripts/install_h323plus.sh`, что и на
голом хосте (PTLib 2.10.9.6 + H323Plus 1.28.0 в `/usr/local`, аудио-плагины,
патч кадра plugin-G.722 на 20 мс) — расхождение образа и хоста означало бы,
что стенд проверяет не то, что работает у пользователя.

Три грабли, уже учтённые в скрипте (при ручной работе всплывут снова):

* **SELinux** (Bazzite/Fedora): bind-mount без `:z` контейнером не виден.
* **podman 6 + устаревший `~/.config/containers/containers.conf`** со
  `default_rootless_network_cmd = "slirp4netns"` — сеть не поднимается вообще;
  скрипт подменяет конфиг через `CONTAINERS_CONF` (файл пользователя не трогает).
* **чужие артефакты cmake** в `tools/h323d/build`: `find_host_binary()` берёт
  первый попавшийся бинарь, и контейнер начал бы тестировать сборку с другого
  хоста; **все** режимы, включая passthrough, монтируют поверх `build/`
  именованный том (`MCU_H323_H323D_VOL`) — внутри всегда сборка текущего
  образа, наружу том не виден.
  У этого решения есть своя грабелька, на ней уже ловились: том один на все
  образы. При переключении между `:latest` и образом с другим ABI стека (например
  `:v129`) инкрементальная сборка подмешивает объекты чужого стека, и хост
  ведёт себя не как свежий код. Для второго образа заводите свой
  `MCU_H323_H323D_VOL` (или чистите том), а результаты замеров хоста всегда
  подписывайте образом, которым собирали.

Знания о версиях стека (теги форков с подчёркиваниями `v2_10_9_6`/`v1_28_0`,
тихий fallback на master, `ENV PREFIX`, ломающий сборку H323Plus) —
в `docs/H323_STATUS.md` и `docs/AI_CONTEXT.md`.

## 8. Эталонный OpenMCU-ru (интероп-фундамент ADR-0002)

Для проверки «картинка уходит в OpenMCU и возвращается» поднят живой
OpenMCU-ru **не на нашем стеке**: в дереве v3.48.0 свои копии PTLib/H323Plus,
поэтому согласование кодеков идёт независимо от `/usr/local` образа
`mcu-dev-h323` — интероп не может «самоподтвердиться». Образ:
`docker/openmcu-ru.Dockerfile` (источник willamowius/openmcu, тег **v3.48.0**,
пин `2b93508`; почему именно тег, а не master — в шапке Dockerfile: на master
отбор исходящего видео по подстроке имени, наш `H.261-CIF{sw}` туда не
проходит). Все одиннадцать граблей сборки (GCC11/make-4.3/FFmpeg 4.4, включая
смертельный `PString::Mid` UB без `-fwrapv`) разобраны в комментариях там же.

```bash
# сборка (контекст не нужен; долго — бандлины, ~15 мин)
podman build -f docker/openmcu-ru.Dockerfile \
    -t localhost/openmcu-ru:v3.48.0 "$(mktemp -d)"

# один раз: общая сеть стенда (DNS-имена вместо IP)
podman network create mcu-lab

# долгоживущий сервис (НЕ --rm): NET_RAW под tshark на плече стенда,
# 1720/tcp+udp — H.323, 1420 — веб-админка с хоста; mcu-lab ПЕРВИЧНОЙ сетью
# (вторым интерфейсом pasta под rootless не втыкается — «invalid network
# mode», живой замер), наш стенд ходит к нему: MCU_H323_NET=mcu-lab +
# --remote-h323 openmcu-ru:1720
podman run -d --name openmcu-ru --network mcu-lab --cap-add NET_RAW \
    --restart=on-failure \
    -p 1720:1720/tcp -p 1720:1720/udp -p 1420:1420 \
    -v "$PWD/docker/openmcu-ru/openmcu.ini:/opt/openmcu-ru/share/openmcu-ru/config/openmcu.ini:z" \
    localhost/openmcu-ru:v3.48.0
```

Каноническое имя стендового сервиса — единственное `openmcu-ru`. Контейнеры
вида `openmcu-dev*` — сборочно-отладочные слепки среды (архив, остановлены);
артефакты снято брать только с `openmcu-ru`, иначе «честный отчёт про чужой
процесс» гарантирован.

Эталонный `docker/openmcu-ru/openmcu.ini` — самосгенерированный на теге дамп
(первый запуск без монтированного файла, остановка SIGTERM — ini пишется при
штатном завершении) плюс дописанная секция `[Parameters]\nTrace level = 2`:
без неё `trace.txt` остаётся на уровне по умолчанию и «Codecs (in preference
order)»/`OpenLogicalChannel` в нём не появятся (флаг `-v` уровень не задаёт —
только ini; проверено живым прогоном). Правки значений в ini — только
заменой существующей строки: в PTLib 2.0.x дубль ключа в секции склеивается
со старым значением переводом строки, а не перезаписывает.

Снятие среза за прогон (после вызова со стенда):

```bash
mkdir -p tmp/openmcu
podman cp openmcu-ru:/opt/openmcu-ru/share/openmcu-ru/log/trace.txt \
    tmp/openmcu/trace_<профиль>.txt
podman logs --since <старт-прогона> openmcu-ru > tmp/openmcu/stdout_<профиль>.txt
```

`stdout` у OpenMCU-ru — не только лог: там их собственная таблица возможностей
(`[RECEIVE_SOUND]= ...`, `[RECEIVE_VIDEO]= ...`) и «Table:» (приоритеты
микшера, ровно 8 аудиоканалов — не полный набор возможностей). Но списки
`[RECEIVE_*]`/`[TRANSMIT_*]` — это ИХ КОНФИГ-желание, а не загруженное:
автогенерация дописывает ключи и для возможностей без плагина (в реальном дампе
`G.7231-6.3k[e]` и весь VP8/H.263/H.264 числятся, а .so у них нет). Правило:
**ini умеет только сужать** — нет .so, нет возможности, сколько `True` ни пиши;
авторитетный источник «что реально в образе» — `find /opt/openmcu-ru/lib/ptlib
-name '*.so'` и фактический TCS/H.245 в трейсе. Дешёвая подпись «образ живой и
набор тот» без H.245: список СОЗДАННЫХ возможностей (голые имена до строки
`VideoMixConfigurator`) — на этом образе ровно 20 (18 аудио от 7 .so-семейств +
H.261-CIF/QCIF), эталон закоммичен: `docker/openmcu-ru/created_capabilities.txt`.

В образе лежат 8 из 11:
H.261-vic, G.722/G.726/G.729/iLBC/Speex/SILK/OPUS; H.263-1998/H.264/VP8/G.7231
не собираются из-за старого FFmpeg API и осознанно пропущены — замеры на H.261.
Трейс — файл, не stdout: `/opt/openmcu-ru/share/openmcu-ru/log/trace.txt`
(путь зашит в бинарь как `SERVER_LOGS`; конфиг — `SYS_CONFIG_DIR`, тот же
`share/openmcu-ru/config`; у 4.x-веток раскладка другая — не переносить).

Комната: вызов на `имя_комнаты@адрес` (по E.164/alias), без имени — комната по
умолчанию (`[Parameters]/Default room`, на дефолтах `room101`). Статус-страницы
(проверены curl на собранном образе): `/Status` — конференции/участники
(meta-refresh 30 c), `/Select`, `/Invite`, `/Parameters`,
`/ReceiveSoundCodecs`/`/TransmitVideoCodecs` (корень `/` — оглавление).
Веб-админка правит тот же ini и требует перезапуска контейнера — таблицы
конференций строятся на старте.

Нестойкость (замер 2026-11-19, дефект их сборки): heap corruption
«realloc(): invalid next size» в `PAbstractArray::InternalSetSize` ←
`H323_RTPChannel::Transmit` на добавлении участника — смерть на 6-м входящем
вызове за день (16-е «Adding member» в одну комнату после 11 микшерных
sleep/wake; core+фрейм: tmp/openmcu/coredump_bt.txt). Рестарт —
`podman restart openmcu-ru`; сервис поднят с `--restart=on-failure` и оживает
сам, живость в замерах проверяйте по `.State.StartedAt`. Правило прогонов:
**рестартовать перед каждым прогоном** (`podman restart openmcu-ru`), а не
держать один контейнер на матрицу: подозреван счётчик добавлений (смерть на
16-м «Adding member»), а рестарт-политика посреди прогона молча съедает
артефакты. Обход посильнее: уникальная комната на вызов (чистый микшер). Это
не UB-арифметика Mid (-fwrapv в образе есть), а другой баг того же семейства
«2012-й код против современных рантаймов».
