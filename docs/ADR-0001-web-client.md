# ADR-0001: Переносить ли клиент на web-интерфейс (WebRTC) вместо нативного Qt?

**Статус:** Proposed
**Дата:** 2026-09-20
**Контекст:** обсуждение будущего проекта MCU

---

## Вопрос

Стоит ли перенести клиентскую часть на web-интерфейс и работать с устройствами
и раскладкой видео в браузере (как BBB)? Или оставить нативный клиент?

Короткий ответ: **не «вместо», а «в дополнение»**. Нативный SIP/H.323-движок
надо сохранить как серверный шлюз, а web-клиент добавить как ещё один тип
участника. Полный перенос «в браузер» сломает главную ценность проекта
(приём SIP/H.323-вызовов от аппаратных терминалов).

---

## 1. Что на самом деле делает BBB (и почему это другой класс продукта)

BBB — это **не «клиент, который рисует видео в тайлах»**. Это:

 

Ключевое: у BBB **нет SIP и H.323 вообще**. Он не принимает вызовы от
аппаратных ВКС-терминалов и не звонит им. Это замкнутая система
«браузер ↔ свой сервер ↔ браузер».

Наш проект — про **интероп с аппаратными терминалами по SIP/H.323 по IP**.
Это принципиально другое.

## 2. Может ли браузер говорить по SIP/H.323?

| Протокол | Браузер умеет напрямую? | Что нужно |
|----------|------------------------|-----------|
| SIP по UDP/TCP | ❌ нет | сервер-шлюз |
| SIP по WebSocket (RFC 7118) | 🟡 только через JS-стек (JsSIP) + SIP-сервер с WS | Asterisk/FreeSWITCH/Kamailio c `ws` |
| RTP | ❌ нет (браузер = WebRTC: SRTP/DTLS/ICE) | медиашлюз WebRTC↔RTP |
| H.323 | ❌ нет и не будет | H.323→SIP→WebRTC (двойной шлюз) |

Вывод: браузер **сам по себе не примет SIP INVITE и не позвонит на
аппаратный терминал**. Между ним и SIP/H.323 обязателен сервер.

## 3. Что реально решает перенос на web (по нашим болям)

| Боль | Решит ли web-клиент | Почему |
|------|--------------------|--------|
| Wayland: пустые тайлы | ✅ **да, полностью** | браузер рисует сам, `<video>`+CSS-grid, никакого native window handle (XID/HWND) |
| Windows-падения сборки | ✅ да | нет PyInstaller/pjsua2-wheel/DLL — это просто страница |
| Реальные имена устройств | ✅ да | `getUserMedia` → браузерный список устройств, ровно как в Zoom/Teams web |
| Проброс GUI в контейнеры | ✅ да | браузер на хосте, сервер в контейнере, X11 не нужен |
| Приём SIP-вызова от Panasonic/Cisco | ❌ **нет** | браузер не SIP-эндпоинт, нужен шлюз |
| H.323 | ❌ нет | см. выше |
| Запись/микширование N-way | ❌ нет в браузере | нужен SFU (mediasoup/Janus/FreeSWITCH) |

То есть web **элегантно закрывает UI/платформенные проблемы**, но
**не закрывает протокольную суть** проекта.

## 4. Варианты

### Вариант A. Полный перенос на web (заменить нативный клиент)
- **Плюсы:** решаются Wayland/Windows/устройства; современный UI.
- **Минусы:** теряем прямой SIP/H.323-интероп (главную функцию);
  нужен SIP↔WebRTC-шлюз + SFU + сигналинг + TURN; H.323 фактически выпадает.
- **Оценка:** это **новый продукт**, а не миграция. Месяцы работы.

### Вариант B. Нативный клиент + web-клиент как отдельный участник (рекомендуется)
 
- **Плюсы:** сохраняем SIP/H.323 и аппаратные терминалы; web-люди получают
  удобный клиент без установки; тайлы/устройства — как в BBB; запись и
  микширование остаются на сервере.
- **Минусы:** нужно поднять SFU + сигналинг (WebSocket) + TURN для интернета.
- **Оценка:** реалистичный, инкрементальный путь.

### Вариант C. SIP over WebSocket без SFU (лёгкий)
Браузер (JsSIP) ↔ Asterisk/FreeSWITCH (WS) ↔ наши терминалы.
- **Плюсы:** меньше кода, чем B; браузер = SIP-эндпоинт.
- **Минусы:** для N-way всё равно нужен серверный микс/SFU; видео-раскладка
  в браузере только для тех потоков, что даёт сервер; сложнее с H.323.
- **Когда:** если нужен только 1:1 или сервер уже микширует.

## 5. Рекомендация

**Вариант B, инкрементально:**

1. **Сейчас:** оставить нативный клиент как есть (он — единственный, кто
   говорит с аппаратными терминалами). Не тратить силы на переписывание UI.
2. **Следующий шаг:** вынести SIP/H.323-движок в **headless-сервер** (он уже
   умеет `--headless`, это почти готово).
3. **Затем:** добавить к серверу **WebRTC-грань** (mediasoup/Janus/LiveKit) —
   браузеры подключаются как участники; видео/аудио микшируются на сервере.
4. **Web-клиент:** простая страница — `getUserMedia`, `<video>`-тайлы, CSS-grid,
   кнопки мута. Устройства и раскладка — «как в BBB», но за интероп отвечает
   наш сервер.

Нативный GUI остаётся для: роли шлюза, записи, отладки, оффлайн-контура.

## 6. Что НЕ надо делать

* ❌ Переписывать всё на JS «потому что BBB так умеет» — потеряем SIP/H.323.
* ❌ Пытаться звонить с браузера на SIP без шлюза — не сработает (нет RTP/UDP).
* ❌ Тащить SFU, пока нет серверной части — некуда его ставить.

## 7. Риски и стоимость (честно)

| Компонент | Стоимость | Комментарий |
|-----------|-----------|-------------|
| Headless-сервер из текущего кода | низкая | `--headless` уже есть |
| SFU (mediasoup/Janus/LiveKit) | высокая | новый стек, деплой, отладка |
| Сигналинг (WebSocket) | средняя | + состояние комнаты на сервере |
| TURN для интернета | средняя | иначе за NAT не соберётся |
| Web-UI (тайлы, устройства) | низкая-средняя | CSS-grid + getUserMedia |
| H.323 в новой схеме | высокая | GStreamer-мост в SFU — нетривиально |

Итого: **не «быстрый фикс», а отдельный этап**. Для текущей боли (Wayland,
Windows) уже есть рабочие локальные обходы (`QT_QPA_PLATFORM=xcb`,
`--doctor`, headless-стенд), так что перенос не горит.

## 8. Решение

**Перенос на web — да, но как второй клиент поверх серверной части, а не
вместо нативного.** Начинать только после того, как SIP/H.323-движок вынесен
в headless-сервер и есть хотя бы один сценарий «сервер ↔ сервер»/«сервер ↔
терминал». До этого — развивать нативный клиент и контейнерный стенд.
