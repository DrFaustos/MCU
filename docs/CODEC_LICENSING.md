# Лицензионная политика кодеков (MCU Client)

Документ политики. Действует для ветки `sip`. Источник истины о наборе
кодеков конкретной сборки — `scripts/codec_probe.py` (зоны: `codecEnum2`
для аудио, `videoCodecEnum2` для видео); всё остальное в этом файле —
юридическая рамка, а не пересказ README.

Ключевое различие, которое здесь путают чаще всего: **лицензия кода
кодека** (BSD/GPL) и **патентная лицензия на алгоритм** (пулы) — разные
предметы. Свободный код OpenH264 не отменяет патентов H.264; закрытая
реализация Polycom не «покупает» право на рединстрибуцию.

## а) Royalty-free маршрут (основной)

Приоритетное направление: **Opus (аудио №1) → G.722 → G.711**, видео —
**VP8**. Все они без патентных пулов: Opus — BSD-2 и обязательство
IETF/Opus Consortium о свободной реализации (RFC 6716); G.722/G.711 —
старые рекомендации ITU без действующих заявленных патентов; Speex — BSD;
iLBC — свободная лицензия RFC 3951; GSM 06.10 — патенты истекли; VP8 —
BSD-код libvpx плюс патентный грант Google, который покрывает и саму
реализацию. Для дистрибутива это означает: **ни одного роялти-платежа за
содержимое бинарей**.

Включается профиль значением `sip.codecs.profile = "royalty_free"`
(или селектором «Набор кодеков» в панели). Цена: аппаратные терминалы
без VP8 не примут видео — для них остаётся маршрут H.264 (п. б).

## б) H.264: единственный обязательный патентный кодек

H.264 — единственный кодек с патентными роялти, без которого нельзя:
весь аппаратный парк ВКС (Polycom/Sony/Cisco) согласует видео только по
H.264/H.263. Обязательство правообладателей не отменяется тем, что
реализация открытая.

Комплаенс-маршрут — **OpenH264 (Cisco)**: код под BSD-2, но главное —
Cisco публикует бинари и **сама платит пулу MPEG LA/Via LA роялти за их
рединстрибуцию** (та же схема, на которой Firefox встроил H.264). Кто
собирает OpenH264 из исходников сам — платит пулу сам. Поэтому: в
дистрибутив попадает бинарник OpenH264 от Cisco, не самопал.

Состояние AVC-пула (проверено по открытым источникам, 2026-11; цифра
обязана перепроверяться юристом при каждой поставке):

* пул администрирует **Via Licensing Alliance** (купил MPEG LA в апреле
  2023); параллельно портфель AVC лицензирует **Access Advance** —
  это два разных пула, платить надо тем, чей список essential патентов
  накрывает продукт;
* интернет-стриминг бесплатного для зрителя видео пул не роялтит
  (решение MPEG LA 2010 г., «на всё время жизни лицензии»); это НЕ
  распространяется на устройства-энкодеры/декодеры — продуктовая часть
  лицензии платная;
* значительная часть базовых патентов AVC уже истекла, но, например,
  патент US 9 356 620 в пуле действует минимум до ноября 2030 —
  рассчитывать на «истекло всё» нельзя;
* в феврале 2026 Via LA объявила новую схему лицензирования стриминга
  (версии спецификации v4+), условия для новых лицензиатов изменились
  с января 2026 — перед любой коммерческой поставкой брать актуальные
  тарифы у пула, не пересказ этого документа.

## в) x264 / x265 / lame в PyInstaller-дистрибутиве

Факт на сегодня: в `dist/MCU-Client` вместе с FFmpeg-бинарями уезжают
`libx264` (GPLv2+), `libx265` (GPL с дополнительным патентным пунктом
лицензиара) и `libmp3lame` (LGPL). Это значит, что бинарь, отданный
заказчику:

1. содержит GPL-модули → срабатывают обязательства GPLv2/LGPL
   (предоставление исходных кодов модулей, сохранение уведомлений);
   молча бандлить их «как есть» нельзя;
2. содержит реализации патентованных кодеков → поверх GPL нужны права
   пулов на рединстрибуцию энкодера (пул лицензирует дистрибьюторов
   устройств/приложений, не «конечных пользователей»).

План:

* собирать FFmpeg дистрибутива **без GPL-модулей**: `--disable-gpl
  --enable-libopenh264 --enable-libvpx`, без `libx264/libx265/lame`
  (запись конференций это не ломает: контейнер MP4/WebM + openh264/VP8);
* `libx265` не бандлировать ни в каком варианте — GPL+патентный пункт
  плюс три правообладателя HEVC;
* в `packaging/` держать manifest бинарей с лицензией на каждый `.so`
  и прогонять его рядом с `scripts/codec_probe.py` перед релизом.

## г) G.722.1 / G.719 / G.729: никогда не в стандартную сборку

Патенты (G.722.1/G.722.1C/G.719 — Polycom/Poly, ныне Zebra; G.729 —
лицензионная история INRS-Telecom/VoiceAge, у ряда реализаций — через
Cisco) не входят ни в AVC-пулы, ни в какие-либо «свободные» гранты.
PJMEDIA правильно делает, что не собирает их по умолчанию.

Решение проекта: в стандартную сборку pjsua2 **не включать эти кодеки
никогда**, включая сборки дистрибутива. Записи `G7221/*`, `G719/*`,
`G729/*` в списках `max_compat`/`wideband` — сознательные
«opportunistic» записи: они дают приоритет только в кастомной сборке,
которую заказчик собрал сам и за лицензию которой платит сам. Стандартная
сборка их молча игнорирует — в этом и смысл, враньём в SDP это не
оборачивается. Тесты `tests/test_codec_compat.py` фиксируют именно такую
семантику (записи есть, приоритета над реально собранными кодеками не
имеют).

## д) Windows pjsua2-wheel: состав не верифицирован

Колёса pjsua2 для Windows распространяются с заранее собранным
pjmedia-стеком неизвестного состава: внутри могут быть и x264, и
самопальный OpenH264, и патентованные аудиокодеки. Пока состав не
документирован, Windows-дистрибутив обязан считаться **непроверенным**
по обоим фронтам (GPL-цепочка и патентные пулы).

Требование перед любой поставкой на Windows: прогнать
`scripts/codec_probe.py` на целевом колесе (он покажет фактический набор
кодеков) и задокументировать DLL рядом с wheel (наличие
`libx264/libx265/lame/openh264`), результат — в `packaging/manifest`.
До этого — не считать Windows-сборку комплаентной.
