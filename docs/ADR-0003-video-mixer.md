# ADR-0003: Видео-микшер (mosaic) на штатных кирпичах pjsua2

Дата: 2026-11-19. Статус: принят, реализован (v1).

## Контекст

Проект позиционировался как «SFU + аудио-микшер»: аудио conference bridge
PJSIP смешивает честно, видео только роутится (ARCHITECTURE §6a). Цель —
приблизиться к OpenMCU/CMX: сервер собирает **видео-композицию (mosaic)** и
отдаёт её участникам единым потоком.

Прямых средств нет: в pjsua2-биндингах 2.16 **нет** доступа к декодированным
кадрам вызова (нет `VideoMediaPort`/`FrameTranslator`/`getFrame` для видео),
в PJSIP нет видео-композиции («not implemented yet»).

## Экспериментально установленные факты (pjsua2 2.16, наш билд; всё проверено живыми прогонами в контейнере mcu-dev-base)

1. `VideoRecorder.createVideoRecorder(файл)` / `VideoPlayer.
   createVideoPlayer(файл)` работают; контейнер — AVI, **видеопоток внутри —
   rawvideo I420** (не MJPEG!: ffmpeg определяет `rawvideo`, кадры
   `w*h*3/2` байт). `getFormat()` у `VideoMedia` в SWIG нет — размеры читаем
   из заголовка файла (`strf` → BITMAPINFOHEADER, `parse_avi_header`).
2. Рекордер pjsua пишется с **жёстким лимитом 5 МБ** (`AVI_REC_FILE_MAX_SIZE`,
   pjsua_vid.c:3412): после достижения писатель молча перестаёт принимать
   кадры. 320x240@15 упирался ровно за 2,9 с (4954270 байт — одна и та же
   цифра в всех прогонах). Отсюда ротация файлов по размеру
   (`max_recorder_bytes`, по умолчанию 4 МБ).
3. `movi LIST size = 0` и `strh frames = 0xffffffff`: размеры и индекс
   дописываются только при закрытии рекордера. Следствия для ffmpeg:
   на seekable-файле avi-демуксер это переживает, но НЕ хвостит — дочитывает
   до текущего конца и выходит rc=0; на не-seekable (pipe) — встаёт навсегда
   (проверено `-loglevel trace`: «movi end=146» и тишина). Патчинг
   заголовка (RIFF/movi size → огромные) не помогает:демуксер ждёт odml-индекс.
   Вывод: байты из файла гонит **самодельный парсер чанк-фрейминга**
   `RecorderFeeder` (заголовки `00dc`/`01wb`), отдающий ffmpeg честный
   `rawvideo`-поток через pipe: читатель блокируется на нехватке байт,
   EOF не наступает, `-re` и перезапуски не нужны.
4. Плеер pjsua понимает в контейнере **только raw-видео** (I420/YUY2/RGB24,
   docs createVideoPlayer). Мозаичный выход ffmpeg обязан быть
   `-c:v rawvideo -pix_fmt yuv420p`: на `-c:v mjpeg` плеер создаётся,
   устройство появляется, но кадров ноль (проверено: probe 326 байт против
   43 кадров у raw). MJPEG — только для веб-ветки (jpeg-сайдек перекодирует).
5. `createVideoPlayer` проигрывает файл **один раз** (loop в 2.16 не открыт).
   Поэтому мозаика пишется поколениями `mosaic_%06d.avi`: композитор всегда
   пишет следующее, плеер доигрывает готовое и переезжает на новое вместе с
   перебиндом capture (`CHANGE_CAP_DEV`). Держать плеер на одном растущем
   файле нельзя — он упирается в «EOF» и глохнет навсегда.
6. `call.getDecodingVideoMedia(med_idx)` — индекс **обязателен** (в реальных
   вызовах видео — поток 1; берём `vidGetStreamIdx()`).
   `VideoMedia.startTransmit(sink, param)` — вторым аргументом нужен
   `pj.VideoMediaTransmitParam()` (SWIG: «argument 3 of type
   pj::VideoMediaTransmitParam const &»); ссылка на param хранится в реестре участников.
7. **Правило потоков**: билд собирается с `threadCnt=0` — PJSIP работает,
   только пока кто-то зовёт `libHandleEvents`. Нативные вызовы из второго
   потока, пока владелец потока внутри нативного вызова, дают AB-BA дедлок
   (доказано faulthandler: main в createVideoRecorder, второй поток в
   getInfo). Поэтому у микшера **нет своего потока**: все нативные операции
   идут из `reconcile()`, который тикает `process_events()` движка.
   `RecorderFeeder` и помпа stdout — чистые IO-потоки (файл/pipe/подпроцесс),
   pjsua не трогают.
8. Фифо как приёмник рекордера **убивает процесс**: `createVideoRecorder`
   открывает приёмник синхронно, `open(O_WRONLY)` на mkfifo ждёт читателя, а
   читатель заводится позже на том же потоке. Только растущие regular-файлы.
9. Помпа stdout дочернего процесса обязана читать `read1()`:
   `BufferedReader.read(65536)` на pipe набивает буфер до конца — mosaic.avi
   оставался нулевым всю жизнь композитора (живой e2e 11/2026).
10. Подпись состава (`_signature`) защёлкивается только при **успешном**
    запуске композитора: иначе первая попытка в окно «файл рекордера ещё без
    заголовка» выключает пересборку навсегда (поймано живым прогоном).
11. `VideoPreview.start()` требует `VideoPreviewOpParam()`; работает headless
    (SDL-dummy), годится как источник для тестов. Устройства Colorbar в
    контейнере честно дают 15 fps, пока рекордер не упёрся в 5 МБ (факт 2).

## Решение

Внешний композитор + штатные pjsua2-порты. Модуль `mcuclient/video_mixer.py`:

    SIP-вызов i --(startTransmit)--> VideoRecorder_i --> in_i.avi (raw I420)
         |            (potok-vladelec PJSIP, reconcile)        |
         |                                            RecorderFeeder (парсер
         |                                             чанков, чистый IO-поток)
         |                                                     | rawvideo pipe
         v                                                     v
    ffmpeg-композитор: N x (-f rawvideo -video_size WxH) -> scale/pad в
    плитки -> hstack рядов -> vstack -> AVI -c:v rawvideo -write_index 0
    на stdout (помпа read1 -> mosaic_NNNNNN.avi следующее поколение)
         |                                                    |
         | те же байты в stdin                                v
         |                                     jpeg-сайдек ffmpeg -> MediaBus
         v                                     ("mosaic", POSIX v1)
    VideoPlayer(mosaic_NNNNNN) = видео-устройство N
         | vidSetStream(CHANGE_CAP_DEV) для всех вызовов (существующий
         v механизм _bind_capture_to_calls)
    все SIP-вызовы получают композицию как «камеру» (v1 — одну общую)

- Раскладка v1: сетка N участников (2x2, 3x3…, активный спикер — v2 по
  уровням conf bridge, они уже честные после фикса getTxLevel).
- v1 отдаёт ОДНУ общую раскладку всем (OpenMCU-basic; per-view без самого
  себя — итерация v2: N выходов композитора, N плееров).
- Ротация: файлы рекордеров пересоздаются по размеру (факт 2), каждое
  ротационное событие пересобирает композитор (сигнатура → None) и плеер
  переезжает на следующее поколение. Цикл в тесте — ~2–5 с.
- Камеры выключенных участников — плитка-заглушка (генерирует композитор),
  аудио-микшер не трогаем (conf bridge уже MCU).
- Кодек для пира — как договаривались (H264/OpenH264, VP8): mosaic попадает
  в пайплайн как «камера», энкодер PJSIP не знает подмены. Внутри — raw I420
  (royalty-free по определению); ffmpeg внешний (тот же контракт, что у
  ConferenceRecorder — GPL-процесс вне linked-кода).
- Платформа v1: **POSIX** (pipe + /dev/fd + pass_fds). На Windows сервис
  `available()` возвращает False и молча не мешает вызовам (per-user
  именованные pipe — v2).
- Фолбэки: ffmpeg отсутствует / вызовов < min_participants / ошибки портов —
  модуль молча неактивен, вызовы идут как раньше (роутинг). Ничего не ломаем.

## Доказательство живым стендом (обязательный пункт)

`scripts/testbed/run_two_instance_mosaic_test.sh` (в контейнере
mcu-dev-base, камеры — Colorbar): слушатель — «MCU» (микшер включён,
min_participants=1), звонящий — обычный терминал (MCU_MIXER=0, стабильная
15 fps камера; взаимная топология «оба микшера» самопитается — оба шлют
друг другу доигрывающие плееры). Критерии и фактические числа прогона
2026-11-19: 5 поколений мозаики по 25–33 кадра 320x240; `Мозаика
(mosaic_NNNNNN.avi) стала видео-устройством 3→4→5→6`; **проба входящего
видеозвонка у терминала — 43 кадра за 6 с уже после того, как MCU подменил
камеру мозаикой** (до подмены поток шёл с камеры, после — только из
мозаичного плеера: это и есть сквозное доказательство). Оба процесса rc=0,
падения/дедлоки не воспроизведены; единичный flaky `grp_lock_acquire`
SIGABRT при автоответе наблюдался ОДИН раз до появления микшера и больше
не появлялся (отдельная известная неопределённость).

## Альтернативы и почему отвергнуты

- **Вирт-камера v4l2loopback + композит в /dev/videoN**: требует DKMS-модуль
  на хосте (Bazzite/rpm-ostree — боль), Windows без аналога. Устройство-плеер
  pjsua закрывает ту же задачу нативно.
- **VideoMediaPort для видео (правки SWIG/C)**: честнее всех, но выпадает из
  pip-канала pjsua2 (наш CI собирает биндинги скриптом — правка слоя C
  окупится позже, отдельным ADR).
- **RTP-мост видео (аналог rtp_audio)**: H264-фрагментация/PLI/90кГц +
  ключевые кадры — большой объём, выигрыша над device-путём нет.
- **aiortc как единый медиастек**: ломает аппаратную ВКС-совместимость —
  фундамент проекта.
- **Чтение файлов рекордера ffmpeg напрямую / pipe с AVI-байтами / -re
  pacing / патч AVI-заголовка**: все четыре варианта проверены живьём и
  умерли на фактах 3/5 (кадры пачками с перезапуском, нулевой вывод,
  обгон писателя в разы). Остался парсер чанков с rawvideo-выходом.

## Следствия

- ARCHITECTURE §6a переписывается: «SFU+аудио-микшер» → «MCU-режим
  композиции (v1: общая сетка) + SFU-режим роутинга».
- Релизный контракт не меняется; флаг `features.video_mixer.enabled`
  (по умолчанию false до обкатки на железе).
- Пропускная способность внутренней мозаики — RAW: байт/с мозаичного файла
  = (cols*tile_w)·(rows*tile_h)·1,5·fps. 1 плитка 320x240@15 ≈ 1,7 МБ/с,
  3x3 960x720@15 ≈ 104 МБ/с — для 9 слотов v1 обязан снизить fps/tile
  (параметры в `features.video_mixer`), иначе диск/pipe тонут. Для веба
  это не критично (jpeg-сайдек перекодирует в малый поток).
- Известные ограничения v1 (честно): картинка обновляется поколениями
  (плеер доигрывает поколение ~2–5 с, кратковременные паузы между
  поколениями); hstack ждёт все входы — зависший вызов замораживает
  пересборку роустра; Windows без микшера; одна общая раскладка всем.
