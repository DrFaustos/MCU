# Статус H.323

* Обновлено: 2026-10-08
* Решение: `docs/ADR-0002-h323plus-unified-media.md`

## Кратко

**Стек H323Plus собран, C++-хост `mcu_h323d` принимает и инициирует H.323-вызовы:
сигнализация Q.931/H.225/H.245 проверена живьём между двумя хостами.** Но хост
пока **только сигнальный**: медиа-каналы (RTP/кодеки) в нём не открываются,
поэтому звук и картинка через него ещё не идут — со звонком «соединение есть,
молчим». Это ожидаемое состояние Этапа 1 (см. таблицу этапов). Есть два
взаимодополняющих пути:

1. `mcuclient/h323_endpoint.py` — «Вариант A»: in-process эндпоинт на
   python-биндингах H323Plus (когда они есть). Слушает порт **1720** и
   заводит участников в общую комнату.
2. `mcuclient/h323_host.py` + `tools/h323d` — «Вариант B»: H323Plus живёт в
   отдельном C++-процессе `mcu_h323d`, Python общается с ним по unix-сокету
   (newline-delimited JSON). Это основной путь, т.к. python-биндингов
   H323Plus не существует.

Важно: приложение **не падает**, если ни хост, ни нативная библиотека не
готовы — `H323Endpoint.start()` возвращает `False`, `H323HostClient.connect()`
возвращает `False`, клиент продолжает работать SIP-only.

`mcuclient/h323_gateway.py` (GStreamer + Asterisk `chan_ooh323`) — старый
обходной путь, помечается устаревшим после проверки Этапа 1.

## Почему протокол не «выбирается» автоматически

Протокол всегда выбирает **вызывающая сторона** настройкой на своём терминале.
SIP и H.323 — два разных порта и два разных стека сигнализации. Нельзя «по одному
адресу принять и то, и другое» без явной реализации обоих стеков на одном хосте.

* Терминал настроен на **SIP** → шлёт INVITE на `room@host:5060` → наш PJSIP примет.
* Терминал настроен на **H.323** → шлёт Q.931 на `host:1720` → примет наш
  `H323Endpoint` либо C++-хост `mcu_h323d` (когда H323Plus собран).

## Что делаем (ADR-0002)

Переходим на **единый медиа-слой H323Plus** (форк willamowius) для H.323 и SIP,
по образцу OpenMCU.ru (там SIP-вызовы тоже создают `H323Connection`).
Это даёт один микшер и один PCM-конвейер без дублирования буферов.

## Что уже есть по Этапу 1

### Вариант A — `mcuclient/h323_endpoint.py`

* по имени «in-process», по факту — **клиент хоста `mcu_h323d`**: python-биндингов
  H323Plus не существует, вся H.323-логика живёт в C++-процессе;
* `H323Endpoint` — превращает события хоста в участников ОБЩЕЙ комнаты, отвечает
  (`call.answer`), отклоняет (`call.reject`), сбрасывает (`call.hangup`), звонит сам
  (`make_call` → `call.make`);
* `H323CallInfo`, `alias_to_uri()`, `state_from_h323()`, `call_info_from_event()`,
  `parse_auto_answer_flag()` — чистые функции, тестируются без хоста;
* graceful degradation: без хоста `start()` возвращает `False`, и клиент продолжает
  работать SIP-only. Упоминание `H323_AVAILABLE` в старых записях журнала
  устарело — такого символа в коде нет, деградация идёт через `start()`.

### Вариант B — C++-хост (`tools/h323d` + `mcuclient/h323_host.py`)

* `tools/h323d/` — процесс `mcu_h323d` на H323Plus/PTLib (CMake): слушает
  H.323, шлёт события `ready` (с полем `auto_answer`) / `call.incoming` /
  `call.outgoing` / `call.connected` / `call.disconnected` / `error` и
  принимает команды `call.make` / `call.answer` / `call.reject` /
  `call.hangup` / `ping` / `shutdown` по unix-сокету.
  Ключ `--no-auto-answer` ставит входящий вызов на паузу (`OnAnswerCall`
  возвращает `AnswerCallPending`, отправлен Alerting) — вызов отвечает
  человек или UI командой `call.answer`. Решение принимается именно там:
  `OnIncomingCall` обязан возвращать TRUE, иначе H323Plus сбрасывает вызов
  с `EndedByNoAccept` и ответить afterwards уже нельзя (`h323.cxx:1537`).
* `mcuclient/h323_endpoint.py` (Вариант A по имени, по факту — клиент хоста):
  * участники заводятся через **общий `CallRegistry`** движка (`registry=`) —
    единый счётчик id на SIP и H.323, иначе H.323 затирал SIP-участника;
  * комната берётся из реестра (`ep.room`), а не хранится ссылкой: у движка
    комната появляется только в `start()`, а эндпоинт создаётся раньше;
  * `handle_call_op("accept"|"reject"|"hangup", id)` — маршрутизация операций
    UI/web до хоста (`SipEngine.set_h323_native()` + `_route_call_op`);
  * режим ответа берётся из `ready.auto_answer`, а не из собственного флага:
    `--no-auto-answer` задаётся аргументами хоста (см. `parse_auto_answer_flag`).
* `mcuclient/h323_host.py` — python-клиент IPC:
  * `H323HostClient` (connect/start/send_command/answer/hangup/close/stop);
  * `HostEvent`, `HostStatus`, `EVENT_MAP`, `event_to_bus_payload`,
    `parse_host_event()`, `encode_command()`, `host_available()`,
    `find_host_binary()` — чистые функции без сокета (тестируемы).
* `run.py`: при `--h323` (или `h323.enabled`) подключается к хосту по
  `--h323-socket` (по умолчанию `/tmp/mcu_h323d.sock`), транслирует события
  хоста в `EventBus` и регистрирует входящих в общую комнату; если хост не
  запущен — пишет подсказку и продолжает SIP-only.
* `scripts/build_h323d.sh` — сборка хоста (требует PTLib + H323Plus).
* `scripts/h323d_smoke.py` — дымовой тест IPC без H.323-терминала.
* `tests/test_h323_host.py`, `tests/test_h323d_client.py` — 37 тестов IPC
  (разбор событий, команды, статус, деградация без сокета).

## Безопасность: закрытый контур, без сертификатов

Осознанное решение для изолированной сети (см. ADR-0002 §3.3):

* H.235 — выключено.
* SIP TLS — не используется (только UDP/TCP).
* SRTP — выключено.
* IPC-сокет — только localhost/unix, без TLS.
* Web-интерфейс (если появится) — HTTP или локальный самоподписанный сертификат,
  без внешнего CA.

## Проверено локально (2026-10-08)

Стек H323Plus **собран** в `/usr/local` (`scripts/install_h323plus.sh`),
C++-хост `tools/h323d` собирается через CMake и проходит дымовой тест
связки с Python-клиентом. С 2026-10-08 добавлена проверка **настоящим
звонком**: поднимаются два процесса `mcu_h323d` на 127.0.0.1 и между ними
проходит полный Q.931/H.225/H.245-обмен — исходящий вызов, приём, отложенный
ответ, `call.connected` с обеих сторон, сброс и `call.disconnected` в обе
стороны (`scripts/testbed/h323_native_two_hosts.py`, RC=0). Медиа при этом
**не проверяется** — его в хосте ещё нет.

 

Исправлено по ходу проверки:

* `to_std(const PString&)` использовал `s.GetPointer()` (не компилируется на
  PTLib 2.10.9) — заменено на `(const char *)s`;
* событие `ready` слалось один раз при старте процесса и терялось, если
  Python-клиент подключался позже (`write_loop` не находил получателя).
  Теперь `ready` шлётся из `Server::set_on_client_connected()`, т.е. в момент
  фактического подключения Python-клиента;
* удалены дублирующиеся/устаревшие исходники в `tools/h323d` (осталось
  каноническое: `main.cpp` + `ipc.hpp` + `json.hpp`).

## Выбор протокола при звонке (v0.2.29)

Для тестов совместимости и отладки протокол исходящего вызова теперь
выбирается явно (`mcuclient/call_proto.py`):

* `auto` — по префиксу адреса (`h323:`/`h323s:` → H.323, `sip:` → SIP,
  голый IP → SIP); при доступном нативном хосте `h323:` уходит в
  `h323_native`;
* `sip` — PJSIP;
* `h323` — GStreamer-шлюз (`h323_gateway.py`);
* `h323_native` — нативный H.323 через хост `mcu_h323d`.

В GUI — список **Протокол**, в CLI — `--proto`, в конфиге —
`features.default_call_protocol`. Это позволяет позвонить по голому IP
именно по H.323 (нативный стек) на аппаратный терминал Sony/Polycom,
не полагаясь на префикс URI. См. `docs/CALL_PROTOCOL.md`.
