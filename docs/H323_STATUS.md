# Статус H.323

* Обновлено: 2026-11-20
* Решение: `docs/ADR-0002-h323plus-unified-media.md`

## Кратко

**Стек H323Plus собран, C++-хост `mcu_h323d` принимает и инициирует H.323-вызовы:
сигнализация Q.931/H.225/H.245 проверена живьём между двумя хостами.** Медиа
тоже есть: аудио-канал соглашается, PCM идёт в обе стороны через
переопределённый `OpenAudioChannel` (событие `pcm.in`, команда `pcm.out`), а
`mcuclient/h323_audio_bridge.py` сводит вызовы в общий микс — два H.323-терминала
слышат друг друга через MCU, эха нет (стенды двух и трёх хостов, RC=0). Тем же
RMS-снимком мост выставляет участникам комнаты `volume_level` и `is_speaking`:
без этого веб-панель показывала «не говорит» у всех, а раскладка `speaker`
держала главным первого по списку — при живом разговоре и без единой ошибки в
логе. Затухание (кто замолчал) живёт не в мосту, а в общем
`audio_mixer.LevelsIndicator`: у веб-микшера ровно та же задача, и две копии
разошлись бы по порогам.
Если `mcu_h323d` умирает посреди разговора, вызовы не остаются «живыми»: обрыв
IPC — это событие `connection.closed`, по нему эндпоинт снимает участников
мёртвого хоста, а аудио-мост освобождает буферы микшера (иначе в комнате
оставался «фантом» в `CONFIRMED`, и web-панель показывала несуществующее
соединение).
С 2026-11-19 картинка через хост ЕСТЬ (Этап 4 первой половины): видеоканал
соглашается, декодированные кадры уходят в Python вторым unix-сокетом
(бинарные записи, latest-wins — JSON-канал аудио не затыкается), а стенд
`scripts/testbed/h323_video_live.py` меряет картинку сквозняком: паттерн хоста
A → H.261 → RTP → декодер хоста B → PNG, семь полос своими цветами и в
правильном порядке (BT.601 75%, сверка побайтная). Боевой кодек сегодня один —
**H.261** (плагин VIC): H.263-1998 не собирается против современного
libavcodec, H.264 — это отдельный стенд `:v129` со стеком 1.29.1 и плагином
OpenH264 (замер: H.264-CIF согласуется, картинка доезжает; H.264-1080 — только
по явному `--video-codecs`). Честная формулировка для заказчика — в
`docs/CODECS.md` §9. Видеостена (webRTC-даунлинк) H.323-вызов пока НЕ
показывает: трек зрителя строится на id из `subscribe`, а aiortc в dev-контейнере
нет — до панели доказано доезжание кадра в шину медиа под id участника и в
предпросмотр `/api/frame.png`. Есть два взаимодополняющих пути:

1. `mcuclient/h323_endpoint.py` — «Вариант A»: in-process эндпоинт на
   python-биндингах H323Plus (когда они есть). Слушает порт **1720** и
   заводит участников в общую комнату.
2. `mcuclient/h323_host.py` + `tools/h323d` — «Вариант B»: H323Plus живёт в
   отдельном C++-процессе `mcu_h323d`, Python общается с ним по unix-сокету
   (newline-delimited JSON). Это основной путь, т.к. python-биндингов
   H323Plus не существует.

Важно: приложение **не падает**, если ни хост, ни нативная библиотека не
готовы — `H323Endpoint.start()` возвращает `False`, `H323HostClient.connect()`
возвращает `False`, клиент продолжает работать SIP-only.

`mcuclient/h323_gateway.py` (GStreamer + Asterisk `chan_ooh323`) — старый
обходной путь, помечается устаревшим после проверки Этапа 1.

## Почему протокол не «выбирается» автоматически

Протокол всегда выбирает **вызывающая сторона** настройкой на своём терминале.
SIP и H.323 — два разных порта и два разных стека сигнализации. Нельзя «по одному
адресу принять и то, и другое» без явной реализации обоих стеков на одном хосте.

* Терминал настроен на **SIP** → шлёт INVITE на `room@host:5060` → наш PJSIP примет.
* Терминал настроен на **H.323** → шлёт Q.931 на `host:1720` → примет наш
  `H323Endpoint` либо C++-хост `mcu_h323d` (когда H323Plus собран).

## Что делаем (ADR-0002)

Переходим на **единый медиа-слой H323Plus** (форк willamowius) для H.323 и SIP,
по образцу OpenMCU.ru (там SIP-вызовы тоже создают `H323Connection`).
Это даёт один микшер и один PCM-конвейер без дублирования буферов.

## Что уже есть по Этапу 1

### Вариант A — `mcuclient/h323_endpoint.py`

* по имени «in-process», по факту — **клиент хоста `mcu_h323d`**: python-биндингов
  H323Plus не существует, вся H.323-логика живёт в C++-процессе;
* `H323Endpoint` — превращает события хоста в участников ОБЩЕЙ комнаты, отвечает
  (`call.answer`), отклоняет (`call.reject`), сбрасывает (`call.hangup`), звонит сам
  (`make_call` → `call.make`);
* `H323CallInfo`, `alias_to_uri()`, `state_from_h323()`, `call_info_from_event()`,
  `parse_auto_answer_flag()` — чистые функции, тестируются без хоста;
* graceful degradation: без хоста `start()` возвращает `False`, и клиент продолжает
  работать SIP-only. Упоминание `H323_AVAILABLE` в старых записях журнала
  устарело — такого символа в коде нет, деградация идёт через `start()`.

### Вариант B — C++-хост (`tools/h323d` + `mcuclient/h323_host.py`)

* `tools/h323d/` — процесс `mcu_h323d` на H323Plus/PTLib (CMake): слушает
  H.323, шлёт события `ready` (с полем `auto_answer`) / `call.incoming` /
  `call.outgoing` / `call.connected` / `call.media` (кодек и частота
  PCM-канала) / `call.disconnected` / `pcm.in` (кадр входящего PCM) /
  `dtmf.in` (принятый набор: `digits`, `via` = `tone`\|`string`, `duration_ms`) /
  `error` и принимает команды `call.make` / `call.answer` / `call.reject` /
  `call.hangup` / `pcm.out` (записать исходящий PCM) /
  `dtmf.send` (передать тоны в вызов) / `ping` / `shutdown`
  по unix-сокету.
  DTMF устроен как H.245 UserInput, а не как RTP telephone-event: хост объявляет
  возможности `AddAllUserInputCapabilities` (wildcard `"*"` их НЕ добавляет — он
  перебирает медиа-форматы) и фиксирует `SetSendUserInputMode(SendUserInputAsTone)`,
  потому что дефолт форка — alphanumeric. Принятый тон приходит и по H.245
  signal, и in-band (RFC 4733): в форке оба стекаются в
  `H323Connection::OnUserInputTone`, поэтому поле называется `via`, а не
  `method`, и `rfc2833` никогда не значения. Тон-пробел (`e_signalUpdate`,
  «текущий тон ещё идёт») отфильтрован, иначе журнал задваивается на каждом
  нажатии; базовый `H323EndPoint::OnUserInputTone` не вызывается — он разворачивает
  тон в `OnUserInputString`, и тот же набор ушёл бы вторым событием без длительности.
  Ключ `--no-auto-answer` ставит входящий вызов на паузу (`OnAnswerCall`
  возвращает `AnswerCallPending`, отправлен Alerting) — вызов отвечает
  человек или UI командой `call.answer`. Решение принимается именно там:
  `OnIncomingCall` обязан возвращать TRUE, иначе H323Plus сбрасывает вызов
  с `EndedByNoAccept` и ответить afterwards уже нельзя (`h323.cxx:1537`).
* `mcuclient/h323_endpoint.py` (Вариант A по имени, по факту — клиент хоста):
  * участники заводятся через **общий `CallRegistry`** движка (`registry=`) —
    единый счётчик id на SIP и H.323, иначе H.323 затирал SIP-участника;
  * комната берётся из реестра (`ep.room`), а не хранится ссылкой: у движка
    комната появляется только в `start()`, а эндпоинт создаётся раньше;
  * `handle_call_op("accept"|"reject"|"hangup", id)` — маршрутизация операций
    UI/web до хоста (`SipEngine.set_h323_native()` + `_route_call_op`);
  * DTMF в обе стороны: `handle_dtmf(id, digits)` / `send_dtmf_all(digits)` —
    `SipEngine.send_dtmf` роутит H.323-участника на хост (у него нет pjsua2-`Call`,
    поэтому SIP-путь для него бессмыслен), а принятые хостом тоны пишутся в
    **общий журнал комнаты** через `set_dtmf_service(engine.dtmf_service)`:
    второй журнал расходился бы с первым, а без журнала «набрал ли терминал PIN»
    по МСУ не проверяется вовсе;
  * режим ответа берётся из `ready.auto_answer`, а не из собственного флага:
    `--no-auto-answer` задаётся аргументами хоста (см. `parse_auto_answer_flag`);
  * обрыв без нашего `close()` (хост упал или убит) — событие
    `connection.closed`, а не тишина: `H323Endpoint._on_host_lost()` снимает
    всех участников мёртвого хоста с `notify_host=False` (в мёртвый сокет
    `call.hangup` слать бессмысленно), `H323AudioBridge.forget_all()` убирает
    их буферы из микшера, не отписывая сам мост — владельцем соединения
    остаётся эндпоинт.
* `mcuclient/h323_host.py` — python-клиент IPC:
  * `H323HostClient` (connect/start/send_command/answer/hangup/close/stop);
  * `HostEvent`, `HostStatus`, `EVENT_MAP`, `event_to_bus_payload`,
    `parse_host_event()`, `encode_command()`, `host_available()`,
    `find_host_binary()` — чистые функции без сокета (тестируемы).
* `run.py`: при `--h323` (или `h323.enabled`) подключается к хосту по
  `--h323-socket` (по умолчанию `/tmp/mcu_h323d.sock`), транслирует события
  хоста в `EventBus` и регистрирует входящих в общую комнату; если хост не
  запущен — пишет подсказку и продолжает SIP-only.
* `scripts/build_h323d.sh` — сборка хоста (требует PTLib + H323Plus).
* `scripts/h323d_smoke.py` — дымовой тест IPC без H.323-терминала.
* `tests/test_h323_host.py`, `tests/test_h323d_client.py` — IPC-разбор
  (события, команды, статус, деградация без сокета): числа — в разделе «Тесты».

    PNG; проверяются полнота записей, порядок и цвета семи полос (BT.601 75%,
    побайтно), параллельный звук (`pcm.in` не проседает) и режим `--no-video`
    (видео не согласуется, вызов и звук не тронуты);
  * `scripts/testbed/h323_video_panel.py` — «терминал + операторская панель»:
    МСУ поднимается настоящим `run.py --headless --web --h323`, терминал звонит
    и включает паттерн, меряется HTTP панели: ряд вызова с `video_codec`, кадр в
    шине медиа под id участника, при `--preview` (включает МСУ
    `--h323-video-preview`) предпросмотр растёт,
    `/api/frame.png` отдаёт живой PNG. Про ловушку счётчиков — ниже, в разделе
    про панель.
  Сборка `./scripts/build_h323d.sh`, запуск
  `LD_LIBRARY_PATH=/usr/local/lib python3 scripts/testbed/<стенд>.py`. Видео-стенды
  требуют video-плагин в стеке, то есть живут в контейнере:
  `./scripts/h323_in_container.sh video-live` / `video-panel`
  (`docs/DEV_CONTAINERS.md` §7).

## Безопасность: закрытый контур, без сертификатов

Осознанное решение для изолированной сети (см. ADR-0002 §3.3):

* H.235 — выключено.
* SIP TLS — не используется (только UDP/TCP).
* SRTP — выключено.
* IPC-сокет — только localhost/unix, без TLS.
* Web-интерфейс (если появится) — HTTP или локальный самоподписанный сертификат,
  без внешнего CA.

## Проверено локально (2026-10-09)

Стек H323Plus **собран** в `/usr/local` (`scripts/install_h323plus.sh`),
C++-хост `tools/h323d` собирается через CMake и проходит дымовой тест
связки с Python-клиентом. С 2026-10-08 добавлена проверка **настоящим
звонком**: поднимаются два процесса `mcu_h323d` на 127.0.0.1 и между ними
проходит полный Q.931/H.225/H.245-обмен — исходящий вызов, приём, отложенный
ответ, `call.connected` с обеих сторон, сброс и `call.disconnected` в обе
стороны, а с 2026-10-08 ещё и **медиа**: тон 800 Гц подаётся командой
`pcm.out`, уходит в RTP и возвращается на другой стороне событием `pcm.in` —
стенд меряет RMS по PCM и по WAV-дампам обоих направлений (`--dump-pcm`),
`scripts/testbed/h323_native_two_hosts.py`, RC=0).

Медиа в хосте держится на трёх неочевидных вещах (без любой из них вызов
«установлен», а звука нет — см. `.ai-free/knowledge/notes.md`):

* `endpoint.AddAllCapabilities(0, P_MAX_INDEX, "*")` — конструктор
  `H323EndPoint` кодеки НЕ выставляет, с пустой таблицей H.245 не соглашает
  ни одного аудио-канала. Вызов ровно ОДИН с wildcard: приоритет кодека задаёт
  штатный `H323EndPoint::ReorderCapabilities(preferenceOrder)` (`h323ep.h:311`
  → `H323Capabilities::Reorder`, `h323caps.cxx:4143`), потому что
  `H323Connection::SelectDefaultLogicalChannel` (`h323.cxx`) перебирает
  возможности строго в порядке таблицы и открывает первую совпавшую. Без
  reorder обход фабрики идёт по алфавиту, и вызов соглашал узкополосный
  `G.711-ALaw-64k` даже при 25 возможностях. Замер зондом таблицы возможностей
  (приём — `GetFrameTime()*GetTimeUnits()` по каждой записи; исходник зонда и
  все замеры — `.ai-free/knowledge/notes.md`): до — `[0] G.711-ALaw-64k`,
  после — `[0] G.722.1-24k{sw}`; живой хост печатает
  `приоритет аудио-кодеков: G.722-64k{sw},G.722.1-24k{sw},…`.
  Вторым вызовом `AddAllCapabilities` приоритет НЕ задают: с уложенными
  video-плагинами он падает в SIGSEGV внутри H323Plus
  (`PrintOn → H323CodecExtendedVideoCapability::GetFormatName` по удалённой
  возможности, замер 2026-10-20 — exit=139).
  В приоритет берётся только аудио с кадром ≥ 10 мс: хост смотрит на
  фактический `GetMediaFormat().GetFrameTime()`, а не на имя кодека. Плагин
  `G.722` в апстриме объявляет кадр в 1 мс (`usPerFrame=1000` → PCM-буфер 32
  байта), т.е. 1000 RTP-пакетов/с и 1000 `pcm.in`-событий/с на канал, и
  Python-конвейер перестаёт тянуть звук; честные 20 мс ему возвращает правка
  определения плагина, которую ставит `scripts/install_h323plus.sh`
  (`patch_g722_frame`). Без этой правки хост остаётся на `G.722.1`, с ней —
  идёт `G.722-64k` (подробности — `.ai-free/knowledge/notes.md`);
* исходящее видео живёт только с правкой grab-size (`patch_pluginmgr_grabsize`
  в `h323pluginmgr.cxx`): апстрим v1_28_0 после каждого кодирования затирает
  `bytesPerFrame` — размер сырого grab-кадра — размером закодированного вывода
  (~2 Кбайт), а следующий `SetFrameSize` выходит по раннему return; grab читает
  кадр не целиком, и по RTP уезжает первый полный кадр с обновляемыми первыми
  ~2 Кбайтами. Поймано 2026-11-19 стендом `h323_video_mix.py`: приёмник
  минуты держал первый кадр (смена композита не долетала); подтверждено
  трассировкой `Read(len≈2000)` на живом канале (подробности — DEV_CONTAINERS §7);
* контент снимается безусловно: `RemoveCapability(e_ExtendVideo)` (H.239).
  `e_Video` намеренно не трогает extended video (`h323caps.cxx:3947`), а H.239
  — это именно оно: на дереве audio+video после `e_Video` в таблице оставались
  `H.239(H.263-720)`, `H.239(H.264)`, `H.239 Control` (35 → 28 записей).
  С 2026-11-19 видео-группа снимается только по `--no-video` (или когда в
  профиле не осталось ни одного видео-формата): с уложенным video-плагином
  хост обслуживает видеоканал, и снимать возможность стало бы ошибкой. Пока
  плагинов в стеке не было, оставлять e_Video в соглашении значило «разрешить
  пиру открыть канал, который хост не обслуживает» — тогда снятие было
  обязательным, об этом напоминает комментарий у `apply_codec_profile` в
  `tools/h323d/main.cpp`;
* decoder-канал **обязан держать реальное время**: `H323_RTPChannel` ждёт, что
  запись в звуковой канал займёт ~20 мс на кадр (см. комментарий в
  `src/channels.cxx`); без пейсинга приёмный тред выкачивает весь RTP разом;
* `Ring::write` в `pcm.hpp` обязан писать в `buf_[head_]` — `head_` уже и есть
  слот записи.

 

С 2026-10-09 к тому же проверено **микширование через MCU**: стенд
`scripts/testbed/h323_native_mcu_three_hosts.py` поднимает три процесса
`mcu_h323d` (MCU + терминалы A и B) и замеряет, что тон A доезжает до B через
микшер MCU (RMS 4297), собственного тона в обратном канале нет — эха нет (RMS 8),
обратное направление живое (RMS 3722), мьют участника заглушает его для
собеседника и возвращает голос после снятия, а завершённый вызов уходит из
микшера (фантомов не остаётся). С 2026-10-21 там же проверяется сквозной DTMF:
набор терминала `12#7` попадает в общий журнал комнаты с id участника A
(`лента='12#7'`, дублей нет), журнал публикует `dtmf.digits`, а отправка МСУ `*9`
доходит до терминала и записывается в тот же журнал. RC=0.

Исправлено по ходу проверки:

* `to_std(const PString&)` использовал `s.GetPointer()` (не компилируется на
  PTLib 2.10.9) — заменено на `(const char *)s`;
* событие `ready` слалось один раз при старте процесса и терялось, если
  Python-клиент подключался позже (`write_loop` не находил получателя).
  Теперь `ready` шлётся из `Server::set_on_client_connected()`, т.е. в момент
  фактического подключения Python-клиента;
* удалены дублирующиеся/устаревшие исходники в `tools/h323d` (осталось
  каноническое: `main.cpp` + `ipc.hpp` + `json.hpp`).

## Заход 2026-11-19: профили кодеков, видео, контейнер, лаборатория

### Профили кодеков и лицензии (docs/CODECS.md)

Два профиля объявления возможностей: `compat` (по умолчанию — историческое
поведение, ничего не снято) и `royalty-free` (снимает ровно `G.722.1-24k` и
`G.722.1-32k`, замерено на живом `ready`). Хост знает
`--codecs-profile/--audio-codecs/--disable-codecs/--allow-codecs/--video-codecs/--no-video`,
панель и конфиг — `--h323-codec-profile/--h323-audio-codecs/--h323-allow-codecs`
(реестр флагов — `docs/DEV_LOCAL.md`), `ready` отдаёт `audio_profile`,
`audio_codecs` и полную таблицу `capabilities` — панель показывает
**объявленное**, а не заказанное. Юридическая рамка (три статуса: истёк,
грант правообладателя, нужна оплата) и формулировка для заказчика — в
`docs/CODECS.md`; инженерный вывод оттуда же: живой кодек сегодня H.261,
H.264 — только стенд `:v129` (1.29.1 + OpenH264, §10 с замерами).

### Видео: первая половина Этапа 4 сделана

`OpenVideoChannel` поднят, декодированные кадры уходят в Python **вторым
unix-сокетом** `<socket>.video` (бинарные записи, latest-wins на стороне
хоста — JSON-канал сигнализации и аудио не затыкается; формат —
`tools/h323d/README.md`). `mcuclient/h323_video_bridge.py` кладёт кадр в
`MediaBus` под **id участника комнаты** — по образцу веб-релея
(`webrtc_ingest.py`, `publish_id`), а не по SIP-префиксу `h323v-`: панель
читает шину именно по id ряда (`web_server.py` → `bus.video_version`), с
префиксом ряд жил без кадров при живом кабеле. Опциональный второй приёмник
— `frame_hub` предпросмотра (`/api/frame.png`).

Где мерить панель (ловушка, зафиксирована стендом): `/api/conference` —
счётчики рядов **веб-конференции**, H.323-вызова там нет вовсе;
`/api/participants` — список без медиа-счётчиков; ряд H.323-вызова с
`video_codec` и счётчик предпросмотра — в `/api/status`. «Кадр доезжает до
шины медиа под id участника и в предпросмотр» — доказано стендом
`h323_video_panel.py`; «видеостена показывает H.323» — НЕТ: webRTC-трек
зрителя строится на id из `subscribe`, aiortc в dev-контейнере отсутствует,
даунлинк проверен только контрактом имени канала.

### Воспроизводимая сборка: `mcu-dev-h323` (DEV_CONTAINERS §7)

Образ собирается тем же `scripts/install_h323plus.sh`, что и ручная
установка, — один источник истины для версий, патча кадра G.722 и укладки
плагинов. Точка входа — `scripts/h323_in_container.sh`
(build/h323d/smoke/testbed/video-live/video-panel/tests/bash/passthrough).
Дефолт — PTLib 2.10.9.6 + H323Plus 1.28.0 + аудио-плагины + `H.261-vic`;
`:v129` (2.10.9.8 + 1.29.1 + OpenH264) — стендовый тег с отдельным томом
сборки. Грабли закрыты в скриптах и разобраны в `docs/AI_CONTEXT.md`
(§3.15–3.18: тихий master на фальш-тегах, `ENV PREFIX`, кадр G.722,
`set -e`-рецептура `all` в plugins).

### Лаборатория без ВКС-железа (docs/TESTING_NO_HARDWARE.md)

`tools/virtterm` — вирт-терминал на H323Plus с профилями возможностей под
типовое железо (sony, tandem-old, old-polycom, narrowband) и детектируемым
медиа-поведением; `scripts/testbed/hw_emu/` — переигрывание pcap против
настоящего `mcu_h323d` (dial на порт из ПРИСЛАННОГО CONNECT — без faststart
иначе не дозвониться), корпус собственных записей, `scripts/testbed/lab_uplink.sh`
— пресеты деградации канала (netem): rate64k роняет RMS приёма с 4026 до
2651 — честные измерения вместо «зелёной тишины». Границы метода — §4 дока.

### Честные границы захода

* Видеомикшер (сборка кадров в раскладку) не делался: есть доставка
  отдельных кадров до шины/предпросмотра;
* браузерный даунлинк H.323-картинки не проверен (aiortc нет в контейнере);
* вектор YUV→RGB исполняется только где есть numpy (в dev-контейнере его
  нет — там прогоняется эталонный Python; самопроверка откатывает на эталон
  при расхождении);
* H.263-1998 не собирается против libavcodec 6 (второй видеокодек — только
  OpenH264 на `:v129`); юридический выбор бинарника/исходников H.264 —
  вопрос не инженерный, закрыт в доке как открытый;
* AEC (хвост Этапа 3) и Этап 2 (SIP через H323Plus) — не тронуты.

## Выбор протокола при звонке (v0.2.29)

Для тестов совместимости и отладки протокол исходящего вызова теперь
выбирается явно (`mcuclient/call_proto.py`):

* `auto` — по префиксу адреса (`h323:`/`h323s:` → H.323, `sip:` → SIP,
  голый IP → SIP); при доступном нативном хосте `h323:` уходит в
  `h323_native`;
* `sip` — PJSIP;
* `h323` — GStreamer-шлюз (`h323_gateway.py`);
* `h323_native` — нативный H.323 через хост `mcu_h323d`.

В GUI — список **Протокол**, в CLI — `--proto`, в конфиге —
`features.default_call_protocol`. Это позволяет позвонить по голому IP
именно по H.323 (нативный стек) на аппаратный терминал Sony/Polycom,
не полагаясь на префикс URI. См. `docs/CALL_PROTOCOL.md`.
