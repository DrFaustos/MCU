# Web-панель управления (встроенный web-сервер)

Приложение MCU — одновременно **клиент и сервер**. Поверх уже запущенного
SIP/H.323-движка (в GUI или в `--headless`) оно может поднять HTTP-сервер
с REST API и страницей управления. Браузер подключается к ПК/серверу, где
запущено приложение, и управляет сессией — как в OpenMCU: участники,
вызовы, муты, раскладка, запись, чат, устройства.

См. также [ADR-0001](ADR-0001-web-client.md) — почему это «в дополнение»,
а не «вместо» нативного клиента.

---

## 1. Как включить

### CLI

    # headless-сервер + web-панель на :8080
    python run.py --headless --web

    # свой адрес/порт/токен
    python run.py --headless --web --web-host 127.0.0.1 --web-port 9000 --web-token s3cret

    # выключить (перекрывает config)
    python run.py --headless --no-web

В логе появится строка вида:

    Web-панель: http://127.0.0.1:9000/ (host=127.0.0.1, port=9000)
    Откройте в браузере: http://127.0.0.1:9000/

### config.json

    "features": {
      "web": {
        "enabled": true,
        "host": "0.0.0.0",
        "port": 8080,
        "auth_token": ""
      }
    }

Приоритет: **CLI-флаг важнее config**.

### TLS (HTTPS) — по умолчанию ВЫКЛЮЧЕН

Панель работает по обычному **HTTP**. TLS специально не включён по умолчанию:
самоподписанный сертификат заставляет браузер показывать предупреждение,
что мешает подключению. Режим **переключается** — CLI, config или галочка
в GUI:

    python run.py --headless --web --web-tls            # HTTPS с авто-сертификатом
    python run.py --headless --web --web-tls \
        --web-cert /path/cert.pem --web-key /path/key.pem

    "features": { "web": { "tls": true, "cert_file": "", "key_file": "" } }

Если `cert_file`/`key_file` пусты — генерируется самоподписанный сертификат
через `openssl` в `~/.local/share/mcu-client/tls/` (модуль
`mcuclient/tls_utils.py`). В GUI — чекбокс **«TLS (HTTPS)»** в блоке
«Web-панель управления»; переключение на лету перезапускает сервер.

### Токен авторизации

* `features.web.auth_token` в config, или
* `--web-token` в CLI, или
* переменная окружения `MCU_WEB_TOKEN`.

Пусто = **без авторизации** (для доверенной локальной сети). Если токен
задан — API требует `Authorization: Bearer <token>` либо `?token=<token>`
в URL (страница сама подставит его в запросы и в EventSource).

## 2. Что умеет страница

* **Тайлы участников** с состоянием, мутами, признаком «говорит». Подсветку
  выставляют все, кто принёс медиа в веб-микшер: браузеры — по своим
  публикациям (`AudioMixSession`), H.323-терминалы — `H323AudioBridge` по PCM
  хоста `mcu_h323d`, SIP-вызовы — через `SipBridgeService`, который объявляет
  микшеру связь «канал `sip-<слот>` ↔ вызов ↔ участник»
  (`AudioMixSession.set_sip_level_targets`) после каждого переподключения слота
  и снимает объявление при остановке моста. Шкала у всех общая: `rms_percent`
  (`LEVEL_FULL_RMS`), затухание по одному порогу `LEVEL_STALE_MS_DEFAULT`
  (120 мс) — терминал гаснет по тому же правилу, что и браузер. Поля приходят в
  `participants[]` и `conference_participants[]` статуса как `speaking` и
  `volume_level` (проценты 0..100).
  *Ограничение честно:* объявление делает нативный мост `SipBridgeService`,
  поэтому на мок-SIP и на пути mediasoup (`push_sip_pcm_to_sfu`, §10) SIP-тайл
  по-прежнему отдаёт `speaking: false` и `volume_level: 0` — связи «слот ↔
  участник» в микшере там нет, а второго источника этой связи не заводят.
  Служебный суммарный канал `sip` (PCM всех вызовов сразу) участником не
  является сознательно: уровней и прав докладчика он не получает, но остаётся в
  миксе, и браузеры обязаны слышать терминал. Заметность задержки на панели
  ограничена ещё и опросом `/status` (своим интервалом), а не измерением.
* **Исходящий вызов** по SIP URI/IP.
* Принять / отклонить / сбросить вызов.
* Мут звука/видео участника, «Заглушить всех», «Сбросить всех».
* **Раскладка** (speaker / gallery_2x2 / gallery_3x3 / grid_auto).
* **Запись** конференции вкл/выкл.
* **Свои устройства:** камера, микрофон, «видео в эфир», демонстрация экрана,
  выбор камеры и источника видео (камера/экран/colorbar).
* **Чат** (SIP MESSAGE) — чтение истории и отправка всем.
* **Своё видео**: снимок локального источника в браузере — `GET
  /api/frame.png` (обновление ~2 к/с) или `GET /api/video.mjpeg`
  (MJPEG-поток, если доступен `cv2`). Это НЕ полноценный WebRTC —
  см. §7.
* Живое обновление: REST-опрос раз в 3 с + **SSE** (`/api/events`) на события
  шины движка (`call.*`, `chat.*`, `layout.*`, `engine.*`).

Страница — один файл `mcuclient/webui/index.html` (без внешних CDN и сборки),
работает и из собранного PyInstaller-бинарника (см. `build.py`, `--add-data`).

## 3. REST API

GET:

| Путь | Ответ |
|------|-------|
| `/api/status` | общий статус: room, pjsip, layout, layouts, recording, camera, microphone, video_send, screen_share, video_source, participants[], version, `sip_bridge`, `sip_ports`, `webrtc_sessions`, `conference_participants[]`. `conference_participants` отдаётся **тем же методом**, что и `GET /api/conference`, а не реестром напрямую: иначе состояние соединения считалось бы в одном маршруте и вралось в другом, а панель берёт участников именно отсюда (заперто `test_both_participant_routes_agree_on_state`) |
| `/api/participants` | `{participants:[...]}` — тот же SIP/H.323-ряд, что в `/api/status`. Человекочитаемая строка `label` несёт **русскую** подпись состояния (`[входящий]`, `[звонит]`, `[соединение]`, `[в разговоре]`, `[завершён]`) и флаги мутов; `idle` остаётся **без** подписи — это дефолт «вызова нет», а не состояние, и заглушка на нём была бы утверждением о состоянии, которого нет. До правки четыре состояния из шести давали один текст (голый URI), а `confirmed` подписывался латинским `[connected]` рядом с русским `[входящий]`: в списке Qt «аппарат звонит», «соединение идёт» и «вызов завершился» были неотличимы. Термины совпадают со словарём панели `STATE_LABEL` — один и тот же `CallState` показывают оба интерфейса (заперто `tests/test_models.py`) |
| `/api/chat` | `{messages:[...]}` |
| `/api/dtmf` | `{events:[...]}` | последние DTMF-тоны (`in`/`out`); панель читает их в журнал тонального автомата и обновляет по событию `dtmf.digits` |
| `/api/devices/video` | `{devices:[{id,name,driver,inputs,outputs}]}` |
| `/api/devices/audio` | `{devices:[{id,name,driver,inputs,outputs}]}` — панель показывает только устройства с `inputs > 0`: сервер отдаёт и динамики (`inputs=0, outputs>0`), а «микрофон», который ничего не захватывает, неотличим от сломанного МСУ; тот же фильтр держит нативный клиент (`mcuclient/ui.py`). Если поля `inputs` нет вовсе (часть сборок pjsua2 и тестовая фикстура), список остаётся полным — иначе панель показала бы «микрофонов нет» там, где они есть |
| `/api/layouts` | `{layouts:[...]}` |
| `/api/address` | адрес МСУ: `{uri, domain, host, host_source, port, dial_targets[], summary, ok, warnings[]}` — см. `docs/SIP_ADDRESSING.md` |
| `/api/codecs` | `{audio:[...], video:[...]}` кодеки с приоритетом |
| `/api/encryption` | `{srtp, web_tls, ...}` текущее шифрование |
| `/api/events` | SSE-поток событий шины |
| `/api/frame.png` | последний кадр источника, PNG (404, если кадров нет) |
| `/api/frame.jpg` | то же в JPEG (если есть cv2) |
| `/api/video.mjpeg` | MJPEG-поток (501, если нет кодировщика JPEG) |
| `/api/conference` | `{participants:[{id,name,kind,video,audio}], webrtc:bool}` — конференция и доступен ли WebRTC. Ряды веб-участников (`kind=web`) несут `state`: **`joined`** — вошёл в комнату, но ни одной живой медиа-сессии; **`connected`** — живая сессия есть (aiortc-публикация, просмотр или транспорт на mediasoup-sidecar); **`dropped`** — живая сессия БЫЛА и закрыта (обрыв, закрытие сервером или выдворение), т.е. это НЕ «ждём трек», а «человек отвалился и сидит в комнате тайлом». Приоритет: живое соединение проверяется первым, поэтому участник mediasoup не может быть показан отвалившимся (заперто `test_live_sidecar_beats_the_close_trace`). Авто-выдворения по этому признаку нет сознательно: у панели нет reconnect'а, и таймер выгнал бы браузер после короткого обрыва молча и навсегда. Значение вычисляет `WebSession.conference_participants`, а НЕ хранит реестр: `Conference` про WebRTC-сессии не знает физически (шина нужна `WebRTCManager`, реестр создаётся раньше), и прежнее `connected` было присвоенным себе утверждением, которое ни один код не подтверждал — `state` не присваивался ни разу за всю историю модуля (для сравнения: `role` и `volume_level` пишут). Заперто `tests/test_web_server.py`. **Как это видит оператор**: панель переводит состояние словарём `STATE_LABEL` (`joined` → «в комнате», `connected` → «подключён», `dropped` → «отвалился») и покрывает им также SIP-значения из enum `CallState` — один и тот же `<div class="state">` рисует оба набора. Перевод применяется ТОЛЬКО при отрисовке: развилка `p.state === 'incoming'` (кнопки «Принять»/«Отклонить») и классы тайла сверяют СЫРОЕ значение, иначе приём SIP-вызовов исчез бы молча. Пустое состояние остаётся пустым (заглушки нет), а НЕИЗВЕСТНОЕ рисуется как есть: панель обновляется чаще сервера, и проглотить новое состояние означало бы потерять признак тайла. Тайл с `dropped` дополнительно помечается классом `.dropped` (оранжевая рамка): слово в углу сетки из десятка тайлов оператор не читает. Заперто `tests/test_webui_participant_state_display.py` (6). **Счётчики кадров** (`video_frames`/`audio_frames`) того же ряда были вечно нулевыми: их увеличивает только `Conference.on_frame`, боевого вызова которого не было никогда (`git log -S conference.on_frame` — пусто, единственный вызов жил в `tests/test_webrtc_sfu.py`), т.е. это было поле-обманка. Сами поля реестра и этот метод удалены следующим срезом того же дня: ряд реестра и ответ `POST /api/conference/join` этих клавиш больше не несут вовсе, живые счётчики существуют только в обогащённом ряду и считаются шине), того же класса, что `remote` у сессий. Теперь их считает шина медиа (`video_version`/`audio_version`) — тот же источник, из которого `AudioMixSession.tick` берёт состав публикаторов и признак «говорит»; счёт по `sessions()` дал бы вторую истину о медиа (у зрителя без публикации он тоже растёт, и молчаливый наблюдатель выглядел бы говорящим). Семантика — ТЕКУЩИЙ канал, а не накопленное за участие: `bus.drop` убирает номер версии, поэтому после обрыва ряд показывает ноль. Пространства id разведены: SIP-мост льёт в ту же шину под `sip-<слот>`, поэтому кадры SIP-вызова не записываются веб-участнику. Считает то же место, что и `state`, — иначе `/status` и `/api/conference` разошлись бы (заперто `tests/test_web_server.py` (67)) |
| `/api/webrtc/sessions` | `{sessions:[...], webrtc:bool}` — живые WebRTC-сессии панели. Каждая сессия: `id`, `state`, `role`, счётчики кадров и **`participant`** — id участника конференции, которому она принадлежит, либо `null` для анонимного offer'а. Поле сознательно **не** взято из `publish_id` релея: у анонима тот равен id сессии (`webrtc-<N>`), и отдать его наружу означало бы показать «участника», которого нет в реестре, — выдворение с таким id вернуло бы штатное `{"ok": false}` (те же пространства имён id, что разведены в `/api/webrtc/offer`). Раньше вместо этого отдавалось поле `remote`, которое не присваивалось ни разу за всю историю модуля: наружу оно уходило вечно пустой строкой, т.е. «адрес неизвестен» выглядело штатным значением. Заперто `tests/test_webrtc_ingest.py` |
| `/api/web_recording` | статус записи веб-конференции (`{recording, file?}`) |
| `/api/mediasoup` | `{available, stats}` — состояние SFU-sidecar (`null`-статистика, если не поднят) |

| `/api/webrtc/close` | `{session}` | закрыть WebRTC-сессию панели; панель зовёт его при остановке публикации, отписке от участника и при закрытии вкладки — `sendBeacon`, токен в `?token=`. Отдельный вызов при выходе из комнаты не нужен: `conference/leave` закрывает сессии участника сам |
| `/api/web_recording` | `{enabled?}` | запись веб-конференции вкл/выкл/toggle (`WebRecorder`: кадры + аудио-микс) |
| `/api/conference/join` | `{name, role?}` | войти в конференцию из браузера (`role`: participant/presenter) |
| `/api/conference/leave` | `{id}` | выйти из конференции. Повторный выход — **штатный** `{"ok": false}` с HTTP 200, а не 404: участник уже вышел, а `sendBeacon` при закрытии вкладки дублирует запрос; поднять там ошибку означало бы показать alert человеку, который добился желаемого. Заперто `test_conference_leave_repeat_is_not_an_error`. Выход освобождает и **медиа**: закрываются WebRTC-сессии этого участника (публикация и просмотр) и его канал шины медиа. Браузер выгнанного не получает команды «закройся» мгновенно, и без закрытия серверной сессии его следующий кадр воссоздавал уже убранный канал — застывший PCM возвращался в микс остальных. Заперто `tests/test_web_leave_closes_ingest.py`. Сессии анонимных `offer` (без `participant`) выходом участника не закрываются: у них другие id. Сам beacon выхода панель шлёт при выгрузке вкладки **первым делом** слушателя `pagehide` — до раннего возврата «есть ли что закрывать»: участник живёт в реестре и без публикации, и beacon после того условия навсегда оставлял в комнате вошедшего без камеры. Заперто `tests/test_panel_leave_on_pagehide.py`. **Тем же маршрутом работает кнопка «Убрать» на чужом веб-тайле** (операторское выдворение): браузер, зависший после обрыва сети, beacon не шлёт в принципе, а `state` веб-участника о живости не сообщает ничего — единственное средство убрать такой тайл прямо сейчас есть у оператора с МСУ. Сервер сознательно **не** сверяет `id` с «тем, кто спрашивает» (у маршрута нет идентификации участника): заперто `test_conference_leave_accepts_someone_elses_id` — если различие «свой/чужой» появится однажды, кнопка станет всегда отказывающей, и правка обязана покраснеть здесь, а не молча сломать панель |
| `/api/conference/rename` | `{id, name}` | переименовать веб-участника. Нет такого id — **404 с причиной**, а не 200 + `{"ok": false}` (панель читает `error` только при `!res.ok`); пустое или пробельное `name` либо отсутствующий `id` — **400**. Панель зовёт его кнопкой «Имя» на тайле чужого браузера; отмена диалога имени на сервер не отправляется |
| `/api/conference/media` | `{id, video?, audio?}` | включить/выключить передачу медиа веб-участнику. Те же коды, что у `rename`: 404 на отсутствующего, 400 если не указано, что менять (оба `video` и `audio` опущены — менять нечего, а `ok: true` на пустом запросе было бы ложью). Панель зовёт его кнопками «Мут» и «Выкл видео» на том же тайле, всегда называя поле |
| — | — | **Важно про `id` в маршрутах конференции:** у веб-участника он строковый (`web-1`), числовой бывает только у SIP-вызова. `Number("web-1")` — это `NaN`, а в JSON — `null`, и сервер отвечает 400 «Некорректный participant id»: обработчик кликов по тайлам обязан читать id как есть, а число брать только для SIP-действий |
| `/api/mediasoup/join` | `{participant}` | войти в комнату SFU-sidecar (mediasoup) |
| `/api/mediasoup/leave` | `{participant}` | выйти из комнаты SFU; закрывает `WebRtcTransport` на сайдкаре (панель зовёт его и при закрытии вкладки — `sendBeacon`, токен в `?token=`) |
| `/api/mediasoup/signal` | `{action, participant, ...}` | сигнализация SFU (`createWebRtcTransport`, `connect`, `publish`, `subscribe` и т.п.) |

Ошибки: `{"ok": false, "error": "..."}` с HTTP-кодом (400/401/404/409/413/500).

## 4. Архитектура и потокобезопасность

 

`pjsua2` требует, чтобы каждый поток, трогающий API, был зарегистрирован
через `libRegisterThread`. HTTP-сервер многопоточный, поэтому **все**
обращения к движку (и чтение статуса, и команды) идут через
`EngineDispatcher.call(fn)` — очередь задач в одном потоке. Это исключает
гонки с pjlib и падения вида assertion.

Отдельная тонкость: часть публичного API `SipEngine` — это `@property`
(`layout`, `is_recording`, `video_send_enabled`, `screen_share_enabled`,
`recording_file`), а часть — методы. Web-слой читает их через хелпер
`_prop(...)`, который сам решает, вызывать или брать атрибут. Прямой вызов
`eng.layout()` для свойства бросает `TypeError` — и без хелпера значение
молча подменялось бы дефолтом (раскладка всегда «speaker», запись всегда
«выкл»). Регрессия закрыта тестом `tests/test_web_properties.py`.

Модули:

* `mcuclient/web_server.py` — HTTP-сервер, REST/SSE, `WebSession`,
  `EngineDispatcher`, `build_web_server`.
* `mcuclient/webui/index.html` — страница (HTML/CSS/JS, один файл).

## 5. Безопасность (честно)

* По умолчанию web-панель **выключена** (`features.web.enabled=false`).
* Без токена она **открыта всем, кто дотянется до порта** — это осознанно
  для локальной сети. В лог пишется WARNING.
* Наружу (в интернет) выставлять **только с токеном** и/или за реверс-прокси
  с TLS (включается `--web-tls`/галочкой в GUI). Токен передаётся в открытом
  виде по HTTP — для недоверенных сетей включайте TLS.
* API не имеет CSRF-защиты (страница и API на одном origin, без cookie).
  Не используйте в браузере с недоверенными вкладками на том же хосте.

## 7. Что пока НЕ сделано

* **WebRTC/SFU**: есть ingest + fan-out + **микширование аудио**; нет
  симулкаста, транскодинга SIP/H.323-видео в браузер.
* Есть **ingest** (браузер публикует свои
  камеру/микрофон в MCU, §8) и **снимок локального источника** для показа
  (`/api/frame.png`, `/api/video.mjpeg`). Удалённые участники в браузер
  не раздаются (нет SFU/TURN), звук участников в браузер не идёт.
  Полноценный WebRTC — отдельный крупный этап (см. ADR-0001, §5).
* WebSocket-сигналинг — нет, только REST + SSE.
* Многопользовательские роли/права — нет (один общий доступ по токену).


## 7a. Вход в конференцию из браузера (как в BBB) и SFU fan-out

Страница — не только панель администратора: любой участник открывает её,
вводит **имя** и присоединяется (форма входа). После входа браузер:

* **публикует** свою камеру/микрофон (`getUserMedia`) в MCU (ingest);
* **подписывается** на видео других веб-участников (fan-out): сервер отдаёт
  каждому зрителю отдельный исходящий видео-трек с шины медиа.

Участники бывают двух видов и видны в одной сетке тайлов:

| Вид | Источник | Видео в браузере |
|-----|----------|------------------|
| SIP/H.323 | pjsua2/H323Plus | через снимок локального источника |
| Веб (`kind=web`) | браузер (WebRTC) | прямой трек (fan-out) |

API конференции: `GET /api/conference`, `POST /api/conference/join` (имя),
`/leave`, `/rename`, `/media`. WebRTC: `POST /api/webrtc/offer` с
`role=publish|viewer` и `subscribe=[id,...]` для зрителя. Публикатору, который
хочет, чтобы его голос был подписан на id участника, надо передать
`participant` (id из `conference/join`): без него сессия получает собственный
канал `webrtc-<N>` — он не совпадает с id участника и живёт отдельно от
реестра конференции (сессия закрывается по `session`, участник — по `id`).

Ограничения: нет **симулкаста** и джиттер-буферов (полноценный SFU — дальше),
лимит 64 веб-участника. Запись веб-конференции есть (§9): `WebRecorder` пишет
кадры `FrameHub` и аудио-микс `AudioMixSession`. Зрители получают и видео, и
**аудио** других веб-участников (аудио-fan-out). TURN поддерживается (см. §7b).

### Оптимизации fan-out (latest-wins + общий кэш)

* **latest-wins:** трек-зритель отдаёт кадр, только когда публикатор выдал
  **новый** (по счётчику версий `video_version`/`audio_version`). Иначе на
  30 к/с слались бы дубликаты — лишний энкод и трафик.
* **общий кэш конвертации:** RGB->`av.VideoFrame` выполняется один раз на
  версию кадра (`MediaBus.shared_frame`) и переиспользуется всеми зрителями,
  а не N раз (по разу на зрителя).

Это снижает CPU и сетевую нагрузку при нескольких зрителях одного
публикатора. Мультикаст/симулкаст и джиттер-буферы — следующий этап.

## 7b. ICE-серверы (STUN/TURN) для WebRTC

По умолчанию WebRTC собирает только локальные (host) кандидаты — этого
достаточно в одной LAN. Для соединения **через интернет/NAT** нужен STUN
(и TURN, если прямой путь недоступен):

    "features": { "web": {
      "ice_servers": ["stun:stun.l.google.com:19302",
                      "turn:turn.example.com:3478?transport=udp"],
      "turn_user": "user", "turn_password": "secret"
    }}

Валидация принимает только `stun:`/`stuns:`/`turn:`/`turns:` URL; логин/пароль
подставляются к turn/turns-записям (`Config.web_ice_servers`). Пусто — только
LAN. TURN-сервер поднимается отдельно (coturn и т.п.) — это инфраструктура.
Готовый coturn лежит в репозитории: `docker/turn/`
(см. [docker/turn/README.md](../docker/turn/README.md)).

## 8. WebRTC-ingest (браузер -> MCU)

Фича **опциональна**: нужен пакет `aiortc`.

    pip install aiortc            # или: pip install -e '.[webrtc]'

Без него `mcuclient/webrtc_ingest.py` импортируется (флаг `WEBRTC_AVAILABLE
= False`), страница работает, а `/api/webrtc/offer` отвечает 503. Это
повторяет приём проекта с `pjsua2`: единственная точка импорта тяжёлой
зависимости + флаг доступности + тесты с фейком.

Поток данных:

    браузер (getUserMedia)
       └─ RTCPeerConnection ──offer──▶ /api/webrtc/offer
                                        └─ WebRTCManager (aiortc)
                                             └─ video -> FrameHub -> /api/frame.png
                                                audio -> приёмник

Раздача (fan-out): зритель подписывается на публикатора и получает его видео
и аудио-треки; аудио хранится как последний s16-кадр на шине.

Ограничения ingest: это **приём** в MCU (раздача — через fan-out); для
интернета/NAT настройте STUN/TURN (§7b); аудио **микшируется**: каждый
зритель получает **один смешанный аудио-трек** (голоса всех, кроме
себя) через `AudioMixSession`; видео — по треку на публикатора.

## 9. Запись web-конференции

`WebRecorder` (`mcuclient/web_recorder.py`) пишет именно конференцию, а не
экран сервера: **видео** — кадры `FrameHub` через FFmpeg (`-f rawvideo`),
**аудио** — смешанный поток `AudioMixSession.record_mix()` в WAV (stdlib).
Управление: `POST /api/web_recording {enabled?}` (toggle), статус —
`GET /api/web_recording` и поле `web_recording` в `/api/status`; кнопка
«Запись веб» на странице. Файлы — в `features.recording_path`.

## 10. SFU mediasoup (симулкаст, масштаб) — опционально

Кроме встроенного SFU-lite на `aiortc` есть **опциональный внешний SFU** на [mediasoup](https://mediasoup.org/) (`mediasoup-sidecar/` — Node.js сервис с C++ worker'ами). Он даёт **симулкаст** и **масштаб** на несколько worker'ов, которых у `aiortc` нет.

* Включается в `features.web.mediasoup.enabled` (по умолчанию **выкл**);  при старте приложение поднимает сайдкар дочерним процессом  (`mcuclient/mediasoup_supervisor.py`) и общается с ним по HTTP  control API (`mcuclient/mediasoup_client.py`). Медиа идёт по RTP,  через API — только управление.
* Требует **Node.js ≥ 20** и открытый диапазон UDP `rtc_min..rtc_max`  (по умолчанию 40000-40100); для интернета — `announced_ip` и TURN.
* Control API: `/health`, `/rooms`, `/rooms/close`, `/rooms/stats`, `/transports/webrtc|plain|close`, `/transports/connect`, `/produce`, `/produce/plain`, `/consume`, `/consumer/set-layers` (симулкаст), `/producer/request-keyframe`. Полный перечень и тела — в `mediasoup-sidecar/README.md`; таблица дока сверяется с кодом тестом `tests/test_sidecar_api_paths.py`.
* **Закрыть один транспорт.** `POST /transports/close` обязаны вызывать каждый
  отказ RTP-моста от уже созданного `PlainTransport` (`stop()` и откат
  `produce_plain`). Без него транспорт освобождается только вместе с комнатой и
  всё это время держит UDP-порт из `rtc_min..rtc_max` (по умолчанию
  40000-40100 = 101 порт), а повторные попытки поднять мост накапливали бы их
  до исчерпания диапазона.
* **Отказ mediasoup ≠ «выключено».** При `enabled: true` и недоступном сайдкаре
  `GET /api/status` отдаёт `mediasoup_rtp: {started: false, reason: ...}`, а не
  `None` (`None` — только когда режим выключен оператором); те же тексты
  доезжают в 503 ответов `/api/mediasoup/*`, поэтому браузер видит настоящую
  причину, а не «не включён». Повторная попытка достучаться до сайдкара — не
  чаще раза в 10 с: мост дёргается на каждый аудиокадр, и повтор без троттла
  вылился бы в шторм запросов к control API.
* **Одна команда для SFU-стека** (mediasoup + coturn): `cd docker/sfu &&
  cp .env.example .env && docker compose up -d --build` — см.
  `docker/sfu/README.md`.
* Запуск/проверка сайдкара: `cd mediasoup-sidecar && npm install &&  npm run smoke`.
* Это **дополнение**, а не замена: базовый `aiortc`-SFU (микс, запись,  мост SIP↔WebRTC) продолжает работать без Node.

## DTMF (тоны набора)

Аппаратные терминалы и телефоны (Polycom, Yealink, ISDN-шлюзы) передают
номер зала, PIN и сигналы IVR **только** DTMF, поэтому МСУ обязан их
принимать и отправлять:

* приём: `onDtmfDigit` / `onDtmfEvent` → событие `dtmf.digits`
  (`digits`, `direction=in`, `participant_id`, `peer`, `method`) и в
  историю, отдаётся `GET /api/dtmf`;
* отправка: `POST /api/dtmf` или `engine.send_dtmf(digits, id=None)`.
  Без `id` тоны идут всем активным вызовам — так правильно «набрать PIN
  в IVR для всего зала»;
* в панели для этого есть **тональный автомат** (секция «Тоны набора»):
  16 кнопок (0–9, `*`, `#`, A–D — буквенные тона шлют ISDN-шлюзы и старые
  Polycom), выбор адресата из списка вызовов и журнал последних посылок.
  Веб-участник в адресаты не попадает: у него нет вызова, сервер ответил бы
  409 «нет активного вызова».

Значения `method` зависят от протокола вызова, а не от настройки:
`rfc2833` / `sip-info` — SIP, `h323` / `h323-string` — H.323 (H.245 UserInput,
см. `docs/H323_STATUS.md`). Для H.323-участника `method` панели не нужен:
`engine.send_dtmf` роутит его на хост `mcu_h323d` сам, потому что объекта
pjsua2-вызова у него нет и SIP-путь для него бессмыслен.

Метод по умолчанию `auto`: RFC 2833, при ошибке SIP INFO. Только
RFC 2833 — и старый шлюз не услышит тоны; только SIP INFO — не услышит
половину парка Polycom.

Журнал комнаты — ОДИН на оба протокола (`DtmfService`): принятый с аппаратного
терминала PIN виден там же, где и тон, набранный SIP-телефоном. Второй журнал
для H.323 означал бы два расходящихся списка «МСУ принял тоны».
