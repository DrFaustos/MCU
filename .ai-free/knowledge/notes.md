# Заметки (проверенные факты проекта)

## IPC `mcu_h323d`: обрыв сокета обязан быть событием, а не тишиной

Клиент `H323dClient` при разрыве только снимал `_running` и писал в лог —
подписчики не получали НИЧЕГО. `H323Endpoint` продолжал держать вызовы
мёртвого хоста как живые: фантом в `CONFIRMED` в комнате и в буфере микшера,
web-панель показывала действующее соединение, `hangup` из панели уходил в
закрытый сокет. `call.disconnected` при смерти процесса (`kill`, OOM) не
приходит НИКОГДА.

Правило: разрыв без нашего `close()` — это `H323dEvent("connection.closed")`.
Намеренная остановка событием НЕ считается, потому что `close()` снимает
`_running` ДО закрытия сокета (иначе ложная тревога на каждом `stop()`).
Зачистка нужна в двух местах: у эндпоинта — `_on_host_lost()` c
`notify_host=False` (мёртвому сокету `call.hangup` не отменяет вызов, но
пачкает лог «не доставлен»), у аудио-моста — `forget_all()`, который НЕ
отписывает мост от событий: владельцем соединения остаётся эндпоинт, иначе мост
терял медиа до перезапуска хоста без единой ошибки.

`mcuclient/h323_host.py` (`H323HostClient`) — второй клиент того же хоста, с
тем же молчанием при обрыве; комнатой не владеет, фантомов не плодит, поэтому
не правился.

Проверка: `tests/test_h323d_client.py::test_host_crash_emits_connection_closed`
и `test_intentional_close_is_not_reported_as_drop`, далее по эндпоинту и мосту
(`test_host_lost_*`).

## DTMF: очередь тонов pjsip не работает без потоков lib

pjsua2 поднят с `threadCnt = 0`, поэтому pjsip **не разыгрывает внутреннюю
очередь тонов**: `Call.sendDtmf("1984#")` и `Call.dialDtmf("1984#")` доносят
**только первый тон** и делают это молча (без исключения).

Единственный рабочий способ — отправлять символы **по одному** и между ними
крутить `libHandleEvents()` (тот же pump, что использует GUI/headless-цикл).
Реализация: `mcuclient/dtmf_service.py`, константы `DTMF_PUMP_STEP_SEC` /
`DTMF_PUMP_TIMEOUT_SEC`; `pump` инжектится через конструктор (в тестах — фейк).

Проверка: `scripts/testbed/run_two_instance_dtmf_test.sh` →
`[+] DTMF MCU<->MCU OK`, `DTMF приняты: 1984#`.

**Грабль с тестами:** unit-тесты этот баг не поймали, потому что фейк `Call`
принимал **любую** строку тонов. Фейк обязан повторять ФОРМУ и СЕМАНТИКУ API
(сколько вызовов, каким методом), иначе «зелёные» тесты врут — баг жил только в
бою.

## Стендовые скрипты: нельзя ждать через time.sleep

PJSIP с `threadCnt = 0` разбирает пакеты **только** пока кто-то зовёт
`libHandleEvents()`. В стендах ждать события нужно исключительно
`scripts/testbed/lib/pump.py::pump(engine, timeout, pred)` — иначе «звонок
MCU<->MCU» не проходит никогда (INVITE лежит в буфере сокета). `pump` заодно
регистрирует текущий поток в pjlib: без этого вызов PJSIP API из «чужого»
потока завершает процесс assertion'ом.

## Предсуществующий краш: второй start/stop SipEngine в одном процессе

`terminate called after throwing an instance of 'pj::Error'` → `Aborted (core dumped)` на **втором** `SipEngine.start()/stop()` в одном Python-процессе. Проверено на базовой линии (`git stash`) — воспроизводится БЕЗ каких-либо правок, т.е. это не регрессия.

Минимальное воспроизведение (без сети): `SipEngine(cfg).start(); process_events(0.2); stop()` дважды → abort. Чистый pjsua2 (`libCreate/libInit/transportCreate/libStart/libDestroy` дважды в одном процессе) — **не** падает, значит дело в объектах, которые держит движок (director-классы Call/Account).

Практические следствия:
* стенды и e2e-проверки: ОДИН движок на процесс, для второго сценария — новый процесс;
* скрипты, дёргающие реальный `start()`, должны завершаться через `os._exit(rc)`;
* `pytest tests/` «висит» после 100% по этой же причине (teardown pjsua2) — не связано с конкретным модулем.

## Адрес МСУ: mcuclient/sip_address.py — правила

Вся логика «как нас набирают» (домен/IP/порт/user) собрана в `mcuclient/sip_address.py` — чистые функции без pjsua2/Qt, покрыты `tests/test_sip_address.py`. GUI (`ui.py`), web (`POST /api/address`) и `config.set_sip_address()` обязаны использовать **одну** нормализацию (`normalize_domain`, `sanitize_sip_user`), иначе три входа разойдутся.

Правила, зафиксированные тестами:
* пустой домен — НЕ ошибка: это режим «звонок по IP», `ok=True`, хост берётся из `domain → nat.public_address → listen(≠0.0.0.0) → IP машины` (`host_source="auto"`);
* голый IPv6 из поля «домен» получает обязательные скобки (`2001:db8::1` → `[2001:db8::1]`); та же скобка нужна в `build_id_uri` — обычная чистка `[^A-Za-z0-9._-]+ → '-'` убивает линию на CUCM/Voisica молча;
* **порт из адреса («mcu.corp:5065») доезжает только в URI, в `sip.port` не пишется** — иначе MCU оглохнет на 5060, а в Contact порт пропадёт. Порт берётся из строки ДО `normalize_domain` (он порт режет);
* `sips:` без порта = 5061; стандартный порт схемы в URI не пишется;
* `dial_targets` всегда содержит IP-вариант (в закрытом контуре без DNS это единственный способ дозвониться); `to_dict()` обязан отдавать `uri`, `ok`, `summary` — их читают Qt (`data.get("uri")`) и web (`a.summary`).

Docs: `docs/SIP_ADDRESSING.md`.

## Teardown pjsua2: держать ссылку на Call недостаточно — нужен `__disown__`

Деструктор SWIG-обёртки `pjsua2.Call` зовёт `pjsua_call_set_user_data(call_id, NULL)`,
а та проверяет `call_id < pjsua_var.ua_cfg.max_calls`. После `libDestroy()`
`ua_cfg.max_calls == 0` → assertion для ЛЮБОГО завершённого вызова → SIGABRT
(rc=134) уже после того, как всё завершилось корректно. `_CALL_KEEPALIVE`
(«просто держать ссылку») не спасает: при завершении интерпретатора модульные
переменные очищаются, список освобождается и деструкторы отработают.

Правильно: `mcuclient/sip_engine.py::_park_call(call)` — сначала `call.__disown__()`,
затем `_CALL_KEEPALIVE.append(call)`. Вызывается из `_drop_participant()` и
`stop()`. Регрессии: `tests/test_call_parking.py` (в т.ч. ветка без `__disown__`
для pybind11-сборок). Проверка в стендах: rc обязан быть 0, а не 134.

## sipp-статистика: читать накопленную (последнюю) колонку

sipp печатает `Successful call`/`Failed call` с ДВУМЯ числами — «за последний
интервал» и «накопленное» (`Successful call | 0 | 1`). Регулярка «первое число»
(`re.search(r"Successful call[^\d]*(\d+)")`) возвращает 0 из первой колонки —
стенд выглядит упавшим при полностью успешном вызове. Берём ПОСЛЕДНЕЕ число
строки: `scripts/testbed/verify_registration.py::_sipp_stat()`.

## Тестовый раннер tests/_runner.py: обязательная точка проверки не имеет права врать

`docs/AI_CONTEXT.md` §4 требует перед коммитом гонять `python3 tests/_runner.py`,
но раннер передавал только `tmp_path`. Итог на 2026-10-08: 9 «FAIL» с
`TypeError: missing 1 required positional argument` (monkeypatch, parametrize)
при зелёном pytest, и молча не собранные 30 файлов — 733 кейса вместо 987.
Правильное направление правки — расширять раннер (monkeypatch с откатом,
parametrize, skipif/skip, pytest.skip/importorskip, `--collect-only`), а не
переписывать тесты под его ограничения.

Грабли:
* pytest 9.1: `Skipped.__module__ == 'builtins'` (MRO: Skipped →
 OutcomeException → BaseException). Распознавать пропуск надо по имени класса в
 `type(exc).__mro__`, не по `__module__`; `except Exception` его не видит вообще,
 и честный пропуск вешает весь прогон.
* покрытие сверять `--collect-only` с обеих сторон — иначе потерянные файлы не
 видны ни в каком выводе.
* счётчик кейсов читать из ФАЙЛА лога, а не из `cat` в terminal(): native-лог
 pjsua2 и лимиты вывода обрезают текст, и казалось, что раннер потерял треть
 набора (было 987, «виделось» 733).

Регрессия: `tests/test_test_runner.py` (14) — семантика раннера на пробах в
tmp_path, гоняется и pytest'ом, и самим раннером.

## H.323-хост: «вызов установлен, а звука нет» — три независимые причины (2026-10-08)

Сигнализация (Q.931/H.225) проходит и при полностью выключенном медиа, поэтому
её зелёный прогон ничего о звуке не говорит. Проверено стендом
`scripts/testbed/h323_native_two_hosts.py` (тон 800 Гц → RMS):

1. **Пустая таблица возможностей.** Конструктор `H323EndPoint` кодеки НЕ
   выставляет — в нём только `autoStart*Audio = TRUE` (`h323ep.cxx:674`).
   Обязателен явный `endpoint.AddAllCapabilities(0, P_MAX_INDEX, "*")` (как в
   эталонном `samples/simple/main.cxx:449`), иначе H.245 не соглашает ни одного
   аудио-канала и `OpenAudioChannel` не вызывается вообще. В хосте сразу снимаем
   видео: `RemoveCapability(H323Capability::e_Video)`.
2. **Decoder-канал обязан держать реальное время.** В приёмном цикле
   (`src/channels.cxx`, ReceiveThread) прямо сказано, что `Write()` обязан
   выполняться ~20 мс на кадр, «иначе jitter buffer не будет работать». Базовый
   `PSoundChannel` блокируется естественно; ring-канал возвращался мгновенно →
   приёмный тред выкачивал RTP разом: 1 048 576 вызовов `Write` за 3 с, 245 МБ
   WAV-дампа, RMS размывался тишиной. Лечится пейсингом по `steady_clock`
   (`McuPcmChannel::Pace()`), с переносом срока при отставании (не догоняем).
3. **`Ring::write` писал в `buf_[head_ + size_]`, двигая при этом `head_`.**
   Двойной сдвиг → индекс за границу `std::vector` → порча кучи: `free():
   invalid pointer` / SIGSEGV обоих хостов. `head_` УЖЕ «слот записи», писать
   надо в `buf_[head_]`. Этот путь не исполнялся НИ РАЗУ, пока не открылось
   аудио, поэтому баг дожил до первого реального RTP.

Ещё две находки того же прогона:

* **WAV-заголовок в `pcm.hpp` был бит**: `memcpy(header + 8, "WAVEfmt ", 4)`
  копирует 4 байта, т.е. пишет только `WAVE`, а тег `fmt ` в смещении 12
  остаётся нулевым → `wave.open()` отвечает «data chunk before fmt chunk» на
  ВСЕ дампы. Нужно два `memcpy`: `header + 8` = `"WAVE"`, `header + 12` = `"fmt "`.
* **`cmd == "pcm.out"` стоял ПОСЛЕ `emit_error("неизвестная команда")`** и без
  `return` перед ним: каждый PCM-кадр (50/с) рождал ошибку. Ветки команд обязаны
  стоять до финального `emit_error`.

Диагностика темпа, которая это нашла: счётчики вызовов `Read`/`Write` в
`McuPcmChannel` (`PCM-TRACE` в логе, включается `--verbose`) — «канал открыт»
≠ «медиа идёт в реальном времени».

## AudioMixer: id участника — ParticipantId = Union[int, str] (2026-10-09, h323)

* `AudioMixer` хранит и сравнивает id, но никогда их не арифметит, поэтому тип
  id объявлен `ParticipantId = Union[int, str]`: SIP/H.323-слой и `mcu_core`
  зовут его числами, веб-слой (`MediaBus`, `AudioMixSession`,
  `SIP_PUBLISHER_ID`) — строками. Пока аннотация была `int`, mypy давал 5
  ошибок в `webrtc_sfu.py` (`set_buffer`/`remove`/`mix_for`/`participant_ids`) —
  то есть веб-микшер был типизирован «в красном» наборе.
* `AudioMixSession.active_publishers()` обязан сузить тип явно
  (`isinstance(pid, str)`), а не кастом: `participant_ids` микшера шире, чем
  живущие в нём веб-публикаторы.
* Внутри цикла `tick()` переменная, итерируемая по `participant_ids`, названа
  `buffered`, а не `pid`: `pid` уже имеет тип `str` из цикла по `publishers()`,
  и mypy отвергал повторное присваивание другого типа (`[assignment]`).
* Остались 3 предсуществующие ошибки mypy (замер на копии HEAD — 8): две —
  присваивание `ndarray` другого dtype в `resample_mono`, одна — Unused
  "type: ignore" при `warn_unused_ignores = True`. Это НЕ дефект микшера.
* Наборы «строгой типизации» сведены проверкой
  `test_strict_typing_sets_do_not_drift_apart` (three-way: секции `mypy.ini` с
  `disallow_untyped_defs`, strict-шаг `ci.yml`, `STRICT_MODULES` в

  можно только через явный `STRICT_SET_AHEAD` — иначе CI зелёный, а строгость не
  применяется.

## CI-окружение — часть воспроизведения: локальный зелёный прогон ничего не доказывает (2026-10-09, h323)

* CI (`lint-and-test`) ставит ТОЛЬКО `pytest pytest-cov ruff` — ни pjsua2, ни
  numpy, ни mss. На машине разработчика они стоят, поэтому тест, тайно
  зависящий от нативного биндинга, зелёный локально и красный в CI. Рецепт
  repro: `python3 -m venv <tmp>/cienv && <tmp>/cienv/bin/pip install pytest` и
  гонять pytest + `tests/_runner.py --collect-only` этим python'ом. Тот же
  изолированный venv нужен и для mypy/ruff: PEP 668 не даёт ставить пакеты в
  боевой `/usr/bin/python3`.
* **Коллекция ≠ план исполнения.** `--collect-only` обязан считать и кейсы под
  активным `skipif`: pytest их собирает, а помечает пропуском только на
  запуске. В мини-раннере ветка skipif стояла до печати `COLLECT`, и мера
  отставала на каждый активный skipif-кейс (в CI — 2 кейса
  `test_sip_interop.py`: «1067 vs 1069», ранее «1020 vs 1022»). Локально — 0
  расхождений, дефект невидим.
* Падение по отсутствующему биндингу маскировалось неделями, потому что
  защищённые тесты имели `if pj is None: return`, а незащищённые полагались на
  «зелёную машину разработчика». Правило: либо явная подмена биндинга
  (`monkeypatch.setattr(se, "_pj", _FakePj)`), либо явный skip — иначе тест
  проверяет состав окружения, а не контракт.
* Фикс CI-красного подтверждается прогоном на GitHub (`gh run watch <id>
  --exit-status`), а не локальным pytest: локально тот же набор был зелёным до
  и после правки.
* После добавления теста в файл, на который есть ссылка «`файл.py` (N)»,
  отставание ловит сам страж (`test_cited_case_counts_match_the_runner`) —
  править надо обе точки: `docs/AI_CONTEXT.md` и база знаний.

## PCM16: усечённый кадр (нечётное число байт) глушил всю конференцию молча (2026-10-10, h323)

* **Симптом.** Два H.323-терминала через микшер MCU замолкают в обе стороны,
  вызовы остаются `CONFIRMED`, в логе — ни строчки. Не «пропал звук у одного»,
  а молчит вся комната.
* **Причина.** `numpy.frombuffer(pcm, int16)` и `array.array("h").frombytes()`
  бросают `ValueError` на буфере с нечётным числом байт. Микшер длину не
  проверял: `set_buffer` принял битый кадр, и с этой минуты падает **каждый**
  следующий кадр ЛЮБОГО канала — первым цепляется `rms_level` (его зовёт
  `_active`/`_mix_ids` на всех буферах), затем `mix_for`. Один битый фрейм
  выключал аудио до перезапуска.
* **Где берётся усечение.** Оборванный `pcm.in`, битая граница newline-IPC,
  любой внешний вызывающий: `mcu_core` и `webrtc_sfu` зовут микшер напрямую.
* **Правка (в корне, а не у вызывающего).** `audio_mixer._even_pcm()` режет
  висячий байт; `_to_int16_array()` обрезает (закрывает `rms_level` и обе ветки
  суммирования), `set_buffer()` хранит только чётный буфер.
* **Грабля двух веток.** `webrtc_sfu.resample_mono()` в pure-Python ветке хвост
  резала (`pcm[:len-len%2]`), а в numpy-ветке ловила `ValueError` под
  `except Exception: return b""` — то есть один и тот же кадр давал **молчаливую
  тишину ровно на машинах с numpy** и нормальный звук без него. Любая правка
  медиа-кода обязана проверять обе ветки: в тестах это `mod._np = None` +
  сравнение результата с numpy-версией.
* **Регрессии** (7 кейсов): `tests/test_audio_mixer.py` (44) — RMS с хвостом,
  `mix` не падает, `mix_for` не глушит собеседника, та же сумма без numpy;
  `tests/test_h323_audio_bridge.py` (35) — усечённый `pcm.in` не глушит комнату
  и следующий кадр проходит; `tests/test_resample_fallback.py` (5) — усечённый
  кадр не пустота, обе ветки согласованы.
* **Мера числа кейсов моста** живёт в `docs/H323_STATUS.md` (22, с 2026-10-10 — 35) — правится
  вместе с тестом, иначе краснеет `tests/test_doc_values.py`.

## Фасад, державший свои копии комнаты и порога (2026-10-10)

- **Как искали.** AST-зонд «поле `self.X` пишется, но не попадает ни в одну
  dict-проецию» дал двух кандидатов. Оба ложны, и полезно знать почему:
  `base_url/timeout/token` — конфиг клиента, а `audio_mix/conference/...` —
  ссылки на дочерние сервисы. Второй, узкий зонд (поля `@dataclass` со `Stats`
  вне всех dict-проекций) дал `McuStats.active_audio/speaker_id` — и это тоже
  ложное срабатывание: dataclass отдаётся наружу целиком, проекции, из которой
  поле теряется, у него нет. Правилу «stats обязан проецировать всё» подлежат
  только словари, отдаваемые вручную (`audio_stats()`), а не dataclass-и.
- **Настоящий дефект оказался рядом и другие.** `McuCore` (комната <-> микшер
  <-> видеостена) держал СВОЮ копию состояния: `self._levels` + буферы микшера
  как список участников и литерал `1.0` как порог «говорит».
- **Комнату нельзя копировать.** `Room.remove()` наблюдателей не извещает: без
  сверки с комнатой на каждой точке входа ушедший терминал оставался в звуке
  (`mix_all()`), в `active_audio` и в докладчиках. Тот же класс фантомов, что
  закрыт в `h323_endpoint` при смерти хоста `mcu_h323d` — признак, что чинить
  надо в общем слое, а не у вызывающего.
- **Литерал порога переживает любую настройку молча.** Микшер решает по
  `config.silence_rms`, фасад сравнивал с `1.0`: при `silence_rms=500` фасад
  продолжал считать докладчиком канал уровня 100. Порог одного признака обязан
  браться из конфига того же микшера, что суммирует PCM (см. также
  «индикатор один на двух продюсеров» выше).
- **Знак сравнения — часть контракта.** `vwall.active_speaker_by_level` имел
  `>`, `AudioMixer` — `>=`: канал ровно на пороге микшер считал голосующим, а
  раскладка `speaker` его не видела. Плюс при равных уровнях надо брать ПЕРВОГО
  по обходу (`max()` в микшере даёт именно первого из равных), иначе подсветка
  и звук расходятся по ячейкам.
- **Дефолт `0.0` у необязательного числа = «тишина».** `on_audio(level=0.0)`
  терял докладчика на громком PCM без единой строки в логе. Для «нет данных»
  нужен `Optional[float] = None` с вычислением из PCM (`rms_level`).
- **Зонд полезнее, чем результат.** `McuCore` в рантайме не вызывается ниоткуда
  (grep по пакету/`run.py`/`daemon/`/webui даёт только тесты и комментарии):

  чтобы в них не плодить вторую копию общей логики перед подключением (Этапы

## Канал в миксе ≠ канал, имеющий право светиться (2026-10-10)

- **Симптом.** Веб-конференция: браузер говорит, тайл не подсвечивается — но
  только пока активен аудио-мост SIP<->веб. Ошибок в логе нет, `volume_level` на
  панели настоящие.
- **Корень.** Индикатор выбирал докладчика по **всем** публикаторам шины, а в
  шине есть служебный канал `SipWebAudioBridge.SIP_PUBLISHER_ID = "sip"` —
  суммарный PCM всех SIP-терминалов. Участника с таким id в `Conference` нет:
  `speaker = "sip"` -> `update_levels` не находит адресата -> `is_speaking=False`
  у всех, включая реально говорящего.
- **Правило.** «Участвует в миксе» и «может быть докладчиком» — разные
  предикаты. `LevelsIndicator.update(..., eligible=...)` обнуляет не-eligible
  каналы **только в снимке для выбора**; `levels()` наружу обязан остаться
  честным для всех (браузеры должны и слышать терминал, и видеть его
  громкость). `eligible=None` = прежнее поведение: у H.323-моста каждый канал и
  есть участник, второе множество ему не нужно.
- **Контракт реестра.** `Conference.participant_ids()` — «у кого есть тайл».
  Без него вызывающий обязан лезть в приватное поле реестра, и право быть
  докладчиком начали бы выдумывать по месту.
- **Враньё в справочнике было важнее кода.** `docs/WEB_CONTROL.md` обещал
  подсветку «для обоих типов участников» и приписывал SIP-ветку продюсеру
  `H323AudioBridge`. Факт: у SIP продюсера уровней нет вообще (`AudioMixer` /
  `rms_level` по `sip_*.py` — пусто), SIP-тайл всегда `speaking=false`.
- **Почему SIP чинится не здесь.** `SipBridgeService._on_frame(pcm, rate,
  channels)` — колбэк pjsua2-порта идентичность вызова НЕ передаёт, а портов
  столько же, сколько вызовов: мерить пер-вызовный level нечем. Нужно менять
  контракт порта (порт -> id вызова), это отдельная задача, а не правка
  индикатора.
- **Что зафиксировано, но не исправлено.** `Room.active_speaker()` и режим
  `speaker` в `layout_service` берут ПЕРВОГО `is_speaking` по обходу, а не
  громчайшего. Сегодня не врёт: в `Room` продюсер флага один, веб-участники
  живут в отдельной `Conference` (`room.add` зовётся только из `call_registry`).
  Расхождение появится вместе с SIP-продюсером — тогда главным окажется тот, кто
  первым попал в словарь.
- **Регрессии:** `tests/test_audio_mixer.py` (44) — `eligible` ограничивает

## Микшер тушил мёртвый канал только в подсветке, в миксе он жил вечно (2026-10-10)

- **Симптом.** Терминал или браузер замолчал навсегда (обрыв RTP, смерть
  процесса, вкладка закрыта без `close_session`), а его последний кадр
  продолжает звучать У ВСЕХ участников. Замерено пробой живьём ДО правки:
  через 1.5 с после последнего кадра `record_mix()` отдавал амплитуду 3000,
  `publishers()` — `['sip']`. Панель при этом показывала «не говорит».
- **Корень.** `AudioMixSession.tick()` вычислял карту `fresh` (выросла ли
  версия кадра шины) и честно тушил по ней `LevelsIndicator`, но `set_buffer()`
  клал для ВСЕХ публикаторов шины. Подсветка и слышимый голос считались от
  РАЗНЫХ предпосылок — поэтому дефект был молчаливым: «говорит» гас, звук
  оставался в миксе бессрочно.
- **Правка.** Затухание в самом микшере по тому же порогу: `tick(now=None)`
  берёт `time.monotonic()` ОДИН раз на тик и передаёт его и `mark()`, и
  `LevelsIndicator.update(now=...)`; новый `LevelsIndicator.is_stale()` —
  публичный именно затем, чтобы продюсер гасил канал по СУЩЕСТВУЮЩЕМУ штампу.
  Своего второго счётчика времени у микшера нет намеренно.
- **Грабля №1 (порог — не ноль).** Глушить по признаку «в этом тике нового
  кадра не было» нельзя: публикация и тик идут одним шагом (20 мс) и законно
  разъезжаются по фазе — живой поток заглох бы через тик (инвариант
  `test_living_stream_does_not_blink_between_ticks`).
- **Грабля №2 (затухание != глушение).** Обязан работать возврат: поток
  возобновился — канал снова в миксе и со своей громкостью. Без этого кейса
  правка «в одну сторону» тихо ломала вызовы с кратковременной потерей звука.
- **Грабля №3 (время — параметр, а не sleep).** Детерминизм без
  `time.sleep(порог)`: `tick(now=0.5)`. Тот же приём, что с `level_stale_ms=-1`
  и `LevelsIndicator(stale_ms=-1.0)`.
- **Что НЕ чинить точечно.** `drop("sip")` по таймеру был бы masking-фиксом: у
  мёртвого источника события «поток иссяк» не бывает в природе (терминал положил
  трубку — UDP просто молчит, RTP-мост никто не останавливает). Чинится класс:
  ЛЮБОЙ канал шины без парного `drop` обязан затухнуть в миксе.
- **Регрессии:** `tests/test_audio_mix_session.py` (24) —
  `test_stale_channel_fades_out_of_the_mix_not_only_the_spotlight` (50 мс —
  живой поток не тронут; 500 мс — канал убран, микс = тишина) и
  `test_channel_revives_when_its_stream_resumes`. RED до правки: падали ровно
  они.

## Битрейт SIP-вызова: чем его НЕЧЕМ измерить (замерено живьём) (2026-10-10)

- **Симптом.** `/api/status` -> `participants[].rx_kbps = 0`, `tx_kbps = 0` при
  активном звонке. Оператор читает это как «медиа нет». `docs/ARCHITECTURE.md`
  обещал, что участник хранит «выбранные кодеки и битрейты».
- **Корень.** `Participant.rx_bitrate_kbps/tx_bitrate_kbps` существовали с
  самого первого коммита как `int = 0`, писателя у них не было никогда; web-
  панель прокинула их в API при создании (`f4b5962`). Ложный ноль, а не дыра.
- **Замер живьём (pjsua2 2.16, стенд двух процессов, MCU<->MCU, G.711):**
  `rtcp.rxStat.bytes/txStat.bytes` заполняются, но это счётчики RTCP-канала:
  за 24.7 с — 1.5 / 2.0 кбит/с вместо ~64 на направление; `rxPkt` +1 пакет за
  2 с вместо ~50/с; `updateCount` растёт ступенями. Считать по ним битрейт =
  выдавать правдоподобное враньё.
- **Готового источника в сборке нет:** у `AudioMedia`/`VideoMedia` поля битрейта

  медиа-битрейта нет ни одного. Единственный честный путь — свой счётчик байт
  RTP на вызов (контракт pjsua2-порта, а не индикатор/проекция).
- **Правило (уже второе применение).** Для «нет данных» у числового поля обязан

- **`_opt_int` из `web_server.py` для исходящих проекций не годится** — он для
  ВХОДЯЩИХ параметров и бросает `ApiError`; чтение статуса падать не имеет

## Аудио-мост: один публикационный id на все вызовы (2026-10-10)

- **Симптом.** На двух SIP-терминалах в конференции с браузерами: терминалы не
  слышат друг друга (в вызов уходит тишина), браузеры после завершения звонка
  продолжают слушать застывший голос терминала (фантом).
- **Корень.** Все SIP-вызовы публиковали PCM в `MediaBus` под ОДНИМ служебным
  id `sip` (`SipWebAudioBridge.SIP_PUBLISHER_ID`). Два следствия: кадры
  вызовов затирали друг друга (в шине остаётся последний принятый), и
  `mix_excluding("sip")` вычитал разом оба вызова. Плюс канал никогда не
  вычищался, а `MediaBus` держит последний кадр до `drop` и микшер берёт состав
  публикаторов из шины → фантом завершённого терминала.
- **Правка.** `channel_of(slot)` → `sip-<слот>`, канал доезжает до приёмника
  как аргумент колбэка; `forget(channel)` убирает канал по `call.closed`, при
  уменьшении числа вызовов и в `stop()`. `web_mix_for_sip(channel)` вычитает
  СВОЙ канал. Shim `_with_channel` решает по инспекту сигнатуры
  (`_accepts_extra_arg`), можно ли передать канал, и кэширует решение: «передать
  наугад» = `TypeError`, который проглотит `except` рядом и звук потеряется
  МОЛЧА.
- **Приём поиска класса дефекта:** grep по константе-конкатенации
  (`PUBLISHER_ID + "-")` и по месту публикации — если N сущностей публикуют под
  одним id, то вычитание/агрегация по этому id врёт для N>1 гарантированно.
- **Грабля тестов (важнее самого бага).** `AudioMixSession.mix_excluding()`
  читает буферы микшера, а их наполняет только `tick()`. Без тика микшер
  отвечает тишиной на ЛЮБОЙ запрос, и проверки «слышит эхо / вычтен не свой
  канал» зелёные независимо от правильности вычитания. Обязательное условие
  различающего теста про звук: наполнить буферы (tick) и сравнивать ДВА разных
  запроса при одной публикации.
- **Вторая грабля того же среза:** порты поднимает не `start()`, а
  `ensure_ports()` (в бою — поллер/событие). Стенд, ждущий порты после
  `start()`, получает `[]` и падает как будто дефект в продукте.

## Шина медиа: канал публикации обязан убираться на КАЖДОМ пути выхода (2026-10-10)

- **Симптом.** Браузер, закрывший вкладку (или оборвавший WebRTC), остаётся в
  аудио-миксе всех остальных бессрочно: его застывший голос суммируется в каждый
  следующий микс. Проба боевым путём (менеджер с шиной → offer → трек с кадром →
  `close_session` → `AudioMixSession.tick()`): после закрытия
  `publishers() == ['web-1']` при нуле живых сессий, `latest_audio('web-1')` —
  ЕСТЬ, амплитуда микса 3000 до закрытия и 3000 после.
- **Корень.** `_MediaRelay` льёт кадры в `MediaBus` под `publish_id`, а
  `WebRTCManager._close_session` гасил реле́й и `RTCPeerConnection`, но шину не
  трогал. `MediaBus` держит последний кадр до `drop()`, а `tick()` собирает состав
  публикаторов ИЗ шины и для каждого зовёт `set_buffer` — поэтому существующая
  очистка микшера `if buffered not in publishers` мёртвый канал не удаляет
  никогда: он в этом списке и состоит.
- **Правка.** `WebRTCManager._forget_bus_channel()`: `bus.drop(publish_id)` при
  закрытии сессии, если канал наполнялся этой сессией (`_bus_frames > 0`) и под
  тем же id не осталось живого публикатора.
- **Почему второе условие не паранойя.** `publish_id` = id УЧАСТНИКА

## Отказ mediasoup: кэш «выключено» навсегда и ретрай, потёкший UDP-портами (2026-10-10, h323)

- **Симптом.** `features.web.mediasoup.enabled: true`, сайдкар живёт и отвечает,
  а панель показывает `mediasoup_rtp: None` — то же значение, что при реально
  выключенном режиме. Браузер при входе в SFU-конференцию получает 503
  «mediasoup не включён». Происходит, если первая попытка обратиться к сайдкару
  попалась в окно его старта (секунды после запуска приложения).
- **Корень 1 (кэш отказа).** В `WebSession` `False` в `_ms_signaling`/`_ms_rtp`
  значил и «оператор выключил», и «пробовали — не вышло». Ленивая фабрика
  начиналась с `if self._X is not None: return self._X or None`, поэтому
  транзиентный отказ запрещал любую повторную попытку до перезапуска процесса.
  Замерено пробой на живом коде (`mcuclient.mediasoup_client.MediasoupClient`
  подменён на «сначала мёртв, потом жив»): после того как сайдкар ожил, новых
  обращений к control API — ровно **0**, `plain_transports_created: 0`.
- **Корень 2 (утечка транспорта).** `MediasoupRtpBridge.stop()` делал
  `self._transport_id = None` — для сайдкара это «транспорт живёт дальше».
  Замерено живьём (Node + C++ worker, `rtc_min..rtc_max` сузён до 45100-45130,
  5 циклов `start()`/`stop()` одной комнаты): `transports 0 -> 5`,
  `producers 0 -> 5`, после `stop()` не освобождён ни один. Каждый висящий
  `PlainTransport` держит UDP-порт из `rtc_min..rtc_max` (по умолчанию
  40000-40100 = 101 порт) — при ретраях диапазон исчерпался бы примерно за
  17 минут непрерывных отказов, и сайдкар перестал бы создавать транспорты.
- **Почему молчало.** Ветка `except` в `mediasoup_signaling()` писала только
  `log.debug` и ставила `False`; отказ `bridge.start()` и отказа веба сводились
  к тому же `None`. Ни один тест не моделировал «сайдкар был мёртв, потом ожил»
  и не считал, сколько транспортов остаётся после остановки.
- **Правка.** `False` теперь значит ТОЛЬКО «выключено оператором»; отказ
  оставляет поле `None`, причина ложится в `_ms_signaling_error`/`_ms_rtp_error`,
  повтор разрешён не чаще `MS_RETRY_INTERVAL` (10 с, поле `_ms_rtp_retry_at`
  ОБЩЕЕ для обеих фабрик). `mediasoup_rtp.reason` и `_ms_unavailable()` (503)
  называют причину. Мост обязан звать `close_transport` на каждом отказе от
  уже созданного транспорта (`_close_remote_transport()`, в т.ч. из `stop()`;

## Согласование кодеков: ключ `name/clock` не видит битый `a=fmtp` (2026-10-10)

- **Симптом.** Polycom/Sony соединяется, согласованный аудиокодек в панели есть,
  звука нет. Для H.264, который в нашем списке есть, журнал пишет «нет в нашем
  списке кодеков». Слова «G.722.1C» в журнале не бывает, хотя в настройках
  терминала кодек подписан именно так.
- **Корень 1.** `negotiate()` сверял только `name/clock`. Битрейт G.722.1 НЕ
  выводится из потока — он обязан прийти в `a=fmtp bitrate=` (RFC 5577 §6,
  RFC 6134 §6), иначе декодер не знает размер кадра. `G7221/16000` +
  `bitrate=8000` совпадало по ключу и объявлялось согласованным.
- **Корень 2.** RFC 4566 порядка атрибутов не требует; шлюзы пишут `a=fmtp`
  раньше `a=rtpmap`, а прежний разбор требовал «rtpmap уже виден» и МОЛЧА терял
  описание → H.264 High приезжал без `profile-level-id`, и диагностика врёт
  («нет в списке» вместо «High profile не поддержан»). Дубль `a=rtpmap` на тот
  же PT стирал уже применённый `fmtp`.
- **Корень 3.** Причина clock-mismatch перечисляла ПЕРВЫЙ попавшийся наш rate
  («у нас G7221/16000» при том, что `max_compat` тянет 32k и 48k) — сообщение
  утверждало то, чего нет, и уводило правку не туда.
- **Правка.** `g7221_variant()` (16/32 кГц → `G.722.1`, 48 кГц → `G.722.1C` —
  то же слово, что в таблице терминала), `g7221_bitrate_issue()` (наборы
  16k: 24/32, 32k: 24/32/48, 48k: 48/56/64 + рекомендованный диапазон +
  кратность 400 — MUST обоих RFC), `_fmtp_issue()` вызывается ДО возврата
  «согласовано», `pending_fmtp` в разборе SDP, `_our_clock_rates()` — полный
  перечень в причине. Отсутствие `bitrate` — НЕ дефект здесь: «терминал не
  прислал» и «прислал невозможный» — разные diagnosis.
- **Приём поиска класса дефекта:** у любого «согласовано/принято» решения
  сверить, какие ПОЛЯ предложения в решении участвовали. Если ключ составлен из
  2 полей, а в предложении их 4 — два поля проверяются «на веру», и битое
  значение проходит как валидное. Симптом всегда один: соединение есть, медиа нет.
- **Грабля RED-замера:** откатывать надо ОДНУ правку за раз (подмена по
  уникальному якорю в копии файла), иначе непонятно, какой из трёх fixes что
  закрыл. Снималось в worktree на `bbf74cc` (чтобы чужой незакоммиченный срез не
  попал в меру): без `_fmtp_issue` падают 2 кейса, без `pending_fmtp` — 2, с
  одним rate — 1.
- **Регрессии:** `tests/test_codec_negotiation.py` (46) — битый битрейт
  отказывается, валидный G.722.1C 64k остаётся, неизвестный H.264 profile
  отказывается, `fmtp` до `rtpmap` применяется и переживает дубль `rtpmap`,
  причина отказа перечисляет 16000/32000/48000.
- **Не закрыто:** `fmtp`-контракт сверяется только для G.722.1 и H.264 (у G.719,
  opus, G.729 — нет); диагностика построена на SDP, т.е. это SIP-путь, а
  H.323-capability exchange (TCS) с той же тишиной в журнале — отдельная работа.

## DTMF в H.323: пять неочевидностей H.245 UserInput (2026-10-21)

- **Задача.** DTMF в H.323-контуре отсутствовал целиком (grep по
  `tools/h323d/*.cpp` и `mcuclient/h323_*.py` пуст), при этом SIP-сторона имела
  полное ядро `DtmfService`. Без тонов аппаратный терминал не набирает PIN в
  IVR — т.е. совместимость с Polycom/Sony была неполной по факту, а не по коду.
- **Wildcard НЕ добавляет UserInput-возможности.** `AddAllCapabilities(0,
  P_MAX_INDEX, "*")` внутри `H323Capabilities::AddAllCapabilities`
  (h323caps.cxx:3362) перебирает ключи фабрики МЕДИА-форматов; подтип
  `UserInput/*` там не появляется, и в самой библиотеке
  `AddAllUserInputCapabilities` не зовёт никто. Единственный образец, где её
  зовут, — `samples/simple/main.cxx:457`. Без явного вызова терминал по
  спецификации вправе не слать `UserInputIndication` вообще: DTMF мёртв при
  любых настройках, и ни один тест это не заметил бы.
- **Дефолт режима отправки в форке — alphanumeric.** `h323ep.cxx:767` ставит
  `SendUserInputAsString`. IVR и терминалы ждут H.245 `signal` (тон), поэтому
  хост фиксирует `SetSendUserInputMode(H323Connection::SendUserInputAsTone)`.
  При этом `GetRealSendUserInputMode` (h323.cxx:~5238) сам деградирует
  Tone→String, если у пира нет tone-возможности, — принуждать тон через
  возможности пир-специфично не нужно.
- **Базовый override звать нельзя.** `H323EndPoint::OnUserInputTone`
  (h323ep.cxx:3195) разворачивает принятый тон в `OnUserInputString`: вызов
  базы дал бы ДВА события на одно нажатие, причём второе — без длительности.
  Поэтому переопределены оба (`OnUserInputTone` даёт длительность,
  `OnUserInputString` ловит alphanumeric) и база не вызывается ни в одном.
- **`e_signalUpdate` приходит тоном-пробелом** (h323.cxx:5535): это «текущий
  тон ещё идёт», а не новый набор. Без `if (tone == ' ') return;` журнал
  удваивался бы на каждом длящемся нажатии. Замер живого стенда: лента пира
  `'12#7'` — ровно набранное, дублей нет.
- **In-band (RFC 4733) неотличим от H.245 signal.** Оба стекаются в
  `H323Connection::OnUserInputTone` (h323.cxx:5525 и :5565 — второй приходит из
  `OnUserInputInlineRFC2833`). Поэтому поле IPC-события называется `via`
  (`tone`|`string`), а не `method`, и значение `rfc2833` не встречается никогда
  — врать оператору «это был in-band» код не имеет права.
- **Отправка — строго под локом соединения:** `FindConnectionWithLock` →
  `SendUserInput` → `Unlock` (эталон `samples/simple/main.cxx:283-285`). Это
  РОВНО НЕ то, что выбрали для `AnsweringCall` (там прямой вызов именно из-за
  самодедлока): `SendUserInput` соединение не лоит, а лок держит объект живым
  на время записи PDU — голый указатель из реестра становился бы висящим, если
  `OnCleared` идёт параллельно.
- **Журнал комнаты обязан быть ОДИН.** Владелец — `DtmfService` SIP-движка;
  H.323 пишет через новый `record_external(digits, direction, participant_id,
  peer, method)` и публикует тот же `dtmf.digits` в том же формате. Второй
  список в `h323_endpoint.py` дал бы два расходящихся «МСУ принял тоны».
  Сырое событие хоста `dtmf.in` в шину уходит как `h323.dtmf` (`EVENT_MAP`),

- **Роутинг движка.** У H.323-участника нет pjsua2-`Call`, поэтому
  `DtmfService._targets` для него пуст и без роутинга панель отчёты

  на `native.handle_dtmf(id, digits)`; рассылка «всем» = SIP-плечо OR
  `native.send_dtmf_all(digits)` (возвращает число, а не bool — пустой список

- **Кросс-языковый страж.** Правка C++ не ломает ни один C++-тест, а панель

## Тональный автомат в Qt GUI: AST-guard вместо рантайма и три брака в самом guard'е (2026-10-21)

- **Симптом.** DTMF работает в стеке (хост + общий журнал + клавиатура в
  веб-панели), но в нативном клиенте `mcuclient/ui.py` поиск по `dtmf` даёт
  НОЛЬ совпадений: оператор за GUI не мог набрать PIN.
- **Класс дыры — «мёртвая возможность», третий раз за ветку** (1-й —
  `/api/webrtc/close`, 2-й — `POST /api/dtmf` панели, 3-й — тоны в Qt-окне).
  Проверять надо не только «сервер различает маршрут», но и «до фичи есть путь
  от ЧЕЛОВЕКА»: web-панель, Qt GUI, CLI — три отдельных входа, и починка одного
  не чинит остальные.
- **Почему GUI молчит в тестах:** PySide6 в CI не ставится (в `ci.yml` прямо
  написано, что тяжёлые GUI-зависимости не нужны), `MainWindow` строится
  внутри `if QT_AVAILABLE:` → в тестовом процессе класса нет вовсе,
  `hasattr(ui.MainWindow, '_on_dtmf_send')` даёт False даже после правильной
  правки. Единственный инструмент — AST по боевому исходнику (приём обкатан в
  `tests/test_ui_web_slots.py`, `tests/test_ui_close_event.py`).
- **Что обязан ловить AST-guard, кроме «метод существует»:** что слот

  поле отправляет; что журнал читает `engine.dtmf_history`, а не заводит второй

  кнопки — цикл по алфавиту ядра, а не 12 хардкодных.
- **Две ловушки Qt, невидимые для тестов:** (1) `clicked.connect(lambda: f(d))`
  в цикле замыкает ПЕРЕМЕННУЮ — все кнопки шлют последний символ алфавита,

  отправлять тон отдельно — строка тонов несётся одной посылкой (H.245
  UserInput / RFC 2833), иначе IVR получает рваный PIN.
- **Ошибки guard'а дороже ошибок кода — все три были мои:** (1) сверять имя
  сигнала надо по `c.func.value.attr`, а не `c.func.attr` (там всегда `connect`)

  завершающийся голым `return`: для проверки «нашли ли форму» нужен флаг или

- **Замер числа кейсов:** мини-раннер печатает «COLLECT test_ui_dtmf_panel.py::имя_кейса»

## Молчаливый отказ: 200 + {"ok": false} там, где док обещает HTTP-код (2026-10-21)

- **Симптом.** Панель: выбираешь камеру/микрофон — alert молчит, селектор стоит
  на выбранном пункте, а устройство не переключилось. Отличить «сработало» от
  «не сработало» оператору нечем.
- **Класс дыры — нарушенный СОБСТВЕННЫЙ контракт ответа.** `docs/WEB_CONTROL.md`
  определяет отказ как «`{"ok": false, "error": "..."}` С HTTP-КОДОМ», и весь
  фронт на этом построен: `api()` читает тело ответа только ради `error` при
  `!res.ok`. А `set_video_device`/`set_audio_device` отдавали 200 + `{"ok": ok}`
  без `error`. Проверка «что обещает док» дешевле реверс-инжиниринга фронта:
  расписание статусов (`grep -oE "status=[0-9]+" web_server.py | sort | uniq -c`)
  сразу показывает, какие маршруты выпали из общей схемы.
- **Дыра в две половины.** Даже честный статус не спас бы: `act()` звал
  `refresh()` только на успехе, а тумблеры/селекторы рисуются из `status` —
  отвергнутый выбор продолжал висеть выбранным. Чинить надо обе: код ответа +
  перерисовку состояния.
- **Порядок «refresh, потом alert» — не придирка.** `alert()` блокирует поток
  выполнения JS до закрытия диалога: первым он показал бы старый статус и
  отпустил страницу только после нажатия ОК — та же ложь с окном ошибки поверх.
- **У `refresh()` внутри catch обязан быть свой `.catch(() => {})`:** иначе
  упавший перечит статуса (движок мог умереть между запросами) подменяет
  настоящую причину «ошибкой обновления» и alert не состоится.
- **Прежде чем проверять `ok` на фронте — найти штатные `ok: false`.** В этом
  сервере их три: два нарушителя (устройства) и `mediasoup_leave`, где
  `ok: false` — штатный идемпотентный ответ (участника уже нет; заперт
  `tests/test_mediasoup_endpoints.py`). Наивная проверка «`if (!data.ok) throw`»
  в `api()` внедрила бы ложные alert'ы на штатные действия. Панель зовёт leave
  не через `act()`, а `api(...).catch(() => {})` — поэтому он и не пострадал.
- **Guard по исходнику обязан вырезать комментарии до поиска.** Проверка
  `re.search(r"refresh\(\)[^;\n]*", catch)` наткнулась на комментарий «Без
  refresh() панель оставалась показывать» и вернула красное «нет .catch()» на
  ПРАВИЛЬНОМ коде. Проверка, краснеющая на верном, вредна вдвойне: её «чинят»
  удалением guard'а. Лечится `_code_only()` (`re.sub(r"//[^\n]*", "")` плюс
  блочные комментарии). Второй случай той же болезни в этой ветке — `c.func.attr`
  вместо `c.func.value.attr` в `tests/test_ui_dtmf_panel.py`.
- **Страж чисел ловит и тебя, когда ты добавляешь тесты.** Каждый кейс,
  дописанный в файл, на который есть цитата, красит
  `test_cited_case_counts_match_the_runner`: `tests/test_web_server.py` (72)
  подрастал срезами с 41 — и цитата обязана поспевать КАЖДЫМ шагом, а не одним.
  Правится по факту, а не на глаз: `tests/_runner.py --collect-only` и подсчёт
  его строк `COLLECT` с именем файла.
- **Сам формат записи базы знаний стоит под стражем и спотыкается о прозу.**
  Две находки в одном абзаце: (1) запись вида «было 41, стало 44», поставленная
  в скобках сразу за именем файла, страж прочитал как заявленное 41 — после
  имени теста он берёт ПЕРВОЕ число в скобках, поэтому «было N» обязано стоять
  за скобкой; (2) пример команды, оканчивающийся двумя двоеточиями после имени
  файла, страж принял за ссылку «файл::символ» и покрасил её как усечённую.
  Правила записи: рядом с именем теста — только актуальное число, а конструкции
  «имя_файла.py::» в цитатах команд не пишутся вовсе.

  мёртвый маршрут сервера — неудобство, а маршрут панели в никуда — всегда битая
  кнопка, и зелёные тесты её не видят вовсе.

- **Не путать «обязательное поле» и «не задано».** `_opt_int` возвращает `None`

  отдельный `_require_dev`: пустое — 400, кривое — 400, строка `"5"` — валидна.

## Выгнанный из комнаты браузер возвращался в микс: связь «сессия ↔ участник» жила не там, где искали (2026-10-21)

- **Симптом.** `conference.leave` убирал участника из реестра и из шины
  (`bus.drop` работает), но его ingest-сессия выживала: `sessions()` по-прежнему
  `['webrtc-1']`, `pc.closed == False`, релей жив. Браузер выгнанного продолжает
  слать медиа (он не знает о выдворении), и следующий кадр **воссоздавал убранный
  канал**: `publishers()` снова `['web-1']` — застывший PCM в миксе всех. Тот же
  класс, что `POST /api/webrtc/close` (2026-10-10): серверную сторону закрывает
  только приложение.
- **«Забыли вызвать» и «нечем вызвать» — это разные правки.** `SessionInfo` поля
  `participant` не имеет, связь живёт только в `_MediaRelay.publish_id`. Пока её не
  предъявить наружу (`close_for_participant`, поиск по релеям), «добавь вызов
  `close_session`» физически невозможно написать — id сессии у вызывающего нет.
  Симптом («кнопка не чистит») всегда описывают словами первой формулировки;
  проверяй вторую, иначе правка упирается в сигнатуру на середине.
- **Хук реестра, а не вызов из HTTP-метода.** `WebSession.close()`/`restart()`
  выгоняют участников циклом прямо по `Conference`, поэтому освобождение, вписанное
  в `conference_leave()`, пережило бы и кнопку, и перезапуск. Правило: если у
  состояния есть несколько путей ухода, вешай очистку на **самый нижний** (реестр),
  а не на самый громкий (HTTP).
- **Порядок создания диктует способ связать.** `Conference` нужен `WebRTCManager`
  (его шина), значит менеджер не может быть создан раньше и аргументом хук не
  передать — только присваиванием после. Поле `on_leave` поэтому публичное.
- **Пространства имён id — отдельный тест.** У анонимного `offer`

  `ensure_future`, а цикл не крутился; в наборе есть зелёный

- **Симптом.** Штатное закрытие вкладки панели: серверные WebRTC-сессии и канал

- **Док врал в ЛУЧШУЮ сторону — и это самый тихий вид лжи.** В таблице

  дублирует запрос». Такого вызова в панели не было никогда. Ни одна из имевшихся
  сверок это не ловит: «док ↔ развилка сервера» — путь объявлен; «панель зовёт →
  сервер знает» — путь зовётся кнопкой. Находка получается только чтением тела

## Человекочитаемая подпись состояния: проверяй КТО её читает и чем индексируй словарь (2026-10-22)

- **ПРАВИЛО про потребителя.** Прежде чем чинить человекочитаемое поле, найди, кто

- **Термины — из интерфейса, а не из головы.** Подписи совпадают со словарём

## «Чинить нечем» обязано быть проверенным замером, а не выводом из прочитанного кода (2026-10-22)
